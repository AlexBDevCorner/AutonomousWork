# RM-004 — Migrate RepoManager from WPF to Avalonia for Linux compatibility

## Goal

Replace the Windows-only WPF presentation layer with Avalonia so RepoManager is
a .NET 10 desktop application that can run on both Windows and Linux while
preserving the existing repository-dashboard behavior, Git safety rules,
keyboard-driven workflow, and persisted user data model.

## Context

- Project: `repomanager`.
- Target repository: `AlexBDevCorner/RepoManager`.
- The current `RepoDashboard.App` targets `net10.0-windows` with
  `UseWPF=true` and uses WPF/XAML, `System.Windows`, `Microsoft.Win32`
  folder picking, WPF clipboard APIs, and Windows Terminal-specific behavior.
- `RepoDashboard.Core` and `RepoDashboard.Infrastructure` already target
  platform-neutral `net10.0`; preserve them where practical rather than
  rewriting domain/application logic.
- `GitCommandRunner` already invokes `git` through
  `System.Diagnostics.Process`; preserve the existing Git safety boundary.
- Existing configuration/state JSON formats and repository IDs are user data
  and must remain compatible.
- This task explicitly requires target-framework and package changes in the App
  and App.Tests projects. That is intentional and overrides the normal
  "do not change target frameworks/packages unless required" restriction.
- The autonomous worker must not modify `.github/`; Linux CI can be added as
  a separate control/repository-maintenance change after this migration.

## Requirements

1. Replace WPF in `RepoDashboard.App` with Avalonia Desktop while keeping the
   existing project/assembly identity unless a change is technically required.
   The application project MUST target platform-neutral `net10.0`; it MUST NOT
   target `net10.0-windows` or use `UseWPF`.
2. Port the main window and all current dialogs/views to Avalonia:
   - main repository dashboard;
   - repository discovery dialog;
   - repository rename dialog;
   - repository removal confirmation;
   - keyboard-shortcut reference.
   Preserve the current user-visible functionality and overall information
   hierarchy; pixel-identical rendering is not required.
3. Preserve the existing MVVM approach with CommunityToolkit.Mvvm and the
   Microsoft.Extensions hosting/DI/logging composition. Core and Infrastructure
   MUST remain independent of Avalonia.
4. Remove production dependencies on WPF/Windows-only UI APIs, including
   `System.Windows`, WPF `Clipboard`, and `Microsoft.Win32.OpenFolderDialog`.
   Use Avalonia-supported APIs/services for windows, dialogs, storage/folder
   picking, clipboard access, and application lifetime.
5. Preserve all existing commands and keyboard shortcuts, including the
   RM-003 `Copy Branch` action and `Ctrl+Shift+B`. Disabled-state semantics
   must remain consistent with the current application.
6. Introduce presentation/platform abstractions where needed so view models do
   not directly depend on Avalonia static/global UI APIs. Clipboard behavior,
   folder selection, confirmation/name dialogs, opening folders, and terminal
   launching must remain testable without a real desktop session.
7. Make desktop integration work on Windows and Linux:
   - Open Folder must use an appropriate platform mechanism and fail with the
     existing user-visible error style instead of crashing.
   - Open Terminal must continue to support Windows Terminal when available and
     support Linux through an available terminal launcher. Prefer an explicit
     `$TERMINAL` when usable, otherwise common/default Linux terminal launchers.
     If no supported terminal is available, the action must be disabled or
     return a clear non-fatal status; do not hard-code `wt.exe` as the only
     implementation.
   - macOS-specific behavior is not required.
8. Keep Git invocation shell-free and preserve all existing safe-update rules:
   no new commit/push/checkout/merge/rebase/reset/stash behavior, and mutation of
   the checked-out branch remains exclusively through the existing safe
   fast-forward updater.
9. Make Git-not-found messaging platform-neutral. It must no longer instruct
   Linux users to install "Git for Windows" or require `git.exe`; the runtime
   requirement is `git` available on PATH.
10. Make path identity semantics correct on both operating systems. Windows path
    comparisons may remain case-insensitive; Linux path comparisons MUST respect
    case sensitivity. Remove unconditional `OrdinalIgnoreCase` assumptions
    where they represent filesystem/repository path identity or duplicate
    detection. Preserve deterministic ordering behavior that is unrelated to
    filesystem identity.
11. Preserve persisted configuration/state compatibility. Existing
    `repositories.json` and `state.json` files must continue to load without
    migration or data loss. Continue using an OS-appropriate local application
    data directory via .NET platform APIs; update Windows-only documentation
    wording accordingly.
12. Convert `RepoDashboard.App.Tests` to platform-neutral tests. It MUST NOT
    target `net10.0-windows` or use `UseWPF`. Replace real WPF clipboard/UI
    dependencies with test doubles or Avalonia-compatible testable abstractions.
    Retain regression coverage for existing command behavior, disabled states,
    shortcuts, dialogs/wiring where practical, and RM-003 Copy Branch behavior.
13. Update `AGENTS.md`, `README.md`, and architecture/runtime documentation
    that directly describes the application as Windows-only/WPF so the repository
    consistently describes Avalonia, Windows + Linux support, platform-neutral
    Git requirements, and supported publish commands.
14. Do not remove existing RepoManager functionality merely because a WPF API
    has no one-to-one Avalonia equivalent. Adapt the interaction using Avalonia
    patterns while preserving the user outcome.
15. Keep the migration focused. Prefer reusing the existing Core,
    Infrastructure, view models, models, and services where they are already
    platform-neutral. Do not rewrite working Git/domain logic just to make the
    migration look more complete.

## Architectural direction

- Treat this primarily as a presentation/platform migration:
  `Avalonia App -> Core + Infrastructure`, preserving the existing dependency
  direction.
- Use the current stable Avalonia Desktop packages compatible with .NET 10.
  Include the normal Avalonia desktop/theme packages needed by the application;
  do not introduce an unrelated UI framework.
- Prefer small injected services such as clipboard/desktop-launch integration
  over referencing Avalonia `TopLevel` or platform APIs throughout
  `MainWindowViewModel`.
- Avalonia's storage provider is the preferred direction for folder picking.
- Keep dialog ownership/lifetime explicit so modal windows behave correctly on
  both Windows and Linux.
- Keep the current repository row/view-model state as the source for presentation
  commands; Copy Branch must not add a Git query.
- For filesystem path equality, centralize the OS-specific comparer rather than
  scattering `OperatingSystem.IsWindows()` checks across unrelated code.
- Do not change `.github/` in this task. The existing Windows autonomous worker
  must still be able to build/test the migrated solution and cross-publish the
  Linux artifact.

## Acceptance criteria

- [ ] `RepoDashboard.App` is an Avalonia Desktop application targeting
      `net10.0`, with no `UseWPF`, `net10.0-windows`, or production
      `System.Windows` dependencies.
- [ ] Main window plus all existing dialogs are implemented with Avalonia and
      expose the same core user workflows.
- [ ] Existing refresh/fetch/safe-update behavior and safety rules are preserved.
- [ ] Add/discover/rename/remove/reorder repository workflows are preserved.
- [ ] Open Folder, Open Terminal, Copy Path, and Copy Branch are supported through
      cross-platform/testable presentation services; Linux is not hard-coded to
      Windows Terminal.
- [ ] Existing keyboard shortcuts are preserved, including
      `Ctrl+Shift+B` for Copy Branch and `F1` for shortcut help.
- [ ] Git-not-found messaging is platform-neutral and checks `git` on PATH.
- [ ] Repository path identity is case-insensitive on Windows and case-sensitive
      on Linux where filesystem identity matters.
- [ ] Existing configuration/state JSON remains readable without migration.
- [ ] `RepoDashboard.App.Tests` targets platform-neutral `net10.0`, has no
      `UseWPF`, and does not require a real system clipboard or interactive
      desktop for normal unit tests.
- [ ] The complete existing test suite passes after adaptation; tests removed or
      rewritten because they were WPF-specific are replaced with equivalent
      behavioral coverage rather than silently dropped.
- [ ] A Windows x64 self-contained publish succeeds.
- [ ] A Linux x64 self-contained publish succeeds from the autonomous worker,
      providing structural evidence that the app and dependency graph are not
      Windows-targeted.
- [ ] README/AGENTS/architecture docs no longer describe RepoManager as WPF or
      Windows-only and include Windows and Linux run/publish guidance.
- [ ] No changes are made under `.github/` or `control/`.

## Verification

Run from the RepoManager repository root:

```powershell
dotnet build RepoDashboard.slnx --nologo
```

Expected: build succeeds with no errors.

```powershell
dotnet test RepoDashboard.slnx --nologo
```

Expected: all test projects pass.

```powershell
dotnet publish src/RepoDashboard.App/RepoDashboard.App.csproj -c Release -r win-x64 --self-contained true --nologo
```

Expected: Windows x64 self-contained publish succeeds.

```powershell
dotnet publish src/RepoDashboard.App/RepoDashboard.App.csproj -c Release -r linux-x64 --self-contained true --nologo
```

Expected: Linux x64 self-contained publish succeeds from the Windows worker
without Windows-targeting errors.

Additionally verify by repository inspection that production/App.Tests sources
do not retain WPF-only references or Windows-only target-framework settings.

## Out of scope

- No new Git operations or expansion into a full Git client.
- No redesign of Core Git/update safety rules beyond platform-correct path
  semantics and platform-neutral Git availability messaging.
- No changes to `.github/`, CI runner topology, or autonomous-control wiring.
- No requirement to run an interactive Linux GUI session inside the Windows
  autonomous worker; a real Linux smoke run/CI job can be added separately after
  this migration.
- No macOS compatibility certification or macOS-specific desktop integration.
- No installer/package-manager work (MSIX, deb/rpm, Flatpak, AppImage, etc.).
- No unrelated visual redesign, new features, or broad refactoring outside what
  is needed for the Avalonia migration and cross-platform behavior.

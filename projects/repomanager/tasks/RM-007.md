# RM-007 — Restore repository grid rendering after Avalonia migration

## Goal

Fix the RepoManager regression where repositories are loaded internally after the
Avalonia migration but the main repository grid is visually empty, making
existing repositories appear to be missing and causing attempts to add them
again to fail as duplicates.

Restore visible repository rows without changing or migrating the existing
repository configuration, and improve add-failure feedback so duplicate or
invalid repositories do not collapse into an unhelpful aggregate message.

## Context

- Project: `repomanager`.
- Target repository: `AlexBDevCorner/RepoManager`.
- RM-004 migrated the application from WPF to Avalonia.
- RM-005 fixed the startup crash caused by named Avalonia controls not being
  initialized correctly.
- After those changes the application now starts, but the central repository
  list/grid is blank.
- A selected repository can still appear in the details panel. For example,
  the current UI shows details for a repository named `Store` while the
  `DataGrid` area itself is empty. This strongly indicates that repositories
  are present in the view model but the Avalonia `DataGrid` is not rendering.
- The current `src/RepoDashboard.App/App.axaml` registers only:
  ```xml
  <Application.Styles>
    <FluentTheme />
  </Application.Styles>
  ```
- RepoManager uses the separate `Avalonia.Controls.DataGrid` package. Avalonia
  requires the DataGrid theme resources to be included explicitly. The missing
  DataGrid Fluent theme is the primary suspected cause and must be verified by
  the implementation.
- `MainWindow.axaml` contains the real repository grid:
  ```xml
  <DataGrid x:Name="RepositoryGrid"
            ItemsSource="{Binding Repositories}"
            SelectedItem="{Binding SelectedRepository, Mode=TwoWay}"
            AutoGenerateColumns="False"
            IsReadOnly="True"
            SelectionMode="Single"
            CanUserSortColumns="False">
  ```
- Existing repository persistence was intentionally kept compatible during
  RM-004. On Windows, `JsonRepositoryConfigurationStore.DefaultPath()` still
  resolves through `Environment.SpecialFolder.LocalApplicationData` to:
  ```text
  %LOCALAPPDATA%\RepoDashboard\repositories.json
  ```
  Do not assume existing repositories were lost and do not introduce a data
  migration unless investigation proves a separate persistence defect.
- The current multi-add implementation catches failures per selected path. For
  multiple failures it only reports an aggregate such as:
  ```text
  Added 0 of 2 repositories. 2 could not be added.
  ```
  This hides useful reasons such as "already on the dashboard" and makes the
  rendering regression look like an add/persistence failure.

## Requirements

1. Reproduce the blank repository-grid behavior on the current RepoManager
   `master` branch using persisted or test repository rows.
2. Confirm the root cause before changing persistence or repository-loading
   logic.
3. Register the Avalonia DataGrid theme/resources required by the version of
   `Avalonia.Controls.DataGrid` used by RepoManager. For the current Fluent
   setup this is expected to be equivalent to:
   ```xml
   <StyleInclude Source="avares://Avalonia.Controls.DataGrid/Themes/Fluent.xaml" />
   ```
   under `Application.Styles`, alongside `<FluentTheme />`.
4. After application initialization, repository rows already present in
   `MainWindowViewModel.Repositories` must render visibly in
   `RepositoryGrid`.
5. Existing repositories persisted before the Avalonia migration must remain
   compatible. Do not delete, rename, relocate, reset, or rewrite
   `repositories.json` merely to make the UI appear correct.
6. Preserve the current Windows configuration location and JSON schema unless a
   separate, independently demonstrated persistence defect is discovered.
7. Add runtime-oriented regression coverage for the rendering/resource issue.
   XML-only assertions that a `DataGrid` element exists are insufficient.
   The test should initialize Avalonia resources sufficiently to detect a
   missing DataGrid theme/style and should exercise a grid bound to repository
   rows where practical.
8. Keep the existing RM-005 runtime named-control/startup tests. Extend the
   Avalonia headless test setup if necessary rather than replacing it with
   text-only AXAML tests.
9. Improve the multi-add failure presentation so the user can understand why
   selected repositories were not added:
   - retain per-path/per-repository failure reasons already collected by
     `AddRepositoriesAsync`;
   - when all selected repositories fail, do not show only
     `N could not be added`;
   - duplicate repositories should visibly state that they are already on the
     dashboard;
   - invalid/non-Git directories should expose their useful validation reason;
   - keep the status concise enough for normal use, but do not discard the only
     actionable error information.
10. Preserve Task 48 partial-success semantics:
    - valid repositories are still added even when another selected path fails;
    - no rollback;
    - duplicate selected paths are attempted once;
    - selection order is preserved.
11. Do not weaken repository validation in
    `RepositoryDashboardService.AddAsync`. A repository already configured
    must continue to be rejected rather than duplicated.
12. Do not add a second repository list or bypass the existing
    `Repositories` / `SelectedRepository` bindings to work around rendering.
13. Keep the change focused on Avalonia resource/rendering correctness,
    regression coverage, and add-failure feedback. Do not redesign the whole
    main window.

## Architectural direction

- Treat the blank grid primarily as an Avalonia application-resource/theme
  regression until proven otherwise.
- Keep `MainWindowViewModel` free of Avalonia resource or styling logic.
- Application-level Avalonia styles belong in `App.axaml`.
- Keep repository persistence owned by
  `JsonRepositoryConfigurationStore` and repository validation owned by
  `RepositoryDashboardService`.
- Reuse the existing `AddRepositoryFailure` information instead of
  re-validating repositories in the UI.
- Prefer a regression test that would fail if the DataGrid package remained
  referenced but its required theme resources were removed again.
- Preserve the existing Fluent application theme and the current DataGrid
  bindings, sorting restrictions, selection behavior, keyboard focus, context
  menu, and shortcuts.

      duplicate.

      `Added 0 of N repositories. N could not be added.`.
- [ ] Mixed multi-add still preserves successful additions when other paths
      fail.
- [ ] Automated runtime/headless regression coverage would catch removal of the
      required DataGrid theme/resources.
- [ ] Existing RM-005 startup/named-control tests continue to pass.
- [ ] Existing `MainWindowXamlTests`, App tests, Core tests, and Integration
      tests continue to pass.
- [ ] Repository ordering, rename/remove behavior, Git safety behavior,
      keyboard shortcuts, and fetch/update behavior are unchanged.
- [ ] No changes are made under `.github/` or `control/`.

## Verification

Run from the RepoManager repository root:

```bash
dotnet build RepoDashboard.slnx --nologo
```

Expected: build succeeds with no errors.

Run the application tests, including the new Avalonia DataGrid resource/runtime
regression:

```bash
dotnet test tests/RepoDashboard.App.Tests/RepoDashboard.App.Tests.csproj --nologo
```

Expected: all App tests pass. The new regression must exercise initialized
Avalonia resources/runtime behavior rather than merely parse AXAML text.

Run the full solution:

```bash
dotnet test RepoDashboard.slnx --nologo
```

Expected: all tests pass.

For a Windows smoke check:

```powershell
dotnet run --project src/RepoDashboard.App/RepoDashboard.App.csproj
```

With an existing `%LOCALAPPDATA%\RepoDashboard\repositories.json` containing
repositories, verify:

1. existing repositories appear as rows immediately after loading;
2. selecting a row updates the details panel normally;
3. adding an already-configured repository does not duplicate it and reports a
   useful duplicate reason;
4. selecting multiple repositories with a mix of valid, duplicate, and invalid
   paths keeps valid additions and reports useful failure information.

## Out of scope

- No repository configuration migration unless a separate persistence bug is
  reproduced.
- No change to Git fetch/update/safety algorithms.
- No redesign of the repository dashboard.
- No new repository-storage format.
- No removal of existing keyboard-first behavior.
- No CI/autonomous-worker runner changes; those belong to RM-006.
- No unrelated feature work.

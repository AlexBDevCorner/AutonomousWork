# MSS-075 — Reconcile completed qualifiers with Dashboard postseason progress

## Goal

Make the Dashboard and Qualifiers page agree on actual, persisted qualifier progress. When all postseason qualifiers have already finished, Dashboard must not report zero progress or offer to run them again; it must recognize completion and expose the next legitimate postseason step. Preserve existing results and make resume/navigation safe and predictable.

## Context

- Project: `mtgsolosports`; target repository: `AlexBDevCorner/MtgSoloSports`, branch `main`.
- Reported 2026-10-11 using two screenshots of the **same save and Season 3** (`NewTest`), with three feeder levels.
- On **Qualifiers**, the heading says `Season 3 qualifiers — 17/17 complete`. All entries show **COMPLETE**:
  - Superleague qualifier: **1/1 complete**, field of 32 athletes, 16 rounds, top 8 qualify.
  - Feeder 1 ↔ Feeder 2: **8/8 complete** (one per color), each with 16 athletes, 16 rounds, top 8 qualify.
  - Feeder 2 ↔ Feeder 3: **8/8 complete** (one per color), each with 16 athletes, 16 rounds, top 8 qualify.
- On **Dashboard**, however, the progress strip has **Qualifier** highlighted, says **0/17 qualifiers · 0/272 total rounds**, and offers **Open 17 qualifiers** and **Run all rounds**. It also says **Next: Run 17 qualifiers**. The `Phase` metric is `AutomaticMovementResolved`.
- This is not just a cosmetic difference. It suggests that per-qualifier completion/results and the Dashboard's postseason step/progress source may be out of sync, preventing progression and potentially inviting a duplicate run.
- Expected progress for the exact reported save is **17/17 qualifiers complete** and **272/272 qualifier rounds** *if all 16 rounds per qualifier are persisted*, followed by the actual next legal step (normally **Rebalance feeders**, subject to authoritative workflow guards).
- Other work addresses qualifier presentation and live progression; investigate the existing implementation before attributing the root cause to caching, derived counters, workflow state, or persistence.

## Requirements

1. **Reproduce and trace the discrepancy.**
   - Trace how Qualifiers derives the `COMPLETE` badges and the 17/17 summary, how Dashboard derives the 0/17 and 0/272 counts, and how the season/postseason phase and current step are persisted and advanced.
   - Include both the backend lifecycle/status API and frontend state/cache/query handling, as applicable. Determine whether this is stale UI state, separate progress storage, an uncommitted transition, incorrect aggregate calculation, or a combination.
   - Use an actual or fixture-based Season 3 save with three feeder tiers and all 17 qualifier competitions completed; do not just adjust text based on the screenshots.

2. **Derive consistent, authoritative progress from persisted execution state.**
   - Dashboard and Qualifiers must agree on qualifier completion for the selected season, including totals and the completed round count.
   - Correct progress should survive navigation between Dashboard/Qualifiers/Live, browser refresh, new application sessions, and resumed saves.
   - Support partially completed qualifiers and mixed completion across Superleague and multiple feeder tiers; do not hardcode 17, 272, or a particular number of tiers.
   - Use persisted results/round execution status as appropriate instead of trusting UI-only counters. A completed qualifier should not be counted as pending, and a qualifier with missing rounds/results must not be falsely considered complete.
   - Handle invalid or inconsistent persisted state deterministically, with an actionable error/recovery path rather than silently overwriting results.

3. **Unblock the real postseason state machine.**
   - When the last required qualifier is completed, resolve the current workflow step from authoritative lifecycle state and move to the **next legal postseason step**. In the reported flow this should normally be **Rebalance feeders**, once its prerequisites are satisfied.
   - Ensure that finishing qualifiers through the Qualifiers page, running them individually or via a bulk action, and resuming a completed save all converge to the same state. Any required finalization/reconciliation must be idempotent.
   - Do not advance when some qualifiers/rounds are genuinely unfinished or when other required preconditions are unmet.
   - Do not simply change the visual step label to make it appear finished while the backend still blocks progression.

4. **Prevent duplicate or destructive runs.**
   - Once all qualifiers are complete, hide/disable run actions for the completed set and display a useful completion summary / next-step action instead.
   - A stale client or direct repeat of **Run all rounds** must not regenerate completed qualifiers, overwrite standings/results, award duplicate outcomes, or repeat movement.
   - If some work is incomplete, only eligible unfinished work should run; resuming or retrying must respect idempotency and progression guards.

5. **Refresh and present state consistently.**
   - Make Dashboard reflect mutations performed from the Qualifiers page and vice versa, without requiring a manual refresh or showing stale zeroes indefinitely.
   - If a backend reconciliation or status refresh is pending, show a correct loading/updating state rather than confident but wrong `0/17` / `0/272` progress.
   - Keep counters and next-step descriptions accurate for an in-progress, partially complete, and fully complete season. Any season selector must use that season's own progress data.

## Architectural direction

- First inspect the source of truth used by qualifier details, completion aggregation, season workflow/phase resolution, Dashboard data loading, and the bulk runner.
- Prefer a single authoritative model or a consistent server-derived status projection used by both pages. Fix the underlying state transition or persistence issue if found, rather than masking it in JSX.
- Use existing app conventions for API/query invalidation and stable progression transitions. Keep re-entry and completion operations idempotent, especially after navigation/restart.
- Preserve legacy/completed saves when possible; add narrowly scoped compatibility/reconciliation behavior only if existing persisted data genuinely requires it.
- Avoid changing the qualifier competition format or re-running outcomes during reconciliation.

## Acceptance criteria

- [ ] With the reported three-feeder-tier Season 3 state, Qualifiers still shows **17/17 complete** and Dashboard no longer shows **0/17 · 0/272**. It correctly shows the persisted completed qualifier and round totals (expected **17/17**, **272/272** for the described fully persisted rounds).
- [ ] Dashboard no longer says **Next: Run 17 qualifiers** or offers **Run all rounds** when all qualifiers are already complete; it presents the real next legal step instead.
- [ ] After all qualifiers finish, the lifecycle can continue to feeder rebalancing (or the actual next legal step) without any forced rerun or manual data repair.
- [ ] Moving between Qualifiers, Dashboard and Live, switching away and back to Season 3, refreshing, and reopening the save produce consistent progress and step selection.
- [ ] Partial progress is accurately represented (individual completed qualifiers, rounds, pending qualifiers) across both pages. Works for one and three feeder-tier universes without hardcoded counts.
- [ ] Repeating a completed/bulk qualifier-run request cannot duplicate matches/awards, change completed results, or corrupt competition state.
- [ ] Any server/client reconciliation is safe for persisted completed saves and does not silently mark genuinely incomplete competitions as finished.
- [ ] Focused regression tests cover full completion, partial completion, refresh/reload/resume, step progression, and repeat-run safety; existing automated checks remain green.

- No unrelated Cup workflow changes or global postseason restructuring beyond the minimum required to correctly advance from completed qualifiers.

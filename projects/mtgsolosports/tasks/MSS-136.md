# MSS-136 - Remove save-size limits from local agent snapshot acquisition

## Goal

Let local coding/journalist agents acquire and query an existing MtgSoloSports save regardless of its size, subject only to available disk space and platform limits. Large saves must work by default without editing code, raising configuration limits or exporting manually.

## Context

- Project: `mtgsolosports`; target repository: `AlexBDevCorner/MtgSoloSports`, branch `main`.
- The user runs the game locally in Docker using the default localhost-bound Compose deployment and explicitly accepts very large saves. They requested this task and authorized `status: ready` immediately.
- MSS-133/MSS-134/MSS-135 introduced `tools/SaveSnapshot` and the local journalist workflow. The user's configured agent invoked `acquire` against the running game but failed with `[snapshot] failed: Save bundle exceeds the 268435456 byte import limit.` It could not query the save.
- `SaveBundle.MaxBundleBytes` and `SaveBundle.MaxDatabaseBytes` both equal 256 MiB. `SnapshotAcquirer` caps the HTTP download and bundle bytes; `Program.ReadBundleFileAsync` caps offline input; shared extraction also rejects oversized bundles and database entries. Changing the download check alone leaves other blockers.
- The current export/helper path uses whole-bundle `byte[]`/`MemoryStream` buffering. Simply replacing 256 MiB with a bigger number leaves memory growth and array-size limitations. Relevant files include `Persistence/Saves/SaveBundle.cs`, `SaveStore.cs`, `Features/Saves/ExportSave`, `tools/SaveSnapshot/{Program,SnapshotAcquirer,SnapshotReader}.cs`, and the snapshot/journalist guides.

## Requirements

1. Remove fixed compressed-bundle and extracted-database size ceilings from the normal local snapshot workflow. Both HTTP `acquire` and explicit offline `acquire --bundle` must accept valid saves above 256 MiB without an opt-in flag or a new configured maximum. Do not substitute a larger arbitrary cap. Retain sensible bounds on small metadata and query output; those are unrelated to save size.
2. Make the necessary export-to-acquisition path stream through temporary files with bounded buffers, including archive creation/download, archive reading/extraction and checksum calculation as applicable. Production snapshot acquisition must not require the entire ZIP or SQLite database in a byte array or memory stream. Use file/stream APIs and wide byte counts so multi-gigabyte artifacts are not constrained by array lengths or 32-bit size arithmetic. Preserve existing public export behavior and bundle compatibility; old small bundles remain readable.
3. Keep the normal path on the existing loopback export endpoint and current Compose deployment. No Docker socket, container shell, volume remap, new port, hosted service or external account is required. The existing user config and documented agent commands continue to work after rebuilding the updated application/helper.
4. Preserve archive shape/path validation, checksum verification, explicit save identity, supported schema/rules/RNG checks and read-only SQLite inspection. Acquisition must never import, migrate, repair or simulate the source save or consume sporting RNG. Keep snapshot consistency under concurrent game progress; never copy a live SQLite file/WAL directly.
5. Preserve failure behavior: failed/cancelled downloads, truncated/corrupt archives, validation errors and file/disk failures must not replace a previously valid snapshot or label stale data as fresh. Clean up temporary download/extraction/export files and dispose streams on success and failure, including Windows file-sharing behavior. Cancellation must remain effective during long transfers. Timeouts must not silently reintroduce an impractical large-save ceiling; document the behavior.
6. Add focused deterministic regression coverage for a valid database above the old 256 MiB extracted limit and a bundle/download above the old 256 MiB compressed limit. Cover HTTP acquisition without relying on Content-Length, offline input, successful read-only queries after acquisition, and preservation of a prior snapshot after a failed large transfer/validation. Exercise the real production paths; tests that only assert changed constants are insufficient. Generate temporary filler data/streams rather than simulating seasons or committing large artifacts. Verify source database/RNG immutability and retain existing malformed-bundle checks.
7. Update `docs/journalist-snapshot.md` and relevant workflow/export documentation with the large-save behavior, disk/temp-file expectations, refresh semantics and a manual smoke test against the default Docker deployment. Clearly distinguish tests actually executed from user-save/Docker checks unavailable to the worker. No real user save or machine-specific configuration may be committed.

## Architectural direction

Use the smallest maintainable change to existing export/acquisition/persistence helpers. Changes in shared save-bundle code and the export feature are authorized only where necessary for this complete snapshot path. Keep ordinary game-import policy unchanged unless a change is necessary for shared compatibility; snapshot acquisition must not inherit an unrelated import cap. Preserve the existing ZIP/manifest contract and read-only query interface. Do not introduce a generic streaming framework, background job system or new package solely for moving files. Follow target `AGENTS.md`, including feature locality, pure simulation kernel and test selection rules. The simulation kernel and sporting rules need no changes.

## Acceptance criteria

- [ ] An agent can acquire a valid save exceeding both former 256 MiB thresholds from the local Docker app with existing configuration, then query save identity/current season and obtain stage evidence.
- [ ] Explicit offline acquisition also accepts large valid bundles; neither path requires a size override or code edit.
- [ ] The production export/download/extraction path uses bounded buffers and temporary files, without whole-artifact byte arrays or arbitrary replacement size ceilings.
- [ ] Corrupt, mismatched, interrupted or cancelled acquisition preserves the previous valid snapshot and cleans temporary resources; inspection never changes source sporting state or RNG.
- [ ] Focused tests execute the above-limit cases through production paths and existing snapshot/export compatibility tests pass.
- [ ] Documentation includes exact rebuild/acquire/query smoke commands and practical disk/timeout behavior; verification reports honestly identify any unperformed Docker/user-save check.

```sh
dotnet test MtgSoloSports.slnx --configuration Release --no-build --no-restore --logger 'trx;LogFileName=timing.trx'
dotnet format MtgSoloSports.slnx --verify-no-changes --no-restore
```

Run each changed test class alone in a fresh process as required by `AGENTS.md`, and run `python3 scripts/test-timing.py <actual-path-to-timing.trx> --top 20`. Run any other applicable repository gates. Tests must not depend on Docker, external services or the user's real save.

Manual smoke, when a local Docker environment and an explicitly configured large test save are available:

```sh
docker compose up --build -d
dotnet build tools/SaveSnapshot/MtgSoloSports.SaveSnapshot.csproj --configuration Release
dotnet run --project tools/SaveSnapshot --configuration Release --no-build -- acquire --config tools/SaveSnapshot/snapshot.config.json
dotnet run --project tools/SaveSnapshot --configuration Release --no-build -- query --config tools/SaveSnapshot/snapshot.config.json --sql "SELECT SeasonNumber, HasSuperleague, IsComplete FROM Seasons ORDER BY SeasonNumber;"
dotnet run --project tools/SaveSnapshot --configuration Release --no-build -- evidence --config tools/SaveSnapshot/snapshot.config.json
```

Expected: acquisition succeeds above the old limits, queries match the selected save, and evidence resolves the latest completed Superleague stage when one exists. Also exercise offline acquisition of the same large exported bundle. Record actual sizes and completed checks; unavailable manual checks must be reported rather than claimed.

## Out of scope

- Simulation, sporting rules, schema/game-rule migrations, season/cup behavior or save-data pruning/compaction to fit a limit.
- Broad redesign of ordinary game import, backup, checkpoint or restore features beyond necessary shared compatibility.
- New authentication, network exposure, cloud/Drive integration, Docker administration requirements or global agent settings.
- Automatic journalism, scheduling, article publication, unrelated UI work or modifying other AutonomousWork tasks.
- Committing snapshots, generated large fixtures, real save identifiers, user archives or local configuration.

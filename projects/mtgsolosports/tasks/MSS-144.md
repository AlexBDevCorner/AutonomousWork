# MSS-144 - Give corrupted-save failures their own HTTP failure class

## Goal

Server-side sporting-state corruption must be reported as a server failure (500 with a clear message), never as a client error (400/409), and no handler may swallow or downgrade a corruption signal. This is a correctness/observability fix; it must not change any sporting outcome, persisted payload, RNG sequence, or save schema.

## Context

- A repository review (2026-11-19) verified the following current-code evidence; re-verify on the live checkout before implementing, line numbers may drift.
- Every minimal-API endpoint maps `InvalidOperationException` to 400 (e.g. `src/MtgSoloSports/Features/Simulation/AdvanceRound/AdvanceRoundEndpoint.cs:34-37`), while handlers throw `InvalidOperationException` for invariant failures such as missing RNG state or a corrupt stage (`AdvanceRoundHandler.cs:119,148,324,329`). A broken universe is therefore indistinguishable from a bad request. AGENTS.md rule: invariant failures abort the mutation - they do abort, but with the wrong failure class.
- `Features/Seasons/GetSeasonStatus/GetSeasonStatusHandler.cs:100-104` catches `(InvalidOperationException or SqliteException)` and returns legacy-formula defaults, so a corrupt/missing activation row is silently reported as a healthy legacy save; the status drives `SimulateSeasons`/`AdvanceToNextEvent` orchestration.
- `Features/Seasons/StartNextSeason/StartNextSeasonHandler.cs:233-241` (`EnsureChaosCompleteAsync`) converts all `InvalidOperationException` from the Chaos lifecycle into a 409 retry signal, downgrading corruption to a user-retryable conflict.
- Message-sniffing control flow: `Features/Seasons/SeasonLifecycle/SeasonLifecycleEvaluator.cs:189,250` and `Features/Cups/SelectChaosCupField/SelectChaosCupFieldHandler.cs:146` branch on `ex.Message.Contains("predates Chaos")`; `Persistence/Saves/SaveStore.cs:324-329,346-351` matches `SqliteErrorCode == 1 && Message.Contains("ChaosCupActivations")`, which also matches a genuine *missing column* error on an already-migrated save, swallowing a real schema defect.
- `Features/Simulation/CompleteStage/CompleteStageHandler.cs:101-106` and `Features/Reports/GoogleDrivePublishing/DriveCallbackHandler.cs:150-153,188-191` swallow exceptions without logging.
- Diagnostics handlers (`Features/Diagnostics/LongRunInvariants`, `LongRunChecksum`, `LongRunStats`, e.g. around lines 28-31 of each handler) call `OpenDbContext` before `EnsureMigratedAsync`, inverted versus every other handler, so the migration-rollback path can replace the file while a context handle exists.
- `Features/Cups/ChaosCupLifecycle.cs:159` already demonstrates the correct narrow pattern (exact `no such table` match).

## Requirements

1. Introduce one corruption-specific exception type (feature-agnostic, so it belongs in `Shared/`), thrown by handlers/persistence wherever the current code throws `InvalidOperationException` for sporting-state corruption or invariant failure. Do not use it for argument validation.
2. Map it to 500 with a clear message in the shared endpoint catch chain; keep `ArgumentException`->400, feature `ConflictException`->409, `SaveNotFoundException`->404 unchanged. Audit all ~120 endpoints' catch maps once.
3. `GetSeasonStatus`: only the genuine legacy-backfill condition may return legacy defaults. Narrow the catch to the exact table-missing SQLite condition (as `ChaosCupLifecycle.cs:159` does) and let everything else propagate as corruption.
4. `StartNextSeason`: pass corruption exceptions through instead of converting them to the 409 not-yet-complete signal; convert only the genuine not-complete signal.
5. Replace message-sniffing with typed exceptions: a typed "predates Chaos" exception for the legacy-save paths, and an exact `no such table` match for the activation backfill, so a missing-column defect on a migrated save fails loudly.
6. Add warning logs to the bare catches in `CompleteStageHandler` and `DriveCallbackHandler` (keep their post-commit-only semantics).
7. Fix the three diagnostics handlers to `EnsureMigratedAsync` before opening the context.
8. Update the frontend `ApiError`/`apiErrorMessage` handling so a 500 renders an actionable error rather than being dropped.

## Architectural direction

- Vertical slices stay; the exception type is a genuinely global shared concept per AGENTS.md section 5. No MediatR, no new frameworks.
- No sporting outcomes, RNG sequences, persisted payloads, or schema changes. Existing saves must keep working identically on the happy path.

## Acceptance criteria

- [ ] An injected corrupt save (missing RNG row / corrupt stage) surfaces as 500 with the corruption message through the real HTTP pipeline, not 400/409.
- [ ] A legacy pre-Chaos save still returns legacy status defaults (regression test through the real path).
- [ ] A missing-column schema defect on a migrated save propagates loudly instead of being swallowed by the activation backfill.
- [ ] Diagnostics handlers open contexts only after migration; tests cover the ordering.
- [ ] Frontend shows an actionable error for 500 responses.

## Verification

Standard AGENTS.md sequence: locked restore, Release build, full test suite, `dotnet format --verify-no-changes`, and the web `typecheck`/`build`/`test` scripts. Add focused HTTP contract tests for each acceptance criterion through the real pipeline (WebApplicationFactory), plus handler tests for the narrowed catches. Run the Diagnostics tests alone from a fresh process.

## Out of scope

- Fixing the corruption causes themselves, UI redesigns beyond the 500 error state, save/schema migration changes, and any change to sporting results or RNG.

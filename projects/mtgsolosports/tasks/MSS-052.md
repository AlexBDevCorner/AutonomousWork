# MSS-052 — Add athlete search with historical and performance filters

## Goal

Add a dedicated **athlete search/browse experience** that makes it easy to find athletes across the full MtgSoloSports roster using text search, useful sporting filters, and sorting.

A key requirement is the ability to filter athletes by the **number of seasons they have spent outside the pool** so experienced league athletes can be found independently of their current status.

The result should work both for quickly finding a known athlete and for exploratory queries such as:
- athletes with at least 5 non-pool seasons;
- athletes currently in Superleague;
- experienced Faeries with honours.

## Context

- Project: `mtgsolosports`; target repository: `AlexBDevCorner/MtgSoloSports`; default branch: `main`.
- Athlete profiles already expose historical sporting information such as league history and competition achievements.
- As the athlete catalogue and season history grow, discovery should not depend on manually browsing competition tables.
- Historical filters must come from authoritative persisted history rather than the athlete's current state.
- Follow `AGENTS.md`, `docs/game-rules.md`, the existing vertical-slice architecture, and current frontend conventions.

## Requirements

1. Add a dedicated athlete search/browse page reachable through the normal application navigation.

2. Provide free-text search by athlete name.
   - Case-insensitive.
   - Partial-name matching.
   - Must compose with all other filters.

3. Add **non-pool seasons** as a prominent first-class filter.
   - Support at least a minimum value, e.g. `Non-pool seasons >= 5`.
   - Prefer min/max range filtering if it fits the existing controls.
   - Count each historical season at most once per athlete.
   - A season counts when the athlete actually participated in the league system outside the pool during that season.
   - Do not derive the value from current league/status.
   - Returning to the pool later must not erase previously counted non-pool seasons.

4. Add useful additional filters supported reliably by the existing data model. At minimum:
   - **Current league / pool status** — specific league(s) and pool.
   - **Colour / league colour classification** using the existing project colour model.
   - **Creature type** where type data is available.
   - **Honours** — athletes with honours and preferably a minimum honours count.
   - **Wins/titles** — allow athletes with at least one competition win/title to be distinguished from athletes whose honours are only second/third places.
   - **Highest league reached** or an equivalent historical league-level filter.

5. Where the existing history model makes them straightforward and unambiguous, also include useful filters such as:
   - total non-pool/league seasons range;
   - seasons spent in a selected league;
   - best league finishing position;
   - Cup participation;
   - Cup podium/title presence.

   Prefer fewer trustworthy filters over speculative derived metrics.

6. Filters must compose using **AND semantics** across categories. For example:
   - current league = Superleague;
   - non-pool seasons >= 3;
   - honours >= 1;
   should return athletes satisfying all selected criteria.

7. Multi-value filters within one category should use intuitive **OR semantics** where appropriate.

8. Add useful sorting. At minimum:
   - athlete name;
   - non-pool seasons;
   - honours count.

   Also support current/highest league, titles, or best league finish where readily available.

9. Each result should show enough information to understand the match without opening the profile. At minimum:
   - athlete/card identity and image where available;
   - current league or pool status;
   - non-pool season count;
   - honours count.

   Additional compact metadata such as creature type, colour, highest league reached, or titles may be shown when useful.

10. Athlete results must link to the existing athlete profile route and preserve existing multi-tab/navigation behavior.

11. Include an obvious **clear/reset filters** action.

12. Keep filter/search/sort state stable while navigating where practical.
   - Prefer URL query parameters if that matches the application's routing conventions.
   - Reloading or copying a search URL should reproduce the same search where practical.

13. Handle empty states clearly:
   - no athletes exist;
   - no athletes match the current filters;
   - text search has no matches.

14. Keep search responsive with the full imported catalogue and accumulated history.
   - Do not load all detailed athlete histories into the browser just to calculate filters.
   - Historical aggregation/filtering should happen in the backend/query layer.

15. Do not change league assignment, pool rules, promotion/relegation, scoring, honours calculation, Cup rules, or simulation outcomes.

## Non-pool season definition

For this feature, **non-pool seasons** is a historical participation metric:

- Count distinct seasons in which the athlete participated as a league athlete outside the pool.
- A season contributes either `0` or `1`, regardless of how many stages/rounds the athlete played.
- League movement within the same season must not double-count that season.
- Returning to the pool later must not remove previously counted seasons.
- The count must be reproducible from persisted historical participation/results.

If the domain already has a precise authoritative concept for "athlete was active in a league during season", reuse it instead of introducing a competing definition.

## UX direction

Use a dedicated athlete catalogue/search layout rather than hiding the controls inside an unrelated competition table.

A practical layout is:
- search field;
- compact filter bar or sidebar;
- active-filter chips/summary;
- result count;
- sort control;
- responsive athlete result grid/list.

The **non-pool seasons** control should be easy to find and not hidden behind an advanced-options flow.

On wide screens, a persistent filter sidebar is acceptable. On narrow screens, filters can collapse into a drawer/panel as long as all functionality remains available.

## Architectural direction

- Implement this as an athlete-search vertical slice.
- Reuse authoritative athlete/history data and existing domain concepts.
- Compute historical aggregates such as non-pool season count in the backend/query layer.
- Avoid N+1 history queries per athlete.
- Prefer a query/projection that applies filters before materializing results.
- Expose a search-result DTO tailored to this page rather than full athlete aggregates.
- Keep filter semantics explicit and testable.
- If pagination is needed, apply filters/sort first and keep search state in the request/URL.

## Acceptance criteria

- [ ] Athlete name search is case-insensitive and supports partial matches.
- [ ] Athletes can be filtered by a minimum number of non-pool seasons.
- [ ] Non-pool season count is based on distinct historical seasons spent participating outside the pool.
- [ ] A season is not double-counted because of multiple stages or league changes in the same season.
- [ ] Historical non-pool seasons remain counted after an athlete returns to the pool.
- [ ] Current league/pool can be filtered.
- [ ] Colour/classification can be filtered.
- [ ] Creature type can be filtered where data exists.
- [ ] Athletes can be filtered by honours.

- [ ] Highest league reached or an equivalent historical league-level filter is available when supported by the current model.
- [ ] Filters compose correctly with text search.
- [ ] Results can be sorted by at least name, non-pool seasons, and honours.
- [ ] Each result shows current league/pool status, non-pool season count, and honours count.
- [ ] Search results link to the existing athlete profile.
- [ ] Filters can be reset easily.
- [ ] Empty/no-match states are clear.
- [ ] Search/filtering performs acceptably against the full catalogue and historical data.

## Verification

1. Run the standard backend build/test checks documented in `AGENTS.md`.
2. Run the frontend checks documented by the repository.
3. Find a known athlete by partial name and mixed case.
4. Filter for `non-pool seasons >= N` and verify athletes below the threshold are excluded.
5. Verify several stages in one season increment the non-pool count only once.
6. Verify a league change within one season still counts that season once.
7. Verify an athlete later returned to the pool retains earlier non-pool seasons.
8. Combine current league, non-pool seasons, and honours and verify AND semantics.
9. Verify multiple selected colours/types use the intended within-filter OR semantics.
10. Sort the same result set by name, non-pool seasons, and honours.
11. Open an athlete from the results and verify navigation works correctly.
12. Verify an impossible filter combination shows a clear no-results state.
13. Check the page at wide desktop and narrow responsive widths.

## Out of scope

- Changing athlete import/catalog rules.
- Changing pool eligibility or league assignment rules.
- Changing promotion/relegation or rebalancing logic.
- Changing how honours, podiums, titles, or scores are awarded.
- Building a general-purpose analytics/reporting system unrelated to athlete discovery.

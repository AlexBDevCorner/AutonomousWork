# MSS-148 - Close the WAL pairing window on save replacement and fix pragma intent

## Goal

Restore/import-overwrite must never pair a freshly moved main database with the previous file's stale WAL, and the connection pragmas actually applied must match the documented intent.

## Context

- A repository review (2026-11-19) verified the following; re-verify on the live checkout.
- `src/MtgSoloSports/Persistence/Saves/SaveStore.cs:2083-2084` performs `File.Move(overwrite:true)` and only afterwards `DeleteCompanionFiles`. Gateless readers (`ReadDetailAsync`, `SaveStore.cs:1765-1776`, reached via `Features/Saves/OpenSave/OpenSaveHandler.cs:22`) can open the new main database next to the old file's stale `-wal`/`-shm` in that window. SQLite with a foreign WAL is documented undefined behavior; every other replacement ordering in the file is careful, so this is the one remaining tear.
- `SaveStore.cs:452` sets `synchronous=NORMAL` once at creation, but it is a per-connection pragma and the per-connection interceptor (`Persistence/Saves/SaveSqliteConnectionInterceptor.cs:33,40`) only sets `foreign_keys` and `busy_timeout`, so every later connection silently runs WAL with the default FULL.
- The codebase already proves WAL-correctness discipline elsewhere (`VACUUM INTO` snapshots with SHA256 sidecars, checkpoint-before-copy in tests); this task extends that discipline to the replacement path.

## Requirements

1. Reorder restore/import overwrite so stale companion files cannot outlive the replaced main file: delete/relocate the live WAL/SHM companions immediately before the move (the replaced file is being discarded anyway), or gate read-context opens on the existing mutation/migration gate. Add a code comment stating the ordering invariant.
2. Make the synchronous-mode intent real: either apply `synchronous` in the per-connection interceptor alongside the other pragmas (preferred, one place) or delete the stale one-time setting and document that WAL+FULL is the deliberate choice. No behavior change beyond the documented pragma.
3. Regression test: restore-overwrite a save that has committed-but-uncheckpointed WAL data, with a reader observing during the window; assert the reader never sees a foreign-WAL pairing and the restored content is the intended checkpoint.
4. Document the file-replacement ordering (mutate -> migrate -> snapshot gates plus companion handling) where the existing save-store documentation lives.

## Architectural direction

- Change stays inside `Persistence/Saves` plus, if the gate option is chosen, the read-path entry points already using `EnsureMigratedAsync`. No schema changes, no sporting outcomes, no RNG involvement. Follow the existing VACUUM/checkpoint test patterns in `SharedSaveTemplates`/`TestSaveStores`.

## Acceptance criteria

- [ ] The ordering invariant is stated in code and enforced; no code path moves a main database in while its old companions can remain.
- [ ] The regression test fails on the pre-change ordering and passes after.
- [ ] The applied connection pragmas match the documented intent for every save connection (assert in a connection-level test).
- [ ] Existing restore/import/checkpoint tests all pass unchanged.

## Verification

Standard AGENTS.md backend sequence: locked restore, Release build, full test suite, `dotnet format --verify-no-changes`. Run the save-store focused test classes alone from a fresh process; include the WAL regression test in that run.

## Out of scope

- Checkpoint format changes, export/import manifest changes, catalog persistence (MSS-147), and any sporting behavior.

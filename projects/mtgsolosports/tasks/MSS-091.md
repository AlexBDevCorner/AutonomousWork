# MSS-091 — Publish and incrementally refresh the full historical report library in Google Drive

## Goal

Expand Drive publishing beyond the current season dossier/almanac to the user's organized historical library: prior season dossiers, Color/Type Cup editions, and Color/Type team histories. Provide a safe **Sync all changed reports** command, and (when auto mode is enabled) publish the Cup/team reports that actually change after relevant competition transitions without re-uploading the whole archive after every stage.

## Context

- Project `mtgsolosports`, target `AlexBDevCorner/MtgSoloSports` (`main`).
- Depends on MSS-089 (manual Drive connection/one-click publisher) and MSS-090 (opt-in stage-based publishing and durable checkpoint/status). Reuse all identity, auth, idempotency, metadata, and failure contracts.
- Existing Drive hierarchy (names only; never hard-code remote IDs or overwrite without adoption):
  `MtgSoloSports/mtshistory/Seasons`;
  `MtgSoloSports/mtshistory/Color Cup/Cups`;
  `MtgSoloSports/mtshistory/Color Cup/Teams Histories`;
  `MtgSoloSports/mtshistory/Type Cup/Cups`;
  `MtgSoloSports/mtshistory/Type Cup/Teams Histories`;
  root `universe-almanac-newtest.md`.
- The user already uploaded many existing .md exports by hand, including season 1–17 and many Type Cup team histories, and wants them updated without repetitive downloads. A manually uploaded duplicate named `(1)` exists for at least one Type Cup team: publishing must surface ambiguity, not increase it.
- Current `Features/Reports` implementations include `CupEditionReport`, `CupTeamReport`, `SeasonDossier`, `UniverseAlmanac`, with correct format/versioning. Use the same generated Markdown as user-facing downloads.

## Requirements

1. Extend Drive publishing settings with a clear folder mapping from supported report semantic types to **existing** child folders under selected `mtshistory`. Let user confirm/adopt existing target folders and files, including legacy or custom names; do not silently create duplicate parallel folder trees.
2. Provide a manual **Sync all changed reports** action with preview/counts, progress and per-category result. Inventory: all existing season dossiers; each available Color Cup/Type Cup edition; each existing Color/Type team history; almanac. Exclude arbitrary Athlete/Standings/League profile reports until explicitly configured later.
3. For each report, use stable semantic identity (save ID, report type, season number or team key) and verified destination file ID. Create only when missing; update the same file ID when changed; skip unchanged. No deletion, rename or overwriting of unknown files. Ambiguous duplicate names (e.g. `(1)`) must be surfaced for explicit resolution rather than guessed.
4. Compute a meaningful content/data fingerprint so volatile generated timestamps alone do not force updates. Use efficient per-type change detection and avoid expensive regeneration of the entire historical library each stage. Show number of created/updated/unchanged/failed files, and allow retrying failures.
5. When optional automatic mode from MSS-090 is enabled, refresh the almanac and current season as already specified, **plus** selectively publish changed Cup edition/team histories after the relevant Cup finalization, selection or other committed event that changes a report. Do not upload every historical Cup/team file on ordinary league stages.
6. Preserve all established reporting distinctions: historical source seasons, phase/status, Type Cup qualifications versus Final and wildcards, Color Cup individual/team, historic rosters/selection snapshots, names and fixed-point scoring values. Do not resimulate sport or create made-up results.
7. Explicitly show published freshness per category and last checkpoint, with safe access errors and paused sync when credentials/destination unavailable. Support resumable continuation after interruption without re-uploading successful files.
8. Keep network work outside sporting transactions and bounded: configurable batch/parallelism appropriate to Google quota, retry-safe upload semantics, cancellation and no memory explosion on large universes. Respect cross-save isolation, no hard-coded public folder IDs, and no secret leakage.
9. Add tests for category routing, two or more Cup source seasons, changed vs unchanged contents, unexpected preexisting file, duplicate name, partial failure/retry, old saves with missing Cups, and relevant event-triggered updates.

## Architectural direction

- Build a small report inventory/dispatch over existing report handlers and the publisher's mapping API. Reuse single-file update implementation from MSS-089.
- Prefer explicit report kinds over a generic query language or filesystem mirroring; these are known, authoritative Markdown exports.
- Treat first adoption of manually uploaded files as an explicit one-time operation. No blind overwrite of conflicting manually edited files.

## Acceptance criteria

- [ ] Full manual synchronization covers seasons, Color/Type Cup editions, Color/Type team histories and almanac into the user-selected folder tree.
- [ ] It reuses explicitly adopted pre-existing files, preserving their Drive URLs/IDs and custom names where configured, without duplicates.
- [ ] Repeat sync with unchanged simulation history writes nothing unnecessary.
- [ ] Relevant Cup changes refresh only affected report categories when auto mode is on, while ordinary stage updates do not re-upload hundreds of team histories.
- [ ] User can diagnose and retry partial failures without losing successful progress.
- [ ] Tests and docs cover folder mapping, old data, duplicate protection, correct historical reports and security boundaries.

## Verification

Run repository-required .NET/React quality gates. In mocked Drive folder tree seed seasons 1–17, Color/Type Cup editions and team histories including a duplicated filename; verify dry-run, explicit adoption, changed vs unchanged sync, multi-season catch-up, one relevant Cup event update and repeated sync idempotence. Check documented manual procedure with user-provided Drive folder mapping, but do not require real Google credentials in CI.

## Out of scope

- One report per athlete, arbitrary SQL, new report types, LLM writing, native Google Docs conversion, unrestricted two-way sync, deleting unknown Drive files, changing game logic, or uploading Drive content into ChatGPT on behalf of the user.

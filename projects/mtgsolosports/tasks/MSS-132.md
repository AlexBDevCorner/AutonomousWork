# MSS-132 - Activate Chaos-aware Cup selection in existing saves from a future season

## Goal

Make existing saves adopt the approved 35/30/20/5/10 selection formula for future Color Cup and Type Cup editions automatically at a persisted season boundary, while preserving current-season selections, historical editions and unrelated sporting rules.

## Context

- Project `mtgsolosports`; target repository `AlexBDevCorner/MtgSoloSports`, branch `main`. Follow target `AGENTS.md`, deterministic integer math and direct vertical slices.
- MSS-105 implemented five-component selection: effective bonus 35%, tier-adjusted completed-season league performance 30%, recent league form 20%, Chaos form 5%, career prestige 10%. Older save snapshots retain 350/300/250/0/100 permille; updating application defaults does not update them.
- Both `SelectColorCupTeamsHandler` and `SelectTypeCupTeamsHandler` load the saved rules snapshot. `StartNextSeasonHandler` does not migrate selection weights. `SaveStore.EnsureMigratedAsync` deliberately checks that schema migration does not change the rules snapshot.
- Chaos gameplay has separate save-scoped activation in `ChaosCupLifecycle`, first eligible source season and format version. Therefore an old save can run Chaos in future seasons while continuing to give its result zero direct selection weight indefinitely.
- Observed on 2026-11-04: the running `NewTest` save was Season 18, Stage 15. Its persisted Season 17 Color Cup selection report showed bonus 350, performance 300, form 250, Chaos 0, prestige 100. This proves the historical edition's formula, not that every later edition or arbitrary save uses the same weights. Reproduce with a legacy snapshot fixture; never edit or simulate the user's live save.
- The requested fix authorizes a named, versioned, forward-only game-rule activation for these outer selection weights. It does not authorize replacing an entire old rules snapshot with today's defaults.
- The two-phase individual Color Cup work, MSS-119 through MSS-121, changes tournament gameplay and is independent of this task.

## Requirements

1. Automatically schedule the approved formula for existing saves that still use the recognized legacy 350/300/250/0/100 weights. Persist the selection-formula version and effective source season once. For an initialized legacy save first upgraded during source season N, use the first newly started season, no earlier than N+1 and no earlier than that save's Chaos activation season. A pending successor already persisted by movement but not started is still N+1. A fresh save using current weights remains current from its first eligible edition. Define and test an uninitialized-save boundary as well.
2. Preserve the currently started source season's selection behavior even if its Cup selection has not happened yet. Apply the new formula to both alternating Cup types from the effective source season onward. Example: upgrading a legacy save during Season 18 keeps Season 18 Type Cup on its old formula; new Season 19 Color Cup and Season 20 Type Cup use 350/300/200/50/100, provided Chaos eligibility permits those seasons.
3. Treat this as explicit game-rule versioning separate from database-schema migration. Keep the original snapshot and unrelated league, bonus, prestige, tournament and RNG settings intact, or preserve equivalent immutable historical rule versions if the existing design requires it. Do not reinterpret historical rounds through current defaults. Retain schema migration's snapshot-preservation guarantee.
4. Select the effective formula by the Cup's source season, not today's current season, UI state or a newly changed global default. Persist or resolve enough edition-specific metadata that selected, partially played and completed Cups retain their original ratings, roster, reports, results and replay. Older reports without new metadata, including fallback reports reconstructed from persisted selections, must still show their original weights and weighted contributions.
5. Use the existing MSS-105 Chaos form calculation and normalization unchanged. A valid legacy source season without a Chaos edition keeps its defined zero raw component. For a newly eligible source season, normal lifecycle checks must require the completed Chaos result before selection. Do not silently replace a missing required result with zero, grant Pool athletes new selection rights, or change color-local versus global normalization.
6. Make activation and selection safe under retries, concurrent first access, restart and every supported entry point, including direct selection endpoints, Next Event and fast-forward/bulk season flows. Establishing activation consumes no sporting RNG, never moves the effective season on retry and never duplicates selections. Persist the activation atomically; unsupported or corrupt state fails without partial sporting changes.
7. Keep the activation decision and edition formula through normal save export/import, checkpoints and restore. Opening or reading historical data must not advance the activation boundary or relabel prior reports.
8. Show the active or scheduled formula and its effective source season through the existing save/Cup selection UI and appropriate read models. An old historical report must visibly retain 35/30/25/10; a new affected edition must show all five components as 35/30/20/5/10. Remove any hard-coded lifecycle/UI text that advertises new weights for a legacy edition. Keep UI work limited to explaining this activation.
9. Document the upgrade boundary and compatibility behavior in `docs/game-rules.md` and the relevant technical documentation. Include a player-facing example for a save upgraded during an even season.

## Architectural direction

- Reuse `ChaosCupLifecycle`'s persisted activation pattern where useful, but keep tournament activation and selection-formula activation independently identifiable. An already existing Chaos activation must not prevent this later selection upgrade.
- Prefer a small save-specific selection policy/effective-season record and shared formula resolution used by both Cup selectors and their report/read paths. Do not redesign the global rules hierarchy or add a generic migration framework.
- Inspect `Persistence/Saves/Rules*SnapshotDocument.cs`, `SaveStore`, `Features/Cups/SelectColorCupTeams`, `SelectTypeCupTeams`, historical selection/report handlers, `SeasonLifecycleEvaluator`, and existing selection tests before choosing the narrowest change.
- Only the five outer weights change at activation. Keep current sporting input calculations, tie-break order, career-prestige model and candidate eligibility.
- Keep pure selection math in `SimulationKernel`; save/version resolution and persistence stay outside it. Preserve save locking and transaction patterns.
- Reuse the cheapest relevant `SharedSaveTemplates` fixture for incidental history. Do not add repeated full-season simulations to prove a local formula or metadata change.

## Acceptance criteria

- [ ] A legacy initialized save schedules a stable future effective source season without manual database edits, a new universe or a separate user confirmation flow.
- [ ] Current-season and historical Cup behavior stays legacy; the first applicable future Color and Type selections use exactly 350/300/200/50/100 and their source season's completed Chaos outcome.
- [ ] A save where Chaos is already enabled but outer weights remain legacy also upgrades successfully.
- [ ] New saves remain on current weights; repeated opening, concurrency, restart and a pending successor do not postpone or duplicate activation.
- [ ] Completed and partially played legacy Cups retain their selection, report, result, replay and RNG data; old stored and fallback reports keep accurate original weights.
- [ ] Activation consumes no RNG and changes no unrelated rules or league/bonus state. Schema migrations still preserve the original rules snapshot.
- [ ] Manual, direct and bulk execution resolve the same effective formula; export/import and checkpoint restore retain the boundary.
- [ ] UI/API/report evidence makes the old-versus-new formula and effective season inspectable; deterministic focused regression tests and repository checks pass.

## Out of scope

- Replaying historical sport, replacing prior selections, rerolling RNG or touching the user's live save.
- Changing Chaos gameplay/eligibility, promotion rules, bonus aging/earning, tier factors, prestige weights, nationality or candidate-pool rights.
- Replacing whole snapshots with current defaults, silently changing unsupported custom rules, a general-purpose rules editor or a broad migration framework.
- Unrelated frontend redesign, new infrastructure/dependencies, or changing other AutonomousWork task statuses/priorities.

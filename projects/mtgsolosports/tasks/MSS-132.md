# MSS-132 — Reproducible subscription-model benchmark for the MtgSoloSports columnist

## Goal

Provide a lightweight, repeatable way for the owner to compare GPT-6 Luna, GPT-6.1 Terra, and GPT-6.1 Sol as MtgSoloSports sports journalists **using ChatGPT/Codex/Work subscription access rather than API billing**. Measure factual accuracy, interesting story selection, and useful writing quality on the same fixed sports data. This task prepares the benchmark; selecting a model remains the owner's decision.

## Context

- Control project: `mtgsolosports`; target repository: `AlexBDevCorner/MtgSoloSports` (local, single-user app).
- There is an existing Google Drive archive `MtgSoloSports/mtshistory` with per-season Markdown dossiers, a `universe-almanac-newtest.md`, and Standings / Color Cup / Type Cup reports.
- At the inspected 2026-10-29 snapshot, season 17 is provisional after 3 of 32 stages; season 16 is final. Data becomes stale as simulation advances, so keep a fixed benchmark snapshot and distinguish it from live reporting.
- Key source rules: official season points differ from weighted career points; Type Cup qualification never awards a title; individual and team Color Cups are separate; provisional standings must never be presented as final.
- In December 2026 ChatGPT and Codex subscription allowances are planned to converge. Efficient model selection matters, but API token prices are not a proxy for included subscription usage.
- The owner wants smaller, self-contained PRs. No model calls or subscription authentication should be required for implementing the benchmark package.

## Requirements

1. Add one focused Markdown benchmark guide under an appropriate `docs/` path. It must explain how the owner can manually run each prompt in a **fresh session** with the same frozen input files using available subscription model selectors in ChatGPT Work or Codex. Do not assume that all models are selectable in ordinary Chat.
2. Define three comparable Russian-language journalism test cases: (a) concise three-stage S17 Superleague recap, (b) historical context and title-defense narrative using S16/S17 and the almanac, and (c) Cup-specific commentary that tests qualification vs final and individual vs team title distinctions. Each case must state exactly which existing report types are required and what to do if data is unavailable.
3. Include reusable Russian-language columnist prompts that ask for engaging, selective reporting rather than a pasted leaderboard, insist on only sourced facts, cite source file/section, and say when evidence is missing. Never fabricate sports results, historical firsts, or completed titles.
4. Provide a clearly scoped scoring rubric: factual accuracy (including **critical-error disqualifiers**), quality of story selection, historical comparisons, prose/readability, and handling of source freshness. Keep an owner-fillable results table for Luna / Terra / Sol without fabricating evaluation outcomes.
5. Explain how to note subscription usage objectively (model, effort, input size, approximate elapsed time and observed usage-dashboard changes if exposed). Do not use API $/token pricing as the measurement; do not promise a fixed messages-per-hour quota.
6. Keep it small and documentation-oriented; if a minimal reproducible fixture is needed, prefer bounded excerpts of existing MtgSoloSports-generated test/example data rather than adding complete season dumps or private Drive exports to the repository.

## Architectural direction

- Reuse existing journalist/report/export terminology from the repository. The benchmark guide is not a new runtime feature.
- Treat all Drive source files as owner-controlled and potentially stale. The worker must not require Google Drive access, credentials, API keys, or direct subscription-model invocation. Source links may serve as optional owner reference; the guide must remain usable with locally exported Markdown files.
- If tests need an expected-facts checklist, use only facts verifiable in the provided fixed snapshots and label them with source/season/stage; otherwise prescribe the extraction procedure without inventing results.

## Acceptance criteria

- [ ] One concise benchmark guide exists in the target repo with three fully specified article prompts and identical source-selection rules across models.
- [ ] The rubric makes fabricated titles, false first-ever claims, wrong point systems, and provisional-as-final claims critical errors.
- [ ] A model-comparison table is present and unfilled; no invented measurements or model rankings.
- [ ] A human with Plus subscription and frozen exported Markdown can run the tests without an API key or modifying MtgSoloSports.
- [ ] No application code, simulation rules, season history, Drive sync, or automatic journalism generation changes are included.

## Verification

1. Review the Markdown benchmark guide for the exact three scenarios, source requirements, prompts, scoring rubric, and empty results table.
2. Check all claims against its named historical snapshot or leave them as verification instructions; confirm no unverified sports facts are treated as known.
3. Confirm the process works with subscription UI/CLI model selection and makes no API-key assumption.
4. Confirm the PR changes only the small documentation package.

## Out of scope

- No changes to how competitions work, rankings, titles, archives, exports, or sync.
- No new AI integrations or automated article publishing.
- No paid model calls, API benchmarking, authentication setup, or programmatic use of subscription entitlements.
- No automatic selection or activation of a model.
- No copying full private Drive archives into GitHub.

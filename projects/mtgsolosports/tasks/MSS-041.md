# MSS-041 — Dedicated league tables with a stage-by-stage placement matrix for bonus calibration

## Goal

Make league standings a first-class, independently explorable browser page available **throughout the season**, not something users must find after a completed stage in Live or navigate deep into History. Offer multiple useful table views, including a 32-athlete × up-to-32-stage matrix showing **each creature's finishing position in every completed stage**. The presentation should make it easy to recognize whether early stage winners disproportionately dominate later standings and to decide whether the current bonus/points system deserves a separate rules-calibration task.

## Context

- Project: `mtgsolosports`; target `AlexBDevCorner/MtgSoloSports`; default branch `main`.
- The current `App.tsx` shell has Saves/Dashboard/Live/History/Records/Cups but **no dedicated Standings navigation**. `LivePage.tsx` fetches `/api/saves/{saveId}/leagues/{leagueId}/standings/current` and displays the current table alongside Live controls. `HistoryPage.tsx` offers historical stage standings and season tables, but its navigation is buried within a page for several unrelated functions. Standings are difficult to inspect independently during normal progression.
- Existing read endpoints/models: `features/athletes/athleteApi.ts` (`CurrentStandings` and `CurrentStandingRow`); `features/history/historyApi.ts` (`fetchHistorySeasons`, `fetchHistoryCompetitions`, `fetchHistoryStages`, `fetchHistoryStageStandings`, `fetchHistorySeasonTable`). Existing `features/standings/zones.ts` provides presentation-only league zones. Reuse these concepts rather than implementing an inconsistent second scoring system.
- `docs/game-rules.md`: each league has 32 athletes and 32 stages of 16 rounds. Every completed stage produces a rank and **championship points** using the standard 32-position table; stage finishing rank also earns bonus, which is not active until the **next stage**. Effective bonus changes future round point value, never the random base finishing order. It is therefore essential to distinguish season championship points, stage positions, earned bonus and active bonus instead of conflating them.
- MSS-040 supplies real save-scoped routes and native profile links. **This task depends on MSS-040** so its dedicated standings route and profile links conform to the new navigation model. Follow `AGENTS.md` and `docs/technical-design.md` (vertical slices, direct Endpoint -> Handler, **no MediatR**).

## Requirements

1. Add **Standings / League tables** as a prominent first-class entry in the main navigation for an open save and link to it contextually from Live and Dashboard (and History where appropriate). The page must be reachable at any point in an active season, including before the first stage finishes; opening it does **not** require completing the currently running stage. Use a distinct bookmarkable save-scoped route, e.g. `/saves/:saveId/leagues/:leagueId/standings?season=N&view=season`. Selecting a league, season and view should be reflected in the URL and survive refresh, Back/Forward and opening in a new tab. Include the Superleague once it exists.
2. Implement at least **two clearly labeled switchable table views**:
   - **Season table (default):** familiar ordered league standings showing current rank, creature/link to its profile, total championship points, completed stage count, stage wins, and other existing useful totals (e.g. round wins and total stage points). Reuse existing zone/champion/qualifier/relegation indicators in the appropriate league/season context. The latest available current standings must be visible during a running season; completed historical seasons show their persisted final table.
   - **Stage placements / form matrix:** one row per league athlete, with the current season's standing (or a clearly defined ranking for a completed season) and one numbered column per stage 1–32. Each populated cell shows that creature's **actual finishing place in that completed stage** (P1, P2, ... P32), not its position in the running season table. Missing/uncompleted stages remain visibly absent, never fabricated or shown as zeroes. Make P1 wins and podiums easy to scan; give stage-column headers clear labels, stage-result details on hover/focus or drill-down, and athlete names as true profile links.
3. Make the matrix specifically useful for **bonus calibration**. Keep season rank, cumulative championship points and stage-win count visible beside the historical places so the user can compare the winner of one stage with its later placements and season rank. Expose earned stage bonus where it is already persisted (e.g. contextual cell details or an optional supplementary bonus display) and distinguish it from any current effective bonus shown. If showing current effective bonus is feasible from an efficient aggregate, label it accurately as time-dependent, not as the bonus used retroactively in all earlier stages. Never imply that a win itself changes shuffle probability. Add a compact explanatory legend for placements, championship points and next-stage bonus activation.
4. Offer straightforward exploration controls: league selector (all eight feeder colors and Superleague when applicable), season selector (current and historical when available), and view switcher. Sorting by current/final season rank must work; allow an easy comparison by stage-win count or championship points if feasible without sacrificing stable row-to-stage alignment. Show completion/progress and when a table was last updated by persisted stage data, not misleading in-progress stage results.
5. Make a **dense 32-stage table practical** on a wide monitor: readable desktop spacing, clear color/contrast for winners/podiums, sticky/frozen identity and headline total columns and a horizontally scrollable stage region; avoid forcing athlete names or current ranks out of view when scrolling to Stage 32. Responsive narrow-screen behavior may simplify the presentation or offer a compact stage-window selector, but must not hide the feature, produce page-wide horizontal overflow or make profile links inaccessible. Maintain the existing dark sports-database look and accessible non-color-only placement cues.
6. Build the matrix from **persisted authoritative stage standings/history**. Audit what the existing API and storage already expose; prefer efficient server aggregation if necessary to avoid 32 sequential requests, N+1 athlete queries or decompression of every historical round for normal page views. Keep the frontend presentation focused in its own feature folder; reuse pure helpers for standings and formatting when genuinely shared. Old completed stages must never change merely because new stages or bonuses become active.
7. Handle initial season before any stage completes; an incomplete current stage; completed and historical seasons; athlete membership/movement between different seasons/leagues; unavailable/deleted saves; rapid selector changes and loading/errors. The grid must align athlete identity to **the selected season and league**, not accidentally mix the same row with a different season's roster. Do not show future-stage placements, and do not silently substitute another league on an invalid direct URL.
8. Preserve existing Live table, reveal flow and History replay functionality. Consolidate reusable presentation/query logic when it reduces duplication, without moving the Live board below the fold or changing sporting calculations.

## Architectural direction

- Build a dedicated `features/standings` page and, only where needed, a matching narrowly scoped backend `Features/Leagues` or `Features/History` **read-only vertical slice** that returns compact stage-placement aggregates for the selected season/competition. Existing `StageStanding`/season-standing projections are authoritative. Reuse existing endpoint(s) if already performant and complete.
- Prefer one compact season/league query for the matrix or bounded parallel reads with explicit cancellation; do not fetch each athlete separately or recompute standings using frontend sporting math.
- For the matrix, show stages 1–32 in chronological order by default even if rows can be sorted by season rank/wins. Stage places are immutable history. Keep the season table and matrix visibly distinguished and share the same selected competition context.
- MSS-040's real routing and native links are required; use its established conventions rather than reintroducing button-only profile navigation.

## Acceptance criteria

- [ ] A dedicated, prominent **Standings** navigation entry opens the selected save's league tables directly before, during or after a stage; Live and Dashboard offer contextual entry points.
- [ ] The **Season table** displays authentic live cumulative championship standings after completed stages and final/historical standings for a completed season. Clear empty/progress states are present before the first completed stage.
- [ ] The **Stage placements** view shows up to 32 numbered stage columns and correctly displays each of 32 athletes' actual saved P1–P32 placements for all and only completed stages. Compare a handful of cells against History's persisted stage standings to prove exact alignment.
- [ ] A creature winning one or several stages is immediately identifiable from P1 cells and stage-win count; its resulting season rank/points stay in view for comparison, and bonus-related labels correctly distinguish earned bonus and next-stage activation.
- [ ] Wide desktop tables keep creature identities and key ranking columns in view when examining late stages; a narrow-screen layout remains usable and accessible, with no uncontrolled overflow.
- [ ] League/season/view changes update a shareable URL; opening a matrix and two creature profiles in separate tabs works and does not corrupt each tab's chosen save/context.
- [ ] Superleague, feeder leagues, season transitions and changed membership show correct season-specific rosters and zones; incomplete future stages are blank/not yet completed, not falsely ranked.
- [ ] Existing Live, History and simulation flows remain intact and no scoring, multiplier, deterministic RNG or persisted round/season data is altered.
- [ ] Add focused tests for stage-to-athlete matrix alignment, incomplete stages, historical season switching, sorting and (where added) aggregate endpoint correctness. Include screenshots of the season table, a populated wide matrix with multiple completed stages, the matrix scrolled toward Stage 32, and one narrow layout. Full repository verification succeeds.

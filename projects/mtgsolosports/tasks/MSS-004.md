# MSS-004 — Add per-save SQLite persistence and save management foundation

## Goal

Create durable independent universes with rules/RNG state that can be safely mutated transactionally.

## Context

- Project: `mtgsolosports`.
- Target repository: `AlexBDevCorner/MtgSoloSports`.
- Default branch: `main`.
- Product rules: `docs/game-rules.md` in the target repository.
- Technical constraints: `docs/technical-design.md` and `AGENTS.md`.
- Architecture is vertical-slice modular monolith. **MediatR is forbidden.**
- Keep sporting simulation deterministic and use fixed-point integer arithmetic.

## Requirements

1. Add EF Core SQLite using Central Package Management.
2. Implement one SQLite database file per save plus a small application-level save index if needed for discovery.
3. Persist `SaveMetadata`, schema version, current season/phase, immutable Rules v1 snapshot and versioned RNG state.
4. Add create/list/open/delete-save vertical slices and Minimal API endpoints; deletion must be explicit and must not silently remove arbitrary files.
5. Ensure database write operations can commit RNG state atomically with future simulation mutations.
6. Enable appropriate SQLite local concurrency/WAL behavior where justified.
7. Add migrations and deterministic integration tests using temporary directories/databases.
8. Do not put all saves into one shared sporting-history database.

## Architectural direction

- Feature slices may use the DbContext directly; do not add generic repository/UnitOfWork abstractions.
- Persistence types may live under `Persistence`, but application use-case code stays with its vertical slice.

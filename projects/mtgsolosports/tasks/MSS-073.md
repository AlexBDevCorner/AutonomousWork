# MSS-073 — Give Dashboard and Athlete panels consistent heights and responsive widths

## Goal

Replace content-driven card sizing with a clean, predictable panel layout on the Dashboard and Athlete profile. Panels in the same layout should have consistent, bounded heights instead of growing or stretching to match long content; content that exceeds a panel's space should scroll **inside** that panel. Give table-heavy panels such as Athlete **History** and **Cups** approximately double the width of normal panels so their data is readable without horizontal scrolling at common desktop sizes.

## Context

- Project: `mtgsolosports`; target repository: `AlexBDevCorner/MtgSoloSports`, branch `main`.
- User-reported on 2026-10-11 with Dashboard and Athlete screenshots.
- Dashboard has panels for standings/leaders, feeder leagues, season progress across all leagues, Cup context, records, Hall of Fame, and stories. One panel may list 25 leagues or more (Superleague plus multiple feeder tiers). Its long content makes the surrounding grid look very uneven, with large empty areas and unrelated cards starting much farther down the page than expected.
- Athlete profile has a large card/identity header followed by Career, Bonus, Identity, Honours, Movements, Selections, Records, History, Cups and Stories panels. Their varied content lengths produce inconsistent heights and ragged rows. History and Cups contain many columns and currently show **horizontal scrollbars** that hide important values (finishes, stages, event details).
- The visual problem is layout, not the underlying information. Preserve all existing data, navigation and controls, including the completion status and historical results.
- MSS-072 separately addresses human-readable labels and capitalization. Keep this task focused on card/grid sizing and content overflow; do not duplicate that task.

## Requirements

1. **Implement a consistent panel/grid sizing system across Dashboard and Athlete.**
   - Use a clear, reusable panel layout pattern (and shared styling/components where appropriate), rather than independent natural heights for every card.
   - Give normal content panels a common bounded height at typical desktop sizes. Grid rows must not grow to the height of the longest card, and adjacent panels must not be stretched into mostly empty boxes.
   - Arrange cards in a compact, aligned grid that uses available screen width and flows naturally into subsequent rows. Eliminate the large vertical gaps seen on the Dashboard.
   - Do not confuse card height with the amount of data: a long table or story list must not make an entire grid row taller.

2. **Scroll long content vertically inside each panel.**
   - Keep each panel's heading, summary/title and applicable actions accessible while its body scrolls independently as needed.
   - Use `overflow-y: auto` or equivalent, with bounded flex/grid children (`min-height: 0` where needed), so a panel doesn't expand because of long lists, tables or text.
   - Avoid nested vertical scroll areas within one panel and avoid double scrollbars caused by competing wrappers.
   - Preserve access to the last row, links and controls; no silent clipping/truncation of data.
   - Ensure scrollbars and focus states are usable in dark theme, including mouse wheel, keyboard and touch/pointer input. Avoid scroll trapping.

3. **Allocate more width to genuinely wide panels.**
   - On desktop, make Athlete **History** and **Cups** each span roughly **two normal panel columns** (including grid gaps) so these tables can expose meaningful columns without horizontal scrolling.
   - Inspect other Dashboard/Athlete data-heavy panels (e.g. season-wide league progress, detailed movement/history tables) and use a double-span layout only where justified by content. Normal panels should keep their normal width.
   - Prefer sensible column width distribution, smaller secondary metadata, wrapping and responsive cell layout over `overflow-x: auto` for History/Cups. Finishes, league names, Cup event/round, team and other existing values must remain visible and readable.
   - Do not solve the issue by cutting off text, hiding important columns, or making everything tiny. Preserve existing interactive links and badges.

4. **Handle viewport changes gracefully.**
   - At wide desktop widths, support regular and double-width cards within an aligned responsive CSS grid. Avoid broken gaps/orphaned narrow columns from wide cards.
   - At laptop/tablet sizes, reduce the number of columns intelligently; wide panels should take the available width rather than forcing page-level horizontal overflow.
   - At narrow/mobile sizes, use one-column/full-width panels and adapt dense tables appropriately (e.g. stacked row details or selective wrapping). Horizontal scrolling is a last-resort fallback only where all data truly cannot fit, not the default at common desktop resolutions.
   - Prevent page-wide horizontal scrolling, overlapping panels, overflowing headings/badges, and obscured controls.

5. **Keep the Athlete identity/header area proportionate.**
   - The athlete image and summary above the card grid must not leave a huge empty block across a wide viewport merely because the container fills the page. Make the summary compact and aligned while keeping image, metadata and navigation visible.
   - It may remain a distinct responsive header rather than an ordinary fixed-height data panel; the fixed-height rule primarily applies to the content-card grid.

6. **Apply the treatment consistently without changing features.**
   - Audit all Dashboard and Athlete panels, including empty, short, very long and historically populated states; do not fix only History and Cups.
   - Preserve the currently shown data, card links, records, progress, tooltips, action buttons, navigation and event semantics.
   - Prefer reusable styling tokens/grid span classes and minimal component adjustments. Do not add arbitrary hardcoded widths to individual tables that defeat the responsive layout.

## Architectural direction

- Inspect existing React/TypeScript Dashboard and Athlete page components and their CSS/layout patterns before changing them. Follow project styling conventions.
- Prefer CSS grid with stable bounded row sizing and explicit span utilities (e.g. normal=1, wide=2), and a panel shell with an always-visible header plus one vertically scrollable body. Use responsive breakpoints and `min-width: 0` / `min-height: 0` on the appropriate grid/flex children.
- The chosen panel height should be a deliberate, reusable sizing value; maintain a consistent visual rhythm rather than optimizing each panel separately.
- Where a table is too dense, improve its layout intentionally rather than hiding mandatory information or moving all overflow into a horizontal scroll area.
- Keep changes frontend-only, and do not change any API or persisted domain model. Coordinate with MSS-072 by avoiding unrelated copy changes.

## Acceptance criteria

- [ ] On Dashboard, long season/league lists stay within their own fixed-height pane with internal vertical scrolling; adjacent panes align and no large empty gaps are created by the long list.
- [ ] All normal Dashboard panels use the consistent height and grid rules, including short-content panels and Stories/Records/Hall of Fame when present.
- [ ] Athlete Career, Bonus, Identity, Honours, Movements, Selections, Records, History, Cups and Stories panels follow the same consistent sizing/scrolling system without content-dependent row expansion.
- [ ] Athlete History and Cups are about twice the width of normal desktop panels, and their currently truncated/offscreen columns can be read without a horizontal scrollbar at typical desktop widths (test at least ~1440px and ~1920px).
- [ ] No data is lost or visually clipped: every row remains reachable, and links/buttons inside scrollable panel bodies work.
- [ ] Panel titles and actions remain accessible while body content scrolls.
- [ ] The athlete image/identity header is compact and does not have the excessive empty full-width area shown in the report.
- [ ] The layout works with sparse and dense saves (one feeder tier and three feeder tiers, multiple seasons, long stories/records) and remains usable on laptop/tablet/mobile widths.
- [ ] No unintended page-level horizontal scrolling, double vertical scrollbars in a single panel, text collisions or unwanted overlap.
- [ ] Existing functionality and automated frontend checks remain green.

## Verification

1. Run the frontend and inspect the Dashboard using a three-feeder-tier completed season with 25 leagues and 32/32 stages. Confirm the long league progress pane scrolls independently without pushing other cards down or inflating the whole row.
2. Open an Athlete profile with multiple seasons, league movements, honours, records, Cup selections and at least four Cup history entries. Compare the grid and the History/Cups tables before and after the change.
3. Confirm desktop behavior near 1440px and 1920px: one normal panel width versus two-column span, no horizontal scrollbar on History/Cups, and bounded equal-height cards.
4. Verify a narrower laptop/tablet width and a mobile viewport: panels reflow without body-level horizontal scrolling or clipped links/values.
5. Test both short/empty and long-content cards; scroll to the last row of each long panel, activate links/actions and navigate back.
6. Confirm header controls, scroll/focus behaviors, and dark-theme scrollbar/focus visibility with keyboard and pointer interactions.
7. Add/update focused layout/component tests for panel shell, span classes and representative wide/overflow content; use actual rendered behavior or browser-level checks where practical, not solely brittle source-string assertions.
8. Run `npm run test --prefix src/MtgSoloSports.Web`, `npm run typecheck --prefix src/MtgSoloSports.Web`, and `npm run build --prefix src/MtgSoloSports.Web`. Include before/after screenshots of both pages and the responsive layout in the PR.

## Out of scope

- Changes to sporting calculations, league/Cup simulation, results, save format or APIs.
- The technical label/capitalization cleanup tracked separately in MSS-072.
- A full visual theme, typography, color scheme or navigation redesign.
- Reducing, omitting or replacing existing dashboard/profile data merely to force cards to fit.
- Redesigning unrelated pages beyond minimal shared-component changes needed to avoid regressions.

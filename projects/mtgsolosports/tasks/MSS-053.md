# MSS-053 — Integrate promotion/relegation and feeder rebalance reveals into the postseason flow

## Goal

Fix the recently added **promotion/relegation** and **feeder rebalance** visuals so they are part of the actual postseason experience instead of existing only as historical/read-only widgets on the Standings page.

When the player manually resolves either lifecycle step from the Dashboard, the backend result should be persisted exactly once and the player should then be taken into a dedicated reveal presentation of that result before continuing to the next postseason step.

The current behaviour — clicking **Resolve promotion & relegation** or **Rebalance feeder leagues**, immediately persisting the result, refreshing the Dashboard, and silently advancing to the next step — misses the purpose of MSS-050 and MSS-051.

## Context

- Project: `mtgsolosports`; target repository: `AlexBDevCorner/MtgSoloSports`; default branch: `main`.
- MSS-050 added `MovementReveal` and mounted promotion/relegation history on Standings.
- MSS-051 added the feeder rebalance reveal and likewise exposed it as a Standings/history presentation.
- Both visual components already consume persisted authoritative sporting results. Do **not** replace that with frontend simulation.
- The Dashboard lifecycle currently executes `advance-next-event`, refreshes status, and changes the next action immediately.
- Promotion/relegation currently has no Live/reveal event integration in `eventModel.ts` / `SeasonFlow.tsx`.
- `MovementReveal` currently initializes with all movements already revealed and only becomes progressive after pressing **Replay the reveal**. That is appropriate for a historical view, but not for the first-time lifecycle presentation.
- The same integration problem should be assumed for feeder rebalancing and verified explicitly.
- Follow `AGENTS.md`, `docs/game-rules.md`, the existing vertical-slice architecture, and current frontend routing/reveal conventions.

## Intended player flow

### Promotion & relegation

Manual postseason progression should behave approximately as:

1. Dashboard shows **Resolve promotion & relegation**.
2. Player activates the step.
3. Backend resolves and persists authoritative movement exactly once.
4. UI opens a dedicated promotion/relegation reveal experience using that persisted result.
5. Reveal starts unrevealed/progressive on this first presentation.
6. Player can reveal movements deliberately, reveal a boundary, reveal all, or skip to the final state.
7. When complete, a clear **Continue** action returns to the postseason flow.
8. The Dashboard now shows the qualifier as the next step.

### Feeder rebalance

Likewise:

1. Dashboard shows **Rebalance feeder leagues**.
2. Backend persists the authoritative rebalance once.
3. UI opens the feeder-rebalance reveal.
4. The actual persisted departures, returns, pool displacements, and pool draws are revealed progressively.
5. Player can finish/skip the presentation and continue.
6. The Dashboard then exposes the Cup-selection step.

The reveal is presentation over already-persisted sporting state. It must never rerun or duplicate the sporting action.

## Requirements

1. Integrate both transition visuals into the **manual postseason lifecycle flow**:
   - promotion & relegation;
   - feeder-league rebalance.

2. Clicking the corresponding Dashboard lifecycle action must no longer feel like an invisible backend operation followed by an immediate jump to the next step.
   - Persist the backend result once.
   - Then navigate/render the reveal for the result that was just persisted.

3. Use an existing Live/reveal route/pattern where practical.
   - It is acceptable to add dedicated transition event keys/routes if that keeps the model clean.
   - From the player's perspective these should behave like real postseason presentation events, not like hidden Standings widgets.

4. The first presentation immediately after resolving a step must begin in **progressive reveal mode**, not fully revealed.
   - Promotion/relegation must not initialize at `revealedCount = total` in this first-time presentation.
   - Feeder rebalance must follow the same principle.
   - Keep deliberate controls such as reveal next / reveal group or boundary / reveal all.

5. Historical/revisit behaviour must remain convenient.
   - Opening an already completed historical transition from Standings may show the final state immediately.
   - A **Replay reveal** action should remain available.
   - First-time lifecycle presentation and historical viewing may use different initial reveal modes explicitly rather than relying on accidental component state.

6. Add an explicit **Continue** / **Back to postseason** action after the reveal has completed or been skipped.
   - It should return to the appropriate current save Dashboard/flow.
   - The next legal backend action should already be visible there.

7. Do not execute the next lifecycle step automatically merely because the reveal completes.
   - Example: finishing promotion/relegation reveal must not automatically run the qualifier.
   - Example: finishing rebalance reveal must not automatically select Cup squads.

8. Preserve the existing backend sporting boundaries:
   - `ResolveAutomaticMovement` / inaugural movement continues to own promotion/relegation decisions.
   - `RebalanceFeeders` continues to own rebalance decisions and RNG/pool draws.
   - Frontend reveal code only reads persisted outcomes.

9. Ensure refresh/reload is safe after the sporting action has already been persisted.
   - Reloading the reveal must not execute the lifecycle action again.
   - The result must be reconstructed from persisted data.
   - Browser back/forward navigation must not duplicate movement or rebalance rows.

10. Promotion/relegation reveal must still display the MSS-050 information:
    - athlete;
    - promoted/relegated status;
    - source league;
    - destination league;
    - boundary grouping;
    - final stable summary.

11. Feeder-rebalance reveal must still display the MSS-051 information:
    - departures to Superleague;
    - returns from Superleague;
    - feeder-to-pool displacement;
    - pool-to-feeder draws;
    - roster-count progression;
    - final per-league summary.

12. Keep Standings as a useful historical inspection surface if desired, but it must no longer be the **only** place where these reveals exist.
    - Do not remove historical access unless replaced by an equally clear route.

13. Make the Dashboard copy/actions reflect the presentation behaviour.
    - Avoid a button label that implies only a silent backend mutation if it will open a reveal.
    - Reuse the application's existing "Play on Live", "Announce on Live", or similar interaction language where it fits.

14. Verify the Season 1 inaugural Superleague transition.
    - If MSS-050's reveal supports it, integrate it consistently into the first-time flow as well.
    - Do not regress the special Season 1 transition.

15. Fast-forward behaviour may remain non-interactive if that is the established meaning of fast-forward.
    - A user intentionally fast-forwarding a season/postseason does not need to be forced through each reveal.
    - The normal manual lifecycle controls are the focus of this task.
    - Historical results must still be available afterwards.

16. Respect reduced-motion settings exactly as the existing reveal implementations do.

17. Do not change scoring, qualification, movement, rebalancing, RNG, Cup selection, or league assignment rules.

## Architectural direction

- Reuse the existing persisted result APIs and MSS-050/MSS-051 reveal components rather than reimplementing the visuals.
- Introduce an explicit distinction such as `initialMode: 'reveal' | 'complete'` (or equivalent) so a component can start progressive for a freshly completed lifecycle event and start complete for historical viewing.
- Extend the event/routing model cleanly if transition reveals need event keys. Do not pretend promotion/rebalance are round-based competitions if that creates awkward semantics; a small transition-reveal abstraction is preferable.
- The backend mutation and frontend presentation should be separable:
  1. run mutation once;
  2. receive enough identity (source season / next season / action) to address the persisted result;
  3. navigate to its reveal;
  4. re-read persisted result on the reveal page.
- Do not hold important result data only in transient React state returned by the mutation request; reload must remain correct.
- Keep historical correctness based on persisted movements/rebalance facts, not current athlete membership.
- Avoid adding new persistence solely for "has watched animation" unless there is already an established gameplay requirement for such state. Presentation completion can remain UI-local.

- [ ] Completing or skipping the promotion/relegation reveal exposes a clear Continue action back to the postseason flow.
- [ ] Returning to the Dashboard after that reveal shows the qualifier (or correct next legal action) without rerunning movement.
- [ ] Clicking **Rebalance feeder leagues** manually persists the result and immediately opens the feeder-rebalance reveal instead of silently advancing.
- [ ] The first rebalance presentation starts progressively and reveals the actual persisted athlete movements/pool draws.
- [ ] Completing or skipping the rebalance reveal returns to the Dashboard where Cup selection is the next legal action.
- [ ] Neither reveal automatically executes the following sporting step.
- [ ] Reloading either reveal after the backend result has been persisted does not duplicate or rerun the sporting mutation.
- [ ] Browser back/forward navigation does not create duplicate movement/rebalance records.
- [ ] Historical Standings/revisit views still show the completed final state and can replay the reveal.
- [ ] Season 1 inaugural Superleague formation has consistent reveal integration where applicable.
- [ ] Fast-forward remains usable without forcing interactive reveal steps.
- [ ] Reduced-motion mode preserves the same information and progression.
- [ ] Existing promotion/relegation and rebalance sporting results remain byte-for-byte/semantically unchanged by the presentation work.
- [ ] Frontend tests cover first-time reveal mode versus historical completed mode for both transitions.
- [ ] Integration tests cover "execute once → navigate to reveal → reload → continue" for both lifecycle actions.

4. Reveal several athletes, refresh the browser, and verify no sporting action is executed again and the same authoritative movements are shown.
5. Finish/skip the reveal and return to Dashboard; verify the qualifier is now next.
6. Run the qualifier, then manually click **Rebalance feeder leagues**.
7. Verify the rebalance result is persisted once and the UI opens its progressive reveal immediately.

9. Finish/skip the rebalance reveal and verify Cup selection is now next.
10. Reopen both completed events from historical/Standings access and verify they open in a convenient completed state with a Replay option.
11. Verify Season 1 inaugural transition behaviour.

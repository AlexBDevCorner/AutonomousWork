# MSS-072 — Clean up technical labels and capitalization across the UI

## Goal

Make all user-facing text in MtgSoloSports read like polished game UI rather than exposing backend enum names, concatenated identifiers, or inconsistent capitalization. Audit **the whole frontend**, not only the reported screens, and correct the findings consistently. This is a focused copy/presentation cleanup, not a redesign of layouts or sporting behavior.

## Context

- Project: `mtgsolosports`; target repository: `AlexBDevCorner/MtgSoloSports`, branch `main`.
- User-reported examples (2026-10-11):
  - Dashboard shows season phase **`CupComplete`**. It should show **"Cup Complete"**.
  - Athlete page > **Honours** shows raw identifier-like honours: `FeederRunnerUp`, `ColorCupIndividualRunnerUp`, `SuperleagueTitle` instead of readable names (e.g. **"Feeder runner-up"**, **"Color Cup individual runner-up"**, **"Superleague title"**).
  - Athlete page > **Records** mixes capitalization within otherwise similar labels/values.
  - Athlete page > **Selections** shows **`ColorCup`** and **`TypeCup`** as single words. They should be **"Color Cup"** and **"Type Cup"**.
- These examples are symptoms, not an exhaustive issue list. Similar strings may appear in Dashboard, athlete profiles, Cups, standings, history, Live/replays, league pages, selection/reveal flows, search/results, tooltips, tables and empty/error states.
- The application has domain enums/status codes and persisted data that must stay stable; only their **presentation** should change. Review `AGENTS.md`, existing frontend conventions and any existing label/display helpers before introducing a new abstraction.

## Requirements

1. **Audit visible copy across the application.**
   - Inspect every primary navigable page and important secondary panels/modals, including Dashboard, athlete profile tabs/panels (Honours, Records, Selections), Cups, Live, Standings, History, competitions/leagues, search and selection/reveal/results views.
   - Look for raw PascalCase/camelCase enum names, concatenated event/competition names, internal phase/action/status values, underscores/hyphens used as code delimiters, enum-like honours/record labels, and inconsistent capitalization or pluralization.
   - Include conditional states and data loaded from historical saves, not only a happy-path new universe. Review both formatted values and static UI text. Fix genuine player-facing inconsistencies; do not blindly title-case all strings.
   - Record the affected surfaces and representative before/after examples in the PR so the wider audit is demonstrable.

2. **Use intentional, user-friendly display names.**
   - Dashboard: `CupComplete` -> **Cup Complete**, and audit **all** season/stage/phase values, not just this one.
   - Athlete Honours: `FeederRunnerUp` -> **Feeder runner-up**, `ColorCupIndividualRunnerUp` -> **Color Cup individual runner-up**, `SuperleagueTitle` -> **Superleague title**; inspect and cover all other honour kinds shown by the application.
   - Athlete Selections: `ColorCup` -> **Color Cup**, `TypeCup` -> **Type Cup**, including selections, reports and historical editions where relevant.
   - Athlete Records: align capitalization, wording, terminology and punctuation across labels and values; pay special attention to mixed case within the same pane.
   - Use natural sports terminology (e.g. "runner-up" instead of "RunnerUp"), preserving proper names such as "Color Cup", "Type Cup" and "Superleague". Make sure labels remain meaningful when viewed without technical context.

3. **Establish a consistent copy style.**
   - Named competitions/entities use their established names (e.g. "Color Cup", "Type Cup", "Superleague").
   - Page/panel headings, badges, state labels and actions should follow one deliberate casing convention per UI context; descriptive prose, table values and record/honour descriptions should read naturally. Avoid arbitrary capitalization changes just because a source enum is PascalCase.
   - Standardize related terms across pages: the same competition, season phase, honour or record must not have multiple spellings/capitalizations depending on which component renders it.
   - Keep text concise and easy to scan; fix obvious awkward grammar/spaces only when within this audit's scope. Do not add lengthy explanatory UI copy.

4. **Centralize domain-to-display-name presentation where it helps.**
   - Look for existing formatters/mappings first; reuse or consolidate rather than introducing duplicate ad hoc replacements on each page.
   - Prefer explicit, typed, exhaustively tested mappings for known domain values, especially phases, cups, honours and record types. A generic regex splitter may be a fallback for genuinely unknown diagnostic values, **not** the main business-labeling strategy: it cannot infer acronym, proper-name, hyphenation or meaningful sports wording.
   - Add coverage or a sensible development-time signal for newly introduced enum values so technical names do not silently leak into the UI.
   - Apply formatting at the presentation boundary. Do not modify serialized enum values, API contracts, persisted event/record keys, identifiers, filtering/sorting logic, or routing; ensure mappings are presentation-only.
   - Preserve sport-specific distinctions such as individual versus team honours, league tiers and different Cup events.

5. **Make the audit visible and testable.**
   - Add frontend unit/component tests for representative labels and every enumerated member of the primary phase/competition/honour display mappings.
   - Check historic and in-progress data rendering, including already-persisted selections, honours and records. Where feasible, test at least one integration-level view/panel per affected category so a correct standalone formatter is not rendered incorrectly by a page.
   - Avoid fragile tests that only assert implementation text without rendering or calling actual display logic.

## Architectural direction

- Treat this as a user-interface concern in the React/TypeScript frontend; backend and persistence should remain untouched unless a demonstrable display-specific data gap requires a very small, compatible extension.
- Reuse existing components and styling patterns. Centralize common semantics but avoid one over-generalized formatter for unrelated domain objects.
- Keep presentation mappings separate from the values used for API calls, comparisons, status progression, links and save-state serialization. A human-readable label must never be sent back as a domain identifier.
- Be careful with user/card-supplied proper names: do not rewrite actual MTG card/athlete names or other free-form content.
- Preserve working navigation, tables, responsive layouts and historical replay.

## Acceptance criteria

- [ ] Dashboard shows **Cup Complete** instead of `CupComplete`; every other exposed phase/status label on Dashboard is reviewed and displayed in readable English.
- [ ] Athlete Honours displays readable honour names for all supported honour types; the reported `FeederRunnerUp`, `ColorCupIndividualRunnerUp` and `SuperleagueTitle` cases are corrected.
- [ ] Athlete Selections displays **Color Cup** and **Type Cup** rather than `ColorCup` and `TypeCup` everywhere relevant.
- [ ] Athlete Records labels and values use consistent, natural capitalization and terminology, with no arbitrary mix of upper/lowercase within similar entries.
- [ ] All major frontend pages and secondary displays are audited for the same class of issue; discovered raw technical identifiers and inconsistent human-readable terminology are fixed, with representative before/after findings documented in the PR.
- [ ] One domain concept receives the same human-readable name wherever shown (including current and historical data); proper nouns and real athlete/card names remain intact.
- [ ] Known labels have centralized/reused typed mappings or equivalent shared presentation helpers where practical; future enum additions cannot silently show raw identifiers in the primary mapped categories.
- [ ] Existing save data, APIs, routes, sorting/filtering, simulation results and season progression are unchanged.
- [ ] Automated display-formatting and relevant page/panel tests pass, along with the normal frontend checks.

## Verification

1. Inventory the user-visible domain/status/honour/record/cup labels and their rendering sites. Capture a concise audit checklist with before/after examples in the PR.
2. Start the app and visually inspect Dashboard in a **CupComplete** save, Athlete > Honours (including runner-up and Superleague title), Athlete > Records and Athlete > Selections (Color Cup and Type Cup).
3. Inspect the other main page routes and commonly reached panels, including completed historical events, pending events, tables, tooltip/badge values and empty states; verify consistent casing and no visible enum names.
4. Run mapping-specific frontend tests, component/page tests for representative records/honours/selections and any affected existing UI tests.
5. Run `npm run test --prefix src/MtgSoloSports.Web`, `npm run typecheck --prefix src/MtgSoloSports.Web`, and `npm run build --prefix src/MtgSoloSports.Web`.
6. Verify that displaying a mapped phase/honour/Cup does not change API parameters, status transitions, route links, existing-save rendering or sporting results.

## Out of scope

- Redesigning page structure, theme, typography system, spacing, navigation or introducing new animations.
- Changing game rules, scoring, honours awarded, Cup/season lifecycles or persisted history.
- Renaming enum members in APIs, database schema or serialization formats for cosmetic reasons.
- Rewriting actual MTG card/athlete names or user-entered data.
- Introducing a full localization/i18n framework or translating the UI into another language.
- Unrelated bug fixes or broad React/backend refactors.

# MSS-046 — Improve table alignment consistency across the MtgSoloSports UI

## Goal

Make tables across MtgSoloSports visually consistent and easier to scan by ensuring each column's header and values use coherent alignment and spacing. Fix the currently obvious cases in Cup history and Cup team-selection explanations, and audit the rest of the UI for the same class of alignment problem so the fix is systematic rather than page-specific.

## Context

- Project: `mtgsolosports`; target repository: `AlexBDevCorner/MtgSoloSports`; default branch: `main`.
- Several tables are currently visually awkward because headers are aligned differently from the values beneath them, or neighboring columns use inconsistent alignment/padding without a semantic reason.
- Known examples include:
  - historical tables for Cups;
  - the Cup teams page/table explaining why athletes were picked;
  - potentially other standings, history, results, league, postseason, or athlete-related tables.
- The problem is presentation only. Existing values, sorting, ranking, scoring, navigation, and game rules should remain unchanged.
- Follow the current frontend architecture and styling conventions. Prefer reusable/shared styling when the same table behavior exists in multiple places rather than adding one-off fixes to every page.

## Requirements

1. Audit user-facing tables in the React frontend for inconsistent column alignment, especially cases where a column header is aligned differently from the cells in that same column. At minimum inspect Cup history and the Cup team-selection/"why athletes were picked" views.
2. For every affected table, make header alignment match the semantic alignment of its column values. Use a consistent convention across the application, for example:
   - descriptive/text columns aligned consistently;
   - numeric/rank/score/points/stat columns aligned consistently;
   - compact icon/status/action columns aligned consistently.
   The exact convention may follow existing good tables in the application, but a header must not appear offset from the values it labels without a deliberate reason.
3. Normalize horizontal padding and column spacing where inconsistent spacing is part of the visual problem. Avoid headers that look detached from their values, columns that appear accidentally shifted, or cell content that changes alignment between rows.
4. Reuse or introduce small shared table/header/cell styling helpers where this removes duplicated alignment rules. Do not introduce a large new table framework or redesign all table components solely for this task.
5. Preserve intentionally different layouts where they communicate meaning. Do not blindly center every column. Alignment should be based on the content type and readability.
6. Keep responsive behavior usable on narrower screens. The alignment cleanup must not cause important text to be clipped, overlap, or make existing horizontal scrolling materially worse.
7. Preserve all existing table content and behavior: data, ordering, sorting (where present), links, row interactions, highlights, medals/status indicators, filtering, and navigation must continue to work unchanged.
8. Check dynamically sized competition tables, including Type Cup fields larger than the normal league size, so the visual fix does not assume a fixed number of rows or teams.
9. If multiple existing table implementations use near-identical CSS with slightly different alignment rules, consolidate only the alignment-related pieces that can be shared safely; avoid unrelated frontend refactoring.

## Architectural direction

- Start by identifying existing table components/styles used by Cup history, Cup team selection, standings, season history, league tables, and postseason result views.
- Prefer semantic CSS classes or small reusable primitives for common alignment modes (for example text, numeric, centered/status) instead of repeated ad-hoc `text-align` declarations.
- Keep the implementation local to presentation concerns. Do not move sporting calculations or derive display values differently just to simplify rendering.
- When a table intentionally mixes alignment modes, make the header and body cells for each individual column share the same rule.
- Use existing design tokens/spacing conventions where available rather than introducing a visually separate table design.

## Acceptance criteria

- [ ] Cup historical tables have headers visually aligned with the values in their respective columns.
- [ ] The Cup team-selection/"why athletes were picked" table has coherent header/value alignment and spacing.
- [ ] Other user-facing tables with the same obvious mismatch are identified and corrected as part of the task.
- [ ] Text, numeric/statistical, and compact status/action columns follow a consistent visual convention across corrected tables.
- [ ] No corrected column has a header visibly aligned one way while its values are aligned another way unless that difference is explicitly intentional and justified in the PR.
- [ ] Existing values, rankings, links, sorting/interaction behavior, highlights, and competition results are unchanged.
- [ ] Tables remain usable at existing desktop and narrow responsive widths, including long athlete/team names and dynamically sized Type Cup fields.
- [ ] The implementation avoids unnecessary one-off CSS duplication when a small shared alignment rule can cover multiple tables.

## Verification

Run the frontend checks documented by the repository, including at least:

```bash
npm ci --prefix src/MtgSoloSports.Web
npm run test --prefix src/MtgSoloSports.Web
npm run typecheck --prefix src/MtgSoloSports.Web
npm run build --prefix src/MtgSoloSports.Web
```

Manually inspect representative pages at normal desktop width and a narrower viewport:

1. Cup history tables.
2. Cup team-selection/"why athletes were picked" table.
3. At least one league/standings table.
4. At least one season/history/results table.
5. A Type Cup/team-event table with a larger field if a suitable save/test fixture is available.

Confirm headers and values line up consistently, long names remain readable, and no functional table behavior changed.

## Out of scope

- No redesign of the overall visual theme, typography, colors, cards, sidebars, or page layouts.
- No changes to competition rules, scoring, simulation, rankings, persistence, or API contracts.
- No replacement of the existing table system with a third-party grid/data-table library.
- No unrelated frontend refactoring beyond small reusable alignment/spacing cleanup needed to make the tables consistent.

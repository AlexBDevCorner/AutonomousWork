# MSS-034 — One-click Scryfall catalog import and clear onboarding UX

## Goal

A new user starting MtgSoloSports locally should be able to populate the shared creature catalog from the Saves screen without downloading a bulk JSON file, using an HTTP client, or knowing that `POST /api/catalog/import` exists. Explain where the card data comes from and make the import state and quota requirements understandable.

## Context

- Project: `mtgsolosports`; target: `AlexBDevCorner/MtgSoloSports`, default branch `main`.
- Follow `AGENTS.md`, `docs/game-rules.md`, and `docs/technical-design.md`. Architecture is a vertical-slice modular monolith using direct `Endpoint -> Handler`; **no MediatR**. Preserve deterministic simulation and fixed-point sporting arithmetic.
- The existing `POST /api/catalog/import` consumes a caller-supplied **JSON array in the request body**. It does not fetch cards from the internet.
- Relevant code: `src/MtgSoloSports/Features/Catalog/ImportCatalog/`, `Persistence/Catalog/CatalogStore.cs`, `src/MtgSoloSports.Web/src/features/catalog/`, `src/MtgSoloSports.Web/src/features/saves/SavesPage.tsx`, and `src/MtgSoloSports.Web/src/App.tsx`.
- The existing catalog parser filters eligible creature cards, excludes tokens, collapses printings by name, classifies eight sporting colors and records display metadata including card image URLs. Each color must have at least 256 unique athletes before a save can be created. Existing saves carry their own athlete snapshots and must not be changed by a later catalog refresh.

## Requirements

1. Add a prominent **Import cards from Scryfall** button in the empty/incomplete-catalog experience on the Saves screen (or its existing catalog banner). A first-time user should discover the action next to the explanation of why save creation is disabled, without leaving the app.
2. Clicking the button invokes a new server-side import-from-Scryfall use case. The backend obtains the current official Scryfall bulk-data **metadata** at runtime (e.g. `https://api.scryfall.com/bulk-data`), chooses and documents the appropriate card dataset (prefer the current `default_cards` offering if it preserves the fields and artwork required by our existing parser), downloads the advertised bulk file and imports it into the shared catalog. Do not hardcode timestamped download URLs, depend on browser-to-Scryfall CORS, scrape pages, or issue individual card lookups.
3. Check Scryfall's **actual current bulk-data format** and metadata fields before implementation. Support the advertised compression/format as needed (including newline-delimited JSON if that's the current offering); adapt the ingestion path without regressing the existing JSON-array API. Prefer streaming/bounded-memory download/parsing rather than buffering a large dataset into a string or loading it all in the browser.
4. Reuse the existing eligibility, duplicate-collapse, sporting-color classification and persistence behavior. Do not change the sporting catalog rules, eight-color quotas, or snapshot isolation of existing universes. Verify the replacement dataset and resulting athlete counts **before** replacing a healthy existing catalog; failed, corrupt, cancelled or quota-inadequate downloads must leave an existing usable catalog intact.
5. Keep the existing manual `POST /api/catalog/import` supported for advanced/offline use. The automatic backend endpoint should have clear error responses for unavailable Scryfall, timeout, malformed/unsupported data and insufficient quota. Avoid overlapping imports (disable repeat clicks in the UI and guard concurrency server-side). Respect Scryfall's published API usage/attribution guidelines and use normal HTTP timeout/cancellation practices.
6. Show **what the import does and its source** in user-friendly copy: e.g. “Cards are downloaded from Scryfall’s MTG bulk data. We keep eligible creature cards, exclude tokens and group different printings of the same card into one athlete.” Include an outbound link to the official Scryfall bulk-data/API documentation and any required source attribution. Clarify that an internet connection is needed for automatic import and that existing saves are not modified by catalog updates.
7. Give visible, accessible UI feedback while importing (working indicator and truthful stage/status text; no invented percentages). On success refresh `/api/catalog/stats` automatically and show imported unique-athlete count and the per-color `count/256` breakdown when useful, plus a clear “Ready to create a universe” outcome. If available from the official metadata, display the source dataset and its last-updated timestamp; don't fabricate freshness if unavailable.
8. If importing/refreshing an already populated catalog, explain that it replaces the **shared catalog only** and request confirmation before an intentional refresh. Existing save files stay untouched. Error states must be actionable, preserve retry, and never misleadingly claim success.
9. Update the standard local run / first-use README instructions: launch app → click import → wait for verified quota → create save; document the existing manual API as a fallback rather than the required onboarding path.

## Architectural direction

- Add a focused Catalog import-from-provider vertical slice and reuse shared catalog parser/persistence only where appropriate; keep Scryfall HTTP/network concerns outside `SimulationKernel`.
- Prefer a server-mediated one-click import over a frontend fetch or a generic provider/plugin framework.
- Use dependency-injected HTTP and mockable/fixture-driven integration boundaries for deterministic offline tests; do not make ordinary CI dependent on live Scryfall.
- Stay consistent with existing dark UI components and feature-scoped React code. A long-running import must not silently leave the interface looking stuck.

## Acceptance criteria

- [ ] With an empty catalog, a user can import cards from the UI with one explicit action and no manual API call or file download.
- [ ] The screen clearly identifies **Scryfall** as the source, links to its official documentation, describes the creature filtering/deduplication, and explains the eight `256`-athlete quotas.
- [ ] The backend discovers the live bulk file through metadata and correctly handles its documented current file format without hardcoded dated file URLs.
- [ ] The successful import refreshes catalog stats and allows save creation as soon as all eight color quotas are met.
- [ ] Import progress/working state, success, error and retry are visibly and accessibly represented; rapid repeat clicks cannot trigger overlapping imports.
- [ ] A user can see per-color shortfalls if a dataset cannot meet quota; an unsuccessful replacement does not destroy a healthy catalog.
- [ ] Refreshing a populated catalog is an explicit action with an explanation that existing universes are unchanged.
- [ ] The existing raw-JSON-array import endpoint remains functional for offline/advanced use.
- [ ] Automated offline tests cover provider metadata/file responses, current file format or representative fixtures, parser integration, bad response, cancellation/failure, concurrency, atomic rollback and UI states.
- [ ] README first-use steps describe the button-first workflow. The full repository verification succeeds.

## Out of scope

- No changes to sport rules, card classification, quotas, simulation results or existing saves.
- No automatic catalog refresh at application startup, recurring background downloads or cloud-hosted sync.
- No generic card-provider abstraction, Scryfall page scraping, or bulk individual card API calls.
- No redesign of unrelated dashboard/simulation/history screens.

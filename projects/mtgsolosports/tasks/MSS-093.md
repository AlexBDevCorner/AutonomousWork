# MSS-093 — Sync individual athlete profiles to a dedicated Google Drive archive

## Goal

Extend MtgSoloSports Google Drive publishing so the user can automatically create and maintain **one Markdown report per athlete** in a dedicated, searchable folder hierarchy, without manually downloading or uploading thousands of profiles. Support a safe initial full publish and efficient updates after simulation progress.

## Context

- Project: `mtgsolosports`; target: `AlexBDevCorner/MtgSoloSports` (`main`).
- Depends on MSS-091, which extends MSS-089/090 with an authenticated Drive publisher, destination configuration, idempotent mapping, batch synchronization and opt-in post-stage publishing. Reuse these facilities rather than writing an independent uploader. MSS-089 was in progress when this task was created.
- The user maintains `MtgSoloSports/mtshistory/` on Google Drive, with `Seasons`, `Color Cup`, `Type Cup` and a universe almanac; preserve those folders, names and contents. Add the athlete collection as another sibling under the **user-selected** `mtshistory` folder, not a hard-coded Drive ID.
- The sporting universe has 2048 athletes under the current rules. Some are active in Superleague/Feeder leagues; others are in the common pool. **Every persisted athlete** must be eligible for export regardless of current league, previous titles or active status.
- MSS-086 implemented an existing read-only `Features/Reports/AthleteReport/GetAthleteReportHandler.cs` export in Markdown/JSON: identity, career, season history, honors, movements, Cup selections/history, record holdings, fixed-point units and snapshot metadata. Reuse the existing Markdown output; do not scrape React.
- The athlete report has volatile generated metadata and some derived global record holdings; meaningful-change detection must not mistake timestamps for sporting changes, nor overlook an athlete losing a global record despite having no individual stage result.
- `SportingColor` has eight stable catalog categories: White, Blue, Black, Red, Green, Multicolor, Hybrid, Colorless. These refer to each athlete's stable printed sporting color, **not** current league membership or nationality.

## Requirements

1. Add a dedicated destination beneath the selected Drive history folder:
   ```
   mtshistory/
     Athletes/
       athletes-index.md
       White/
       Blue/
       Black/
       Red/
       Green/
       Multicolor/
       Hybrid/
       Colorless/
   ```
   Create missing child folders only with explicit existing Drive authorization, reuse verified existing folders, and never modify the user's unrelated content. Allow another user-configured athlete root name or chosen folder; do not hard-code account-specific folder IDs.
2. Put **one UTF-8 Markdown file per athlete** in the respective stable sporting-color folder, such as `athlete-123-world-breaker.md`. The athlete's persistent save-scoped integer ID is its identity; the name slug is only human-readable decoration. Store save ID + athlete ID + report type → remote Drive file ID and folder mapping. Prevent collisions for duplicate display names, slug changes and renamed athletes. Do not move files automatically when league/pool membership changes.
3. Include the full set of persisted athletes, **including pool athletes who have not yet played a season**. Avoid relying on paginated UI results or only the current league roster. Use a bounded, deterministic server-side list/inventory of athlete IDs and their stable color; include unavailable report handling without silent omission.
4. Add an obvious **Publish all athletes / Sync changed athletes** action in Reports / Drive settings. The first full publish should be resumable, operate in batches with visible progress (N/total, created/updated/unchanged/failed), cancel/retry support and safe quota/rate-limit handling. Ordinary subsequent runs should be incremental. Existing full-library sync (MSS-091) should optionally include Athletes, with a clear count/estimated workload and explicit user action for first bulk import; do not silently perform thousands of writes as a side effect of pressing the existing small `Publish now`.
5. Reuse the existing Athlete report generator (`GetAthleteReportHandler`) with the exact same selected save and serialized Markdown content as the individual download. Do not generate fresh sporting statistics from scratch, scrape HTML, or create separate report semantics. The report must remain valid for active athletes, inactive athletes, pool athletes, and historical careers. Ensure no per-athlete simulation side effect.
6. Generate `athletes-index.md` (and optionally compact JSON if useful) with all athletes, stable ID, current display name, color, current league or pool, a link/path to their report, and clear coverage/snapshot metadata; include stable deterministic ordering and size-conscious format. This index should be updated as needed and may be referenced from the Drive report library.
7. On **opt-in** automatic publication (MSS-090), enqueue changed athlete profiles when their persisted history/career state changes after a completed **global stage** or relevant Cup/selection/postseason/new-season event. At minimum capture participants whose season result or effective bonus changed, athletes with newly recorded honours/selections/movements, and any record-holding updates for other athletes. Coalesce rapid stage/bulk simulations, deduplicate IDs, and publish the latest committed snapshot rather than an intermediate stale state.
8. Given that one stage may affect hundreds of active athletes, **do not re-upload all 2048 files on every stage**. Use trustworthy change detection (known affected IDs and/or meaningful per-athlete fingerprint), plus an explicit occasional full reconciliation to detect missed changes. Exclude volatile report generation timestamps from fingerprint comparisons. An athlete in the pool with unchanged historical data should be skipped; changes to global record holdings must not be missed. Avoid N+1 expensive global maxima queries: implement a safe bulk projection or caching/preload strategy for many reports instead of calling the single-athlete handler 2048 times naively.
9. All Drive writes must occur **outside simulation transactions**, with bounded work, retry/backoff and persistent progress/checkpointing per save. Never delay, roll back or fail an already-completed stage because a file upload fails. If the application shuts down before uploading everything, resume when it runs again; it must not claim background operation while the local app is closed.
10. **Idempotency and safety:** update previously mapped Drive file IDs in place; skip unchanged semantic content; never create `(1)` duplicates on retry; detect remote changes and ambiguous matching names; avoid overwriting independently edited files without the existing publisher's conflict policy; never delete unknown user files. If athlete name changes, retain the mapping and do not create another athlete file.
11. Isolate multiple sporting saves. A mapped destination for one save cannot silently publish an unrelated save's athlete reports to the same folder; require explicit mapping/confirmation or per-save folder separation as appropriate. Maintain credentials server-side per the existing publisher and no new OAuth scopes unless genuinely needed with user consent.
12. Show useful UI status per category and overall (last successful checkpoint, pending count, failures, retry), with a way to find/open the Drive destination. Make the default scope for `Publish now` remain current dossier/almanac per MSS-089; athlete publication must be discoverable and clearly distinguished.
13. Clarify user-facing ChatGPT workflow: a Drive folder containing thousands of reports is **not equivalent to thousands of ChatGPT Project file uploads** or a guarantee that every report is automatically retrieved. The human-readable index assists explicit retrieval; do not promise automatic knowledge/project synchronization.
14. Add mocked Google API tests plus report/inventory integration tests covering all 2048 default athletes, all eight color folders, empty/pool careers, duplicate names, name changes, stable IDs across seasons, create/update/unchanged, partial failure/resume, high stage activity, bulk simulation, race/coalescing, record-holder removal, cross-save isolation and OAuth errors. No live Drive access in CI.

## Architectural direction

- Extend the existing Drive publisher's explicit report inventory and mapping logic from MSS-091. Use `Features/Athletes` existing persisted catalog and career queries, not frontend pagination.
- For bulk operation, design an efficient batched athlete-report projection or shared read-only snapshot query/reader that can reuse career/record lookup aggregates; avoid `2048 x` global record queries and thousands of SQLite contexts. Keep small, bounded memory batches; do not load all complete profile histories into a single giant object.
- Separate the deterministic report generation from Drive side effects. Use one persistent work queue/checkpoint per save/destination; no generic distributed queue infrastructure is required for a local app.
- Prefer file IDs and stable semantic identities over filenames for update mapping, and original sporting color over current league for directory placement. Folder IDs are configured/adopted per user and never baked into source.
- Avoid new mediator frameworks, new simulation rules, changes to scoring/cup calculations and arbitrary SQL endpoints.

## Acceptance criteria

- [ ] With a configured Drive connection, user can create/reuse `Athletes` with eight sporting-color subfolders and publish **one distinct Markdown report for every athlete** in the selected save, including those in the common pool.
- [ ] Athlete filenames contain stable IDs and descriptive names; each corresponding report matches the existing athlete download and correctly contains career, honours, movements and Cup history.
- [ ] `athletes-index.md` lists and links all athletes with ID/name/color and an accurate snapshot/coverage label.
- [ ] Initial publish completes in resumable chunks with progress, error counts, bounded network/DB activity and no duplicate remote files on retry.
- [ ] Re-running sync with no meaningful changes does not re-upload the athlete corpus because of generated timestamps.
- [ ] Opt-in post-stage publishing updates genuinely affected athlete profiles, coalesces high-volume events, and never uploads all unchanged pool reports on ordinary stages.
- [ ] Cup selection, movement and changed record-holder cases are updated, including athletes who did not play the latest stage.
- [ ] Separate saves are protected from accidental cross-publication. Failure, disconnection, restart and manual retries behave safely without changing game state.
- [ ] Download buttons, current dossier/almanac publication, Cup/team sync, and existing `MSS-091` behavior remain intact.

## Verification

Run the full .NET/React gates from `AGENTS.md`. Use fake Google API integration tests with a complete 2048-athlete fixture and simulated folders, then verify:
1. First bulk publish creates exactly the expected eight color folders + 2048 distinct athlete files + one index.
2. Repeated publish with unchanged save state performs no unnecessary Drive content updates.
3. A completed stage changes only a relevant subset of reports, not all pool athlete files; verify checkpoint update and exact report content.
4. A Cup result or season boundary changes affected athlete reports, including existing record-holder deltas.
5. A restarted/interrupted publisher resumes without duplicating files; name collisions, alternative slugs, Google 429s and remote conflicts stay safe.
6. All individual downloaded athlete reports and corresponding Drive files contain identical meaningful factual data for selected examples.

## Out of scope

- Replacing the existing individual Athlete Markdown export or changing its data model.
- Automatically importing all Drive documents into a ChatGPT Project, publishing Google-native Docs, AI-written athlete biographies or narratives.
- Uploading full round-level replay data, per-athlete artwork, extra JSON files by default or editing simulation outcomes.
- Changing the user's existing Seasons/Cups hierarchy or automatically deleting unknown Drive files.

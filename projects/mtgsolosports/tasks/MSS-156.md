# MSS-156 - Add an enforceable ESLint gate for the web project

## Goal

The web project gains a small, pinned ESLint setup (react-hooks + TypeScript rules) wired into the required verification commands, and every existing `eslint-disable` suppression is either justified or removed - ending the current state where 20 stale-closure suppressions exist with no linter to enforce them.

## Context

- A repository review (2026-11-19) verified the following; re-verify on the live checkout.
- `src/MtgSoloSports.Web` has no ESLint anywhere: no config file, no devDependency, no lint script. Only `tsc` and `node --test` gate correctness.
- Yet ~20 `eslint-disable-next-line react-hooks/exhaustive-deps` comments exist (e.g. `features/live/LiveEventView.tsx:381,457,524`, `features/history/HistoryPage.tsx:139-151`). These suppressions are unenforced prose: nothing checks that the disabled rule would actually fire, or that the suppression is still needed after refactors.
- The backend deliberately uses "a small curated analyzer set rather than a huge opinionated rule pack" (AGENTS.md quality gates); the frontend gate should mirror that philosophy.
- AGENTS.md frontend constraints: no Tailwind, no component/animation libraries; ESLint is a dev tool and gate, not a UI dependency, and is acceptable.

## Requirements

1. Add ESLint as a pinned devDependency with a flat config limited to: TypeScript ESLint (recommended, type-checked only where fast enough to keep CI cheap), react-hooks (exhaustive-deps and rules-of-hooks), and React 19 compat. No styling/ownership opinion packs.
2. Add a `lint` npm script and wire it into the required verification sequence: AGENTS.md build/verification list and `.github/workflows/ci.yml` (before or after typecheck, preserving failure propagation).
3. Baseline must be zero warnings: run the linter, fix every genuine finding (missing deps are real bug candidates - fix the code, preferring the shared-hook patterns from MSS-154 over new suppressions).
4. Each remaining `eslint-disable-next-line` must be either removed or paired with a one-line comment naming why it is safe (e.g. "load once on mount, keyed by save id in deps"). Grep-audit at the end: no unexplained suppressions.
5. Keep CI cost reasonable: if type-aware linting is too slow, use syntactic rules only and document the choice.
6. No product code behavior changes from rule fixes except where a rule fix corrects a real stale-closure/bug - each such correction gets its own commit and a test where practical.

## Architectural direction

- Dev tooling only; no runtime dependencies, no formatter changes (dotnet format unaffected), no design-system implications. Follow the existing npm script style in `package.json`.

## Acceptance criteria

- [ ] `npm run lint` exists, is pinned, and exits clean with zero warnings on the current tree.
- [ ] CI runs the lint step and fails the job on lint errors; the AGENTS.md verification list includes it.
- [ ] Every surviving suppression is justified with an adjacent comment; a grep audit shows none unjustified.
- [ ] Web tests, typecheck, and build all still pass after any code fixes.

## Verification

Standard AGENTS.md web sequence plus the new `npm run lint` (`npm ci`, `test`, `typecheck`, `build`, `lint`). Confirm the ci.yml job actually runs lint (inspect the workflow step list; cite completed CI evidence only if observed).

## Out of scope

- Hook consolidation (MSS-154), ReportsPage decomposition (MSS-155), backend analyzer changes, formatting changes, and any UI redesign.

# MSS-133 - Add a local read-only save snapshot helper for agent journalism

## Goal

Let a locally running journalist agent obtain and inspect a fresh, verified SQLite snapshot from the containerized game on demand, without manual downloads, Docker administration access or Google Drive.

## Context

- Project: `mtgsolosports`; target: `AlexBDevCorner/MtgSoloSports`, branch `main`.
- The user runs the game in a container and will request articles manually in chat. The intended recurring request is a review after each completed Superleague stage, covering all rounds of that stage.
- `compose.yaml` serves the app on `http://localhost:8080` and stores per-save databases in the named volume `mtgsolosports-data`, under `/data/saves`. Do not expose that volume or the Docker daemon to the journalist.
- Existing `GET /api/saves` and `GET /api/saves/{saveId}/export` support discovery and portable export. `SaveStore.ExportAsync` captures a consistent snapshot; `SaveBundle` handles `save.db`, `manifest.json`, archive bounds and checksum validation. Reuse these contracts; never copy an active database file out of the volume.
- This is the foundation for MSS-134 evidence queries and MSS-135 journalist instructions/archive. Existing Drive publishing remains optional and unchanged.

## Requirements

1. Add a small repository-owned local CLI/helper, runnable from Windows PowerShell with the game's existing development prerequisites. It must work with the default container deployment, without container shell execution, Docker socket access, host volume remapping, new listening ports or application credentials.
2. Provide a one-time configuration for the loopback app URL, explicit save ID and local working directory. Enumerate saves for setup, but never silently select the first save or infer identity only from a mutable display name. Do not embed the user's real save ID or machine paths in tracked files.
3. On explicit invocation, fetch the selected save through the existing export route. Support using an already downloaded bundle offline as well. Use bounded download/extraction, controlled staging paths and existing bundle validation, including checksum, manifest/database identity and supported schema/rules versions. Reject invalid, mismatched or unsupported data without migrating or repairing it.
4. Publish a new working snapshot only after the complete operation succeeds. A failed download or validation must not replace the previous valid snapshot or represent it as fresh. Return actionable errors for app unavailable, unknown save, bad archive and incompatible schema. Resolve relative paths consistently against documented configuration.
5. Open extracted SQLite data with an actually read-only connection. Do not call application bootstrap, import, OpenSave, EnsureMigratedAsync, schema migration, seeding, activation/backfill or simulation paths. Never alter sporting state, RNG, source bundle, manifest or the validated database during inspection.
6. Return compact machine-readable output containing snapshot location, save identity, source/export timestamp, acquisition timestamp, schema/rules versions, content fingerprint and available season/stage coverage. Keep logs separate from data output and return a nonzero exit code on failure.
7. Keep data acquisition separate from offline querying so all follow-up queries for one article use the same snapshot. Document read-only SQLite inspection and bounded additional SELECT queries for questions not covered by the later stage helper. Avoid an unrestricted network query service.
8. Keep generated bundles, databases, runtime settings and caches out of version control. Use one replaceable working snapshot by default rather than automatically retaining a full database for every stage. Do not read or copy the separate Drive credential store.
9. Document the helper's installation/build/run steps as executable PowerShell one-liners, local access requirements and offline behavior. Do not modify global Codex settings, weaken existing sandbox/approval boundaries or claim the local API is an enforced read-only security boundary merely because this helper uses GET.
10. Add focused tests for successful fetch/offline acquisition, wrong save identity, checksum mismatch, unsafe archive shape, unsupported versions, interrupted refresh preserving the valid snapshot, read-only query behavior and source database/RNG immutability.

## Architectural direction

Prefer one small .NET host tool using existing project/runtime and SaveBundle facilities, with a minimal local configuration file. Keep networking and staging separate from read-only database operations. Avoid a generic repository, new service, MCP server, AI SDK or parallel persistence implementation. Reuse existing export integrity tests and cheap prepared-save fixtures where appropriate. The default container's existing loopback export endpoint is the only game access required.

## Acceptance criteria

- [ ] A local command obtains a verified snapshot of the explicitly configured save from the default container deployment; an existing bundle also works offline.
- [ ] An invalid or failed refresh cannot become the active snapshot or silently fall back as current data.
- [ ] Metadata identifies the exact data source and coverage, and all inspection uses read-only SQLite access without initialization/migration side effects.
- [ ] Additional documented read-only queries can inspect the same snapshot without fetching a second source.
- [ ] No game, container or global-agent configuration changes are needed for the normal route, and runtime data is ignored by Git.
- [ ] Focused validation and a complete PowerShell setup/download/inspect example are delivered.

## Verification

Run the focused helper/bundle tests using the actual new project/filter, then the required backend build, formatting and test checks from target AGENTS.md; record exact commands and completed results. Exercise a local HTTP test host or loopback stub returning a real valid export, then run the helper offline against it. Compare source/save hashes and persisted RNG before/after inspection, and prove a write attempt through the reader fails. Test refresh failure with a pre-existing working snapshot. Document a manual smoke procedure against the default Compose app; do not require a running Docker daemon or live user data in CI.

## Out of scope

- Stage evidence/standings interpretation, article generation, editorial notebooks or archive management, covered by MSS-134/MSS-135.
- Automation, scheduled jobs, model/API integration, token accounting, new UI or reporting service.
- Changing sporting rules, simulation, save migration/import, export formats or the existing snapshot algorithm.
- Direct access to live SQLite/WAL files, Docker administration, Drive changes, remote publishing or global agent configuration.

# MSS-063 — Add Type Cup qualification draw, Live progression, Final, and history UX

## Goal

Present the scalable Type Cup as a clear tournament experience.

For over-32 fields, users should see the random group draw, follow qualification groups, understand who advanced or was eliminated, and then experience a fresh 32-team Final. Preserve the current polished Cup/Live/history style and keep direct-final Type Cups simple when there are 32 or fewer teams.

## Context

- Depends on MSS-062.
- Current React Type Cup experience assumes one team event:
  - `typeCupApi.ts` returns one team/leg result;
  - `CupEditionPage` and `CupTeamPage` show selection/result data;
  - Live event models one Type Cup team event with four athlete-rank groups;
  - historical pages expect one final set of team standings.
- The new backend exposes tournament draw, zero-or-more qualification groups, finalists, and Final.
- For 33-64 teams the natural presentation is two semifinal-like qualification groups with 16 advancing from each.
- For larger fields use generic "Qualification Group A/B/C..." terminology so the UI scales without pretending every stage is literally a semifinal.

## Requirements

1. Add a Type Cup tournament overview for the selected season.
   It should show:
   - total selected teams;
   - whether the Cup is direct-final or qualification + Final;
   - qualification group count;
   - group sizes;
   - places advancing from each group;
   - current tournament state;
   - Final field size.

2. Show the persisted random draw clearly.
   - Group teams under Qualification Group A/B/C... (or equivalent).
   - Preserve team badges/squad links where existing UI supports them.
   - Make it explicit that the draw is random and persisted, not strength seeded.
   - Do not redraw client-side.

3. Preserve a simple direct-final experience for <=32 teams.
   - Do not show empty qualification scaffolding.
   - Existing Type Cup navigation should feel essentially unchanged.

4. Integrate qualification into Live progression.
   - Show which qualification group is active/completed/pending.
   - Within an active competition group, reuse the existing #1/#2/#3/#4 athlete-rank-group presentation and round progression.
   - After a qualification group completes, show its final team table and qualification cutoff.
   - Provide clear continuation to the next qualification group and ultimately to the Final.
   - Do not require returning to Dashboard after every group.

5. Support fast progression.
   - Preserve the ability to run the remaining Type Cup automatically.
   - A fast-run path must use backend persisted progression and canonical order, not frontend simulation.
   - The UI should remain usable for a tournament with several qualification groups.

6. Make qualification result tables easy to read.
   At minimum show:
   - team rank;
   - creature type/team;
   - score;
   - qualified/eliminated status;
   - visible cut line after the final qualifying place.
   Reuse current table-alignment conventions from MSS-046.

7. Present the Final as a new sporting stage.
   - Label it clearly as **Type Cup Final**.
   - Explain that qualification points reset.
   - Show the 32 finalists before/while the Final starts.
   - Final result page continues to show Gold/Silver/Bronze and champion as the authoritative Type Cup podium.

8. Generalize team/leg result views.
   - Allow inspection of qualification group legs as well as Final legs.
   - Make phase/group context explicit so a "Group #1 rank" is not confused with qualification-group identity.
   - Use data-driven labels rather than parsing strings.

9. Extend Cup history.
   Historical Type Cup editions should show:
   - original selected team count;
   - qualification draw when one existed;
   - each qualification group's final table;
   - qualified teams;
   - Final table/podium;
   - old-format Cups without fabricated qualification stages.

10. Extend athlete Cup history/profile semantics where appropriate.
    - An athlete eliminated in qualification still has a Type Cup participation for that season/team.
    - Final participation should be distinguishable from qualification-only participation.
    - Do not count qualification-group victories as major honours.

11. Keep UI performance bounded.
    - Do not eagerly render every round payload for every qualification group.
    - Tournament overview may load summary data first and fetch detailed group/round data on demand.
    - Avoid a giant single table/DOM for all teams and all stages.

12. Preserve responsive/accessibility quality.
    - Desktop, tablet, and phone layouts remain usable.
    - Qualification status cannot rely on color alone.
    - Existing reduced-motion behavior for Live/reveals remains respected.
    - Controls remain keyboard-operable.

13. Update frontend tests for direct-final and qualification formats.

## Architectural direction

- Extend the current Cup edition/team pages rather than create unrelated parallel navigation.
- Model tournament phase and qualification group explicitly in frontend types/routes.
- Reuse existing Cup team tables, badges, squad tiles, Live action controls, and result formatting where practical.
- For two groups, "Semifinal A/B" may be used as a friendly secondary label, but generic qualification-group identity must remain available for 3+ groups.
- Backend persisted facts are authoritative; the frontend never computes who qualified.

## Acceptance criteria

- [ ] A <=32-team Type Cup opens directly into the familiar Final flow.
- [ ] A 33-64-team Cup displays two random qualification groups and 16 advancing places in each.
- [ ] A 65+ team Cup displays the correct number of generic qualification groups and quotas.
- [ ] Live clearly progresses qualification groups before the Final.
- [ ] Completed qualification tables show an obvious qualification cutoff.
- [ ] Users can continue through groups without unnecessary Dashboard round trips.
- [ ] "Run remaining" completes the backend tournament in canonical order.
- [ ] Final is clearly separate and starts with reset scores.
- [ ] History retains qualification draw/results and Final result.
- [ ] Qualification-only athlete participation appears correctly in athlete Cup history.
- [ ] Old historical Type Cups still render correctly.
- [ ] Large tournaments do not eagerly render/load every round payload.
- [ ] Frontend tests, typecheck, and build pass.

## Verification

Run:

```bash
npm ci --prefix src/MtgSoloSports.Web
npm run test --prefix src/MtgSoloSports.Web
npm run typecheck --prefix src/MtgSoloSports.Web
npm run build --prefix src/MtgSoloSports.Web
```

Also run the standard backend suite for changed API contracts.

Manual/end-to-end verification:
1. Open a 32-team Type Cup and verify no unnecessary qualification UI appears.
2. Open a 35-team Cup, inspect random Group A/B draw and 16/16 cutoffs.
3. Play several qualification rounds manually on Live.
4. Finish one group and inspect qualified/eliminated states.
5. Run remaining groups automatically and verify the 32-team Final field.
6. Confirm Final scores start at zero.
7. Complete Final and inspect podium/honours.
8. Inspect an athlete eliminated in qualification and confirm the Cup appearance is retained.
9. Inspect a 65+ team Cup with 3+ qualification groups.
10. Reopen old Type Cup history created under the previous >32 single-field format.
11. Check desktop/tablet/phone layouts.

## Out of scope

- Changing squad allocation rules.
- Strength seeding.
- Knockout brackets/home-away series.
- Carrying qualification scores to Final.
- New major honours for qualification-group winners.
- Color Cup changes.

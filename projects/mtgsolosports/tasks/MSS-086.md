# MSS-086 — Introduce structured, human-readable exports for Athlete and Standings pages

## Goal

Let a spectator download complete, trustworthy textual reports of an athlete profile and a selected league/season standings table for sharing with ChatGPT, without manually copying UI panels. Establish a small reusable export contract that later Cup, team, league and season reports can extend.

## Context

- Project `mtgsolosports`; target: `AlexBDevCorner/MtgSoloSports` (`main`).
- MtgSoloSports is a local single-user .NET 10 / React + TypeScript application using one persisted SQLite database per universe/save. Canonical read slices already exist for `Features/Athletes/GetProfile`, `Features/Leagues/SeasonTable`, `Features/Leagues/CurrentStandings`, and their React screens.
- Existing `Features/Saves/ExportSave` downloads a portable `.mtgsave.zip` database backup; **that is not the reporting format**. Do not change backup/import behavior.
- Intended usage: provide factual source material to ChatGPT for sports reporting. An export is a snapshot of selected *persisted* data, not AI-generated commentary and not text scraped out of the rendered DOM.
- Later tasks MSS-087 and MSS-088 build on the format and conventions introduced here. Follow `AGENTS.md`, including direct Endpoint → Handler, **no MediatR**, no generic repository/service architecture.

## Requirements

1. Provide user-visible `Download report` action on the **Athlete profile** and **Standings** pages. Keep the UX compact and consistent with the dark sports-database styling; allow `Markdown (.md)` and `JSON (.json)` formats without requiring manual text selection.
2. Produce reports **on the backend** from authoritative persisted read models/queries. Reports are scoped to the current save and exact page selection; never synthesize results in React or depend on pagination/virtualization hiding rows.
3. Athlete report includes card/athlete identity (stable ID and display name), career summaries, season-by-season participation with historical league/tier and results, honours, official Cups and placements, team selections, movements, and any existing relevant profile projections that can be obtained reliably. Include empty sections when no results exist. Do not fabricate missing histories.
4. Standings report includes precisely the **selected season and selected league**, league identity/tier/colour, all official rows (not only visible viewport), rank, athlete ID/name, points, stage/season context, relevant movement or qualification zones if already authoritative, and a clear `provisional` versus `completed/final` status. Historical seasons must not silently fall back to current season, Superleague or another feeder division.
5. Define a **small versioned report contract** suitable for future exports. JSON must be valid and stable, with at least `schemaVersion`, `reportType`, `saveId`, scope identifiers, snapshot phase/season/stage information, and typed data. Markdown must be readable standalone, with title, same scope/status/metadata, descriptive headings, tables or concise subsections, and unambiguous field labels. Do not embed JSON as a substitute for a Markdown report.
6. Keep sporting numbers exact: preserve stored fixed-point units (for example thousandths) and clearly document them in JSON; format Markdown scores consistently without changing sporting calculations. Differentiate 0, null/unavailable, incomplete and not-applicable. For event/league totals, name the score type correctly; weighted Career Leaders points are not official league standings points.
7. Use a consistent, safe filename pattern containing the report kind and enough season/league/athlete context to distinguish downloads, plus correct `Content-Type` and `Content-Disposition: attachment`; UTF-8 works with punctuation and unusual creature names.
8. Ensure snapshot reads cannot mix states across a simulation mutation: use existing persisted boundaries/consistent-read capabilities where practical. A download must be read-only, consume no RNG, modify no save data, and require no external services.
9. Handle invalid save, missing athlete, unavailable season/league, incomplete history and server failures with appropriate HTTP responses and visible error feedback. Avoid path traversal, user-supplied SQL, arbitrary table access, and uncapped user-entered queries.
10. Reuse existing query/projection code and browser download utilities; allow shared *report contract/rendering helpers* only where justified, but avoid creating a global generic analytics/query-builder layer. Document exported fields, units, status semantics and versioning in the repository.

## Architectural direction

- Prefer focused export slices in the appropriate Features area or a small `Features/Reports` grouping with direct Endpoint → Handler; reuse `GetAthleteProfile`, `SeasonTable` and `CurrentStandings` semantics, including their completed/provisional distinctions.
- A stable reporting envelope and compact Markdown rendering primitives may be shared by future report slices. Keep report format independent from React components and sporting simulation.
- Frontend controls should download the API response as a file; use existing API error/loading conventions and keyboard-accessible UI patterns.
- Make no schema migrations unless genuinely unavoidable; do not copy the full SQLite database into a report.

## Acceptance criteria

- [ ] From an athlete page, a user can download one complete UTF-8 `.md` report and one valid `.json` report for that athlete, including multi-season/Cup history and identifying context.
- [ ] From Standings, downloads reflect **exactly** the chosen save, season and league, with every row in the correct order and the correct provisional/final status.
- [ ] Each export carries version, scope, readable labels and precise sporting values; reports are usable without access to the MtgSoloSports UI.
- [ ] JSON and Markdown agree on athlete identities, rankings, achievements and numerical values.
- [ ] No unrelated athlete, league or save data leaks into the report.
- [ ] Empty/new saves, old-format saves where supported, long athlete careers, multiple feeder levels and unavailable data are handled without invented results.
- [ ] Export calls are read-only and do not change save checksum/simulation progression or RNG.
- [ ] Download actions are usable via keyboard, show failures and do not disturb existing page navigation.
- [ ] Tests cover formatting, exactness, determinism of sporting content, bad identifiers, current vs historical standings and long/special-character names.

## Out of scope

- Cup edition, team and league profile downloads (MSS-087).
- Full-season journalism dossiers and historical almanacs (MSS-088).
- Generic SQL editor, arbitrary query builder, custom report designer, raw SQLite dump, or exposing the filesystem/database over a network.
- Direct ChatGPT authentication, external API/MCP server, cloud synchronization or automated ChatGPT project uploads.
- Sporting scoring, rules, rankings, persistence model, save backup/import, or page redesign unrelated to download actions.

# MSS-050 — Add a visual promotion and relegation reveal

## Goal

Make the promotion/relegation event feel like a meaningful end-of-season moment instead of only presenting the outcome as static data.

Add a dedicated **promotion and relegation reveal** that visually communicates athletes moving between leagues: relegated athletes should visibly move down to their destination league, while promoted athletes visibly move up into their new league.

The experience should be clear, dramatic enough to feel important, and still leave a useful static summary after the reveal is complete.

## Context

- Project: `mtgsolosports`; target repository: `AlexBDevCorner/MtgSoloSports`; default branch: `main`.
- Promotion and relegation are important season events because they change where athletes will compete next season.
- The current event needs more visual weight and should make it immediately obvious **who moved, in which direction, from which league, and to which league**.
- MtgSoloSports already has reveal-oriented competition UI. Reuse the established visual language and interaction patterns where practical rather than creating a disconnected presentation style.
- Follow `AGENTS.md`, `docs/game-rules.md`, the existing vertical-slice architecture, and current frontend styling conventions.

## Visual direction

Use a **league movement board** as the main concept.

For each promotion/relegation boundary:

1. Show the two affected leagues as vertically related destinations, with the higher league above and the lower league below.
2. Represent each affected athlete with a compact athlete/card tile using existing athlete imagery and identity conventions where available.
3. Reveal movements one by one:
   - a **relegated** athlete starts in the higher league and visibly moves downward across the league boundary into the lower league;
   - a **promoted** athlete starts in the lower league and visibly moves upward across the boundary into the higher league.
4. Once the movement completes, leave the athlete visibly placed on the destination side with an explicit **PROMOTED** or **RELEGATED** state and the destination league name.
5. After all movements have been revealed, show a stable final summary of all league changes so the result remains easy to inspect without relying on the animation.

The animation should reinforce the sporting meaning of the event. Avoid decorative motion that does not communicate league movement.

## Requirements

1. Add a dedicated visual presentation for the promotion/relegation event.

2. The presentation must clearly show, for every affected athlete:
   - athlete identity;
   - whether they were promoted or relegated;
   - previous league;
   - destination league.

3. Visualize league hierarchy spatially:
   - higher league above lower league;
   - promotion moves upward;
   - relegation moves downward;
   - league boundaries/destinations remain clearly labelled throughout the reveal.

4. Reveal affected athletes progressively rather than instantly dumping the complete result on screen.
   - Reuse the application's existing reveal interaction conventions where practical.
   - Provide a way to advance through the reveal without requiring the user to wait for long automatic timers.
   - A completed event must also be viewable immediately in its final state when revisited.

5. Use existing athlete/card imagery where available. The reveal should be visually recognizable as MtgSoloSports rather than a generic list of names.

6. Make promoted and relegated states visually distinct, but do not rely on colour alone. Direction, labels/icons, and movement should communicate the result.

7. If several athletes move across the same league boundary, keep the sequence understandable and avoid overlapping cards or animations.

8. If the competition structure contains several promotion/relegation boundaries, reveal them in a logical order and make the active boundary obvious. Do not mix unrelated league transitions into an unreadable single animation.

9. At the end of the reveal, show a persistent summary grouped by destination/source league or boundary, for example:
   - promoted athletes;
   - relegated athletes;
   - old league → new league.

10. Revisiting a completed historical promotion/relegation event must show the actual historical movements from that event rather than deriving them from the athlete's current league.

11. Respect reduced-motion preferences. When reduced motion is enabled, preserve the same information and reveal progression using restrained transitions or immediate state changes.

12. Keep the presentation responsive. Athlete names/cards, league labels, controls, and movement results must remain usable on both wide desktop screens and narrower layouts.

13. Preserve all existing promotion/relegation rules, qualification logic, tie-breaks, league assignments, and persisted results. This task changes presentation only.

## Architectural direction

- Start from the existing promotion/relegation event/result slice and existing reveal components.
- Keep sporting calculations and movement decisions in the current backend/domain logic. The frontend should receive authoritative movement results rather than reimplement promotion/relegation rules.
- Expose enough result metadata for the UI to render each movement explicitly: athlete, source league, destination league, and movement type.
- Prefer a small reusable movement/reveal model/component if multiple league boundaries use the same behavior.
- Use CSS transitions/animations consistent with the existing frontend rather than adding a heavy animation framework solely for this feature.
- Persist/reuse reveal completion state only if the existing event reveal architecture already has an established mechanism for it; historical correctness must come from persisted sporting results, not from animation state.

## Acceptance criteria

- [ ] Promotion/relegation results are presented through a dedicated visual reveal rather than only a static table/list.
- [ ] Every affected athlete clearly shows their previous league, destination league, and promoted/relegated status.
- [ ] Promoted athletes are visually shown moving upward into the higher league.
- [ ] Relegated athletes are visually shown moving downward into the lower league.
- [ ] League names/boundaries are visible enough that the movement can be understood without reading an explanatory paragraph.
- [ ] Multiple movements across the same boundary remain readable and do not visually collide.
- [ ] Multiple league boundaries are presented in a clear sequence/grouping.
- [ ] The reveal can be progressed deliberately without forcing the user through long automatic delays.
- [ ] After completion, a clear static summary of all movements remains visible.
- [ ] Revisiting a completed historical event shows the correct historical promotion/relegation movements.
- [ ] Reduced-motion users receive the same information without depending on movement animation.
- [ ] The layout works at existing desktop and narrow responsive widths.
- [ ] Existing promotion/relegation outcomes and league assignments remain unchanged.
- [ ] Frontend tests cover rendering of promotion, relegation, multiple movements, completed/historical events, and the no-movement/edge state if such an event is possible.

## Verification

1. Run the standard backend checks documented in `AGENTS.md` if any API/DTO code changes.
2. Run the frontend checks documented by the repository, including at least typecheck, tests, and build.
3. Complete a season/event with both promoted and relegated athletes.
4. Verify each movement starts from the correct league and ends in the correct destination league.
5. Verify several athletes moving across one boundary remain readable.
6. Verify an event with multiple league boundaries presents each boundary clearly.
7. Complete the reveal and confirm the final summary matches the authoritative competition result.
8. Reopen the completed event and confirm the historical movements remain correct.
9. Verify the experience at a wide desktop width and a narrow viewport.
10. Verify reduced-motion mode still communicates every movement and result clearly.

## Out of scope

- Changing promotion/relegation qualification rules, number of promoted/relegated athletes, tie-breaks, or league structure.
- Changing season scoring or simulation outcomes.
- Redesigning unrelated league tables or season pages.
- Adding a general-purpose animation framework solely for this feature.

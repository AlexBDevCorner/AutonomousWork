# MSS-092 — Include per-stage athlete placements in Standings exports and season dossiers

## Goal

Preserve the **stage-by-stage journey of every league athlete** in exported reports. An athlete's final or provisional season rank alone does not tell the story: the report should show each completed stage's individual placement (P1–P32) so a ChatGPT sports columnist can trace winning streaks, slumps, reversals and late recoveries from factual source data. Include the same Superleague stage history in the Season Dossier, since that is the primary journalism source shared with ChatGPT.

## Context

- Project: `mtgsolosports`; target: `AlexBDevCorner/MtgSoloSports`, default branch `main`.
- MSS-086 (Athlete + Standings exports) and MSS-088 (Season Dossier) are already implemented and done. This is a focused **enhancement to their existing reports**, not a new reporting framework.
- The Standings UI already shows a 32-stage placement matrix loaded from `GET /api/saves/{saveId}/history/seasons/{seasonNumber}/competitions/{leagueId}/placements`. See `Features/History/GetSeasonPlacements`, `src/MtgSoloSports.Web/src/features/standings/standingsApi.ts`, and `matrix.ts`.
- `SeasonPlacementCell` includes `AthleteId`, `StageNumber`, `StageRank`, `EarnedBonusThousandths`, `ChampionshipPointsThousandths`, `StageScoreThousandths`, `RoundWins`. All values already come from persisted `StageStandingEntity`; no new data or round replay is required. Incomplete stages have **no cell**; absent does not mean P32, zero points or a completed stage.
- `Features/Reports/StandingsReport/GetStandingsReportHandler.cs` currently emits only total table rows via `StandingsReportJson` and `StandingsReportMarkdown`.
- `Features/Reports/SeasonDossier` includes a full Superleague standings table and a `stageProgression` **winners-only** summary; it does not describe the placements of all 32 athletes in all completed stages.
- Distinguish **per-stage placement** (P1…P32 finish in one stage) from **cumulative season rank after that stage**. This task exports the former; do not label it as the latter or invent season-rank progression.

## Requirements

1. Enhance the **existing Standings Markdown and JSON report** for the **exact selected save + season + league** with a complete, chronological, per-athlete list of placements for all **persisted completed stages**, including historical completed seasons and current provisional seasons. All athletes shown in the standings roster should be represented; preserve the current full-season standings table, metadata, status and zones unchanged.
2. Use the same authoritative `StageStandingEntity` data/semantics as `GetSeasonPlacements`; reuse its projection/mapping and validation logic where practical rather than introducing separate calculations, frontend scraping, decompression of round payloads, or any extra sporting RNG work. All report data must be captured in one consistent read transaction, as the Standings report already does.
3. **JSON**: add a versioned, documented, structured placements section (or a clearly named per-athlete nested collection) with unambiguous `stageNumber`, `athleteId`, `stageRank`, `championshipPointsThousandths`, `earnedBonusThousandths`, `stageScoreThousandths` and `roundWins`, sourced from persisted completed stages. Use stable athlete IDs, deterministic ordering, integer fixed-point values and explicit units. Never conflate stageRank with overall seasonRank. Keep existing `standings` and other fields backward-compatible (additive contract change where feasible).
4. **Markdown**: add a readable `Stage placements` section with every athlete's P1–P32 result across all completed stages, in chronological stage order and sorted by the main standings rank. Prefer 8-stage blocks (Stages 1–8, 9–16, 17–24, 25–32, or available partial ranges) rather than a single unwieldy 32-column table. Rows should identify athlete name **and ID**, and cells should display concise labels like `P1`, `P12`; optionally explain additional exact stage points/bonus in an appendix, but avoid excessively widening the matrices.
5. Empty and incomplete data must be explicit: never label an unplayed/in-progress stage as completed, silently fill its ranks with zeros/last place, or fabricate a missing stage. If no stages have completed, include a clear `No completed stages yet` explanation instead of a fictitious matrix. Historical finalized seasons should include the full persisted stage history. Derive stage counts from saved rules where appropriate, not an assumption that every old save has the current default format.
6. Extend **Season Dossier Markdown and JSON** with the equivalent full **Superleague** athlete-by-stage placement trajectory for its selected season, including current in-progress seasons, using the same matrix and JSON semantics as the Standings report. Preserve `stageProgression` winner summaries (do not substitute one for the other) and all existing Cup/postseason/record sections. For legacy Season 1 without an official Superleague, follow and clearly label the dossier's existing league fallback; do not misidentify a feeder as Superleague.
7. Keep scope bounded: the Season Dossier only needs a full stage matrix for the league already used for its full table (normally Superleague), **not** 24 feeder matrices. Exporting a specific feeder league's full matrix belongs to its Standings report. Keep Markdown usable for ChatGPT text ingestion and report size reasonable.
8. Validate integrity: completed stage groups must cover the correct league's season roster/ranks, no duplicate `(athleteId, stageNumber)`, no cross-season/save leakage and no ambiguous silently dropped values. If persisted stage data is corrupt, fail with an actionable error instead of manufacturing a plausible trajectory.
9. Preserve exact official scoring and historical status semantics: stage championship points are **per stage**; season championship points in the existing table are **cumulative totals**; earned stage bonus applies only from the next stage. Avoid using weighted Hall of Fame career points. No persistence, rules, game results, page styling or save backup changes.
10. The new content should naturally be included in any future Markdown/JSON download or Google Drive publishing workflow that calls these existing report generators, without creating new report names or a second export endpoint. Where applicable, ensure existing meaningful-content change detection and fingerprints consider the new stage data so the next publish sees an updated report.
11. Add focused tests for selected historical season/league identity; 32 athletes and multiple completed stages; exactly one stage; no completed stage; a partially played current stage; legacy first season; JSON-vs-Markdown rank alignment; special-character names; stage points/bonus exactness; and the dossier's Superleague trajectory vs its Standings export. Ensure existing old response fields and dossier winner summaries remain intact.

## Architectural direction

- Extend `Features/Reports/StandingsReport` and `Features/Reports/SeasonDossier`, sharing a small read-only `StagePlacementReport` projection/renderer if needed to avoid inconsistent JSON/Markdown behavior. Existing `GetSeasonPlacementsHandler` has `MapCells` and `ValidateStandings` primitives; reuse/adjust safely rather than duplicate the same stage logic.
- Keep direct Endpoint → Handler (no MediatR), source data `AsNoTracking`, fixed-point integers in JSON and plain `P#` labels in Markdown.
- Preserve a single consistent snapshot per report and avoid nested independent contexts/HTTP calls. The dossier currently queries stage rows for winners; consider reusing the same loaded rows for both winners and the new matrix where reasonable.
- Avoid altering unrelated reports, standings UI, score calculations, or the semantic meaning of Stage Placements.

## Acceptance criteria

- [ ] Downloading a completed Standings report (`.md` and `.json`) shows **all 32 athletes' actual per-stage rankings** for every completed stage in the chosen league.
- [ ] Current-season Standings reports show only completed-stage placements and never assign ranks to a partly finished or future stage.
- [ ] Markdown matrix is legible, labels `Stage N` and `P#` clearly and is split into reasonably sized chronological blocks; rows match the main table's athlete IDs and rank order.
- [ ] JSON provides the exact stage rank, points, earned bonus, stage score and round wins for each persisted completed cell, with correct field names/units and stable IDs.
- [ ] Season Dossier for the same season includes its Superleague full placement matrix in Markdown and JSON, while keeping the previous winners-only stage progression and all other content.
- [ ] A specific feeder Standings export contains that feeder's own placements and never defaults to Superleague; dossier's legacy fallback is clearly identified.
- [ ] Incomplete/empty/legacy seasons and bad stored data are handled honestly; no fake positions, missing-athlete joins, duplicate stage entries or cross-save leaks.
- [ ] Export remains read-only, deterministic in sporting data, efficient, and compatible with existing report endpoints and Drive publishing.
- [ ] Automated tests cover all above, with normal backend/frontend quality gates passing.

## Verification

Run repository checks from `AGENTS.md` (at least .NET restore/build/test/format and React test/typecheck/build). Inspect Markdown and parsed JSON from a multi-season save, including:
1. A completed Superleague season; verify all athlete x completed-stage cells against the existing GetSeasonPlacements API.
2. An ongoing season midway through the stages, with an incomplete next stage; verify no fabricated cells.
3. An F1 (or F2/F3) Standings report for the same season, verifying exact league scoping.
4. Season Dossier for the matching season and Superleague, verifying identical stage placements and unchanged stage winner list.
5. Empty and legacy Season 1 cases.

Confirm report generation never changes save progression, stored stage standings or RNG, and existing report downloads remain valid.

## Out of scope

- Cumulative overall season-rank movement after every stage (distinct statistic from Stage Placements); an additional historical projection would be a separate feature.
- Exporting every league's stage matrix into one huge Season Dossier, all rounds or individual round placements, or building a generic historical analytics engine.
- New Standings UI views, changing stage ranking/bonus/points rules or modifying persisted sporting data.
- Google Drive OAuth/publishing implementation, independent ChatGPT integration or broad report format redesign.

# MSS-089 — Connect MtgSoloSports to Google Drive and add one-click report publishing

## Goal

Let the user press **Publish to Drive** in MtgSoloSports to update an existing current-season dossier and universe almanac **in place** in their own Google Drive hierarchy, eliminating manual download/upload after each stage. Establish a secure, read-only-to-simulation publishing foundation for future automatic and broader report synchronization.

## Context

- Project `mtgsolosports`, target repository `AlexBDevCorner/MtgSoloSports`, default branch `main`. Follow `AGENTS.md`: vertical-slice Endpoint → Handler, no MediatR; never change simulation/scoring rules.
- MSS-086, MSS-087 and MSS-088 are done. Reuse the existing `Features/Reports` contract, `SeasonDossier` and `UniverseAlmanac` handlers and `src/MtgSoloSports.Web/src/features/reports/ReportsPage.tsx`.
- MtgSoloSports runs locally, commonly as a single ASP.NET Core + React service in Docker with named-volume persistence. It is not an internet-hosted service; Google Drive publishing requires **new explicit user authorization from within MtgSoloSports**. The ChatGPT Google Drive connector cannot be reused as application OAuth credentials.
- User's actual Drive organization to preserve (names as example, **no hard-coded folder IDs**):
  `MtgSoloSports/mtshistory/universe-almanac-newtest.md`,
  `MtgSoloSports/mtshistory/Seasons/season-17-dossier.md`,
  with `Color Cup/Cups`, `Color Cup/Teams Histories`, `Type Cup/Cups` and `Type Cup/Teams Histories` reserved for future sync.
- Existing filenames may be manually chosen (e.g. `universe-almanac-newtest.md`) and must not be guessed over or replaced without explicit adoption.
- Google Drive API supports updating content of an existing file via files.update; a narrow `drive.file` OAuth scope can manage app-created/explicitly shared files. It does **not** imply that an app can edit every preexisting file just because it knows a folder ID. Access and account linking must be implemented honestly, without silently escalating to full Drive scope.

## Requirements

1. Add a compact **Google Drive publishing** section to Reports with connection status, `Connect Google Drive`, `Disconnect`, destination configuration, `Publish now`, progress and last-result/error status. Existing download .md/.json actions continue unchanged.
2. Implement a documented OAuth 2.0 user-consent flow appropriate to this local/browser/Docker setup. Prefer least-privilege access (`drive.file` and explicit file/folder selection or equivalent). If narrow authorization cannot safely grant access to existing documents, provide a deliberate adoption/consent step or clear error; **do not** request all-Drive write permissions or invent a bypass. No need to expose the user's entire Drive.
3. Keep any application OAuth client config and refresh tokens server-side in persistent, permission-restricted local storage separate from each sports save. Never commit secrets, expose access tokens in frontend responses, put them in query strings/logs, or ship the ChatGPT connector's credentials. Support disconnect/revoke where available. Work after container restart using existing persistent volume/config. Provide practical setup documentation for a personal OAuth application and localhost callbacks; fail gracefully if Google credentials are not configured.
4. Allow selecting/configuring the target `mtshistory` directory and explicitly mapping the **current season dossier** to `Seasons/season-N-dossier.md` and the **universe almanac** to a file under the root. Support existing user-created files by explicit selection/adoption, retaining their remote file IDs and custom names (including `universe-almanac-newtest.md`). New files use stable report filenames.
5. `Publish now` regenerates the **current/latest season dossier** and **almanac** from persisted reports and uploads their Markdown payloads. Only publish data for the selected save; never export a different universe into a destination configured for another without explicit warning/confirmation. Report metadata, fixed-point numbers, historical/provisional status and content must match the download endpoints.
6. **Update in place** using the stored verified Drive file ID for a previously adopted/created report. Do not create `(1)` duplicates on retries; resolve destination conflicts and ambiguous name matches by stopping with actionable diagnostics or asking user to explicitly adopt one file. No blind delete/rename/move of user-owned objects. Maintain a small persistent mapping: save + report semantic identity → folder/file ID, destination name and last successful content fingerprint.
7. Avoid unnecessary writes: compare meaningful report content/state, not a volatile generated timestamp; unchanged publication should report `Up to date`. Retry-safe handling of timeouts and partially acknowledged uploads must re-check file identity before create. If an existing remote file was edited independently since last publish, do not silently discard edits without an explicit policy/confirmation.
8. Publication may be triggered only by user action in this task; network and Google API failures must never roll back, advance or corrupt a simulation. Use server-side read-only snapshot generation, bounded requests/retries/cancellation, and visible per-file outcome (created/updated/unchanged/failed) plus last-published season/stage/phase.
9. Keep destination configuration separate from sporting save data and backup ZIPs, and avoid exposing publishing endpoints to unrelated origins. Support multiple saves without mixing destinations; use existing localhost-only security assumptions but add appropriate OAuth state/PKCE, callback and CSRF protections.
10. Document setup and limitations: Google Cloud OAuth credentials/consent required, internet required for publishing, the app must be running to publish, destination permissions, how to link/refresh a Drive folder inside ChatGPT, and Drive updates do not automatically replace separately uploaded ChatGPT Project copies.
11. Test against fake Google OAuth/Drive clients (no real account needed in CI), including existing-file adoption, ambiguous names, refresh/restart, token failure, idempotent re-publish, in-place updates, stale remote edits, failed upload and cross-save isolation. All sporting functions remain unchanged.

## Architectural direction

- Favor focused `Features/Reports/GoogleDrivePublishing` handlers and a small typed Google Drive API client over a generic export/synchronization framework. Reuse existing report handlers, not loopback HTTP calls into your own server.
- The Google cloud consent client needs operator setup; never assume access because ChatGPT can read a Drive account.
- Keep immutable snapshot export separate from Google side effects. In-place remote writes are allowed only against explicitly selected/adopted destinations.
- If Google Picker is used, correctly handle access grants to **existing individual files**. A selected parent folder alone must not be assumed to grant read/write access to every preexisting child with `drive.file`.
- Add no new database schema to game saves for synchronization state; use local application-level settings storage in the persistent Docker volume.

## Acceptance criteria

- [ ] User can connect their own Google account, select the destination and inspect publishing status in Reports.
- [ ] `Publish now` creates or updates the current season dossier plus almanac as valid UTF-8 Markdown in the correct hierarchy.
- [ ] An already-present, explicitly adopted file is updated in place with the same Drive file ID, link and desired filename; a second publish with unchanged sporting state creates no duplicates.
- [ ] Manually named existing almanac can be selected without silently creating an additional file.
- [ ] Wrong save/destination, missing authorization, duplicates, remote conflicts and upload failures produce recoverable errors without changing any sporting outcomes.
- [ ] Authentication secrets stay server-side and survive ordinary container restart; disconnect works; token refresh/expired consent is handled.
- [ ] Export content matches current persisted dossier/almanac and is scoped correctly to season/save.
- [ ] Backend/frontend tests prove idempotency, authorization state and error handling; user-facing setup docs exist.

## Verification

Run .NET restore/build/test/format, React test/typecheck/build, and any Docker smoke checks mandated by `AGENTS.md`. Add fake OAuth/Drive integration tests; manual opt-in E2E checklist: configure OAuth in localhost Docker, connect account, adopt existing season/almanac Markdown files, publish, advance stage, publish again, verify **same file IDs** and changed content, republish unchanged, test disconnected/expired credentials and transient failures. Do not place live credentials or private folder IDs in tests or task content.

## Out of scope

- Automatic publication after stage/Cup completion (MSS-090).
- Bulk initial upload/synchronization of every historical Cup, season and team report (MSS-091).
- Native Google Docs conversion, automatic ChatGPT Project upload, LLM-generated commentary, Google Drive-wide sync or unrelated Drive cleanup.
- Cloud-hosting MtgSoloSports, exposing SQLite/HTTP publicly, new simulation transitions, data model migrations, or broad project refactoring.

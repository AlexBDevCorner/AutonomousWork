# MSS-150 - Unify the two diverged qualifier engines

## Goal

One qualifier engine serves both the Superleague promotion qualifier and the feeder boundary qualifier, so future tie-break/rule changes cannot silently apply to one pipeline but not the other. Persisted results must be byte-identical before and after the refactor.

## Context

- A repository review (2026-11-19) verified the following; re-verify on the live checkout.
- `src/MtgSoloSports/Features/Superleague/RunQualifier/RunQualifierHandler.cs` (~1304 lines) and `src/MtgSoloSports/Features/Qualifiers/BoundaryQualifierRunner.cs` (~1138 lines) are ~65% line-overlap copies of the same engine, and they have already diverged: ranking goes through `StageCalculator.Rank(..., LeagueLevel.Feeder1)` in one and `RankWithFieldSize(...)` in the other; SHA-256 checksum builders are duplicated (`:541` vs `:518`); payload types are separate near-copies.
- The divergence is a live sporting-correctness risk: a tie-break or rule fix applied to one pipeline silently leaves the other producing different outcomes.
- Both endpoints and contracts stay as they are; only the internal engine consolidates. AGENTS.md demands deterministic simulation and versioned RNG; the two paths already run under the shared save lock with RNG state committed with results.

## Requirements

1. Extract one qualifier engine (feature-shared within `Features/Qualifiers`/`Features/Superleague` as fits the existing structure) parameterized by boundary/level and any genuinely different inputs. Keep both public endpoints, routes, and response contracts unchanged.
2. Eliminate the duplicated ranking call, checksum builders, and payload types; one implementation, two parameterizations.
3. Byte-identical outcomes: for the same seeds and starting states, both qualifier paths produce identical persisted payloads, checksums, and RNG state progression before and after the refactor. Prove with golden pinned seeds covering each path (do not replace existing pinned seeds or rule versions - AGENTS.md testing rules).
4. Where the two engines' behaviors genuinely differ today (not merely drifted copies), surface each difference explicitly in the PR description and preserve current behavior per path unless the difference is provably an unintended copy bug; any behavior change beyond consolidation must be its own follow-up, not smuggled in.
5. Keep RNG consumption order and transaction boundaries exactly as today (RNG state commits with results in one transaction).

## Architectural direction

- Follow the existing handler structure; no MediatR, no generic services. The extracted engine is feature-internal, not a `Shared/` abstraction, unless it is genuinely global - justify placement either way in the PR. Kernel stays pure and untouched.

## Acceptance criteria

- [ ] One engine implementation exists; both handlers delegate to it; no duplicated checksum/ranking/payload code remains between the two features.
- [ ] Golden-seed equivalence tests (per path) pass with unchanged expectations versus pre-refactor baselines recorded in the task evidence.
- [ ] Existing qualifier/superleague handler and HTTP contract tests pass unchanged; no expected sporting values change.

## Verification

Standard AGENTS.md backend sequence: locked restore, Release build, full test suite, `dotnet format --verify-no-changes`. Before refactoring, record pre-refactor golden outputs for both paths; after, rerun and diff. Run the qualifier/superleague focused classes alone from a fresh process.

## Out of scope

- Changing qualifier rules, tie-breaks, sporting math, seeds, rule versions, or which athletes qualify; frontend changes; unrelated refactors.

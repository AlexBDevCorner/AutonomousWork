# MSS-149 - Repair the save migration chain's snapshot drift and new-save cost

## Goal

New saves must not replay the full historical migration chain from zero, and the hand-edited model snapshot must be reconciled with the toolchain so the next generated migration is trustworthy.

## Context

- A repository review (2026-11-19) verified the following; re-verify on the live checkout.
- `src/MtgSoloSports/Persistence/Saves/SaveStore.cs:451`: every `CreateAsync` runs `MigrateAsync` from zero, replaying ~35 migrations per new save.
- The five newest migrations (e.g. `Persistence/Saves/Migrations/20261105000000_AddColorCupIndividualFormat.cs`) have no `.Designer.cs` companion, while `SaveDbContextModelSnapshot.cs:161` already contains their columns - the snapshot is hand-maintained. The next `dotnet ef migrations add` diffs against that hand-edited snapshot; any drift silently generates a broken migration.
- Schema migration and game-rule migration are separate concepts (AGENTS.md); this task is purely schema-side. Rules JSON must remain byte-identical across this work.

## Requirements

1. Make new saves fast and deterministic: create the database at the current schema baseline directly (squashed baseline migration or equivalent single-step creation) while existing saves continue migrating through the full existing chain. No existing save may require different steps than today, and migration must stay idempotent per save.
2. Reconcile the snapshot: regenerate `SaveDbContextModelSnapshot.cs` with the EF toolchain so it matches the real model at HEAD, and add every missing `.Designer.cs` for existing migrations, or commit to hand-written migrations with a CI check that fails loudly when a migration without a Designer file is added. Pick one policy and document it where migrations live.
3. Prove equivalence: a save created through the new fast path has the same schema (tables/columns/indexes/checks) as one created by replaying the full chain - assert with a schema-comparison test, not spot checks.
4. Failed-migration rollback (checkpoint -> migrate -> verify -> rollback) must keep working for both paths; the rules-snapshot byte comparison stays.
5. Documentation: record the chosen policy in the persistence area (migration README or equivalent) so future contributors follow it.

## Architectural direction

- Work stays in `Persistence/Saves` (migrations, snapshot, `SaveStore` creation/migration path) plus a schema-equivalence test in the test project. The EF tool may be used locally to regenerate the snapshot; do not change `SaveDbContext` model semantics. No sporting outcomes, no rule-version changes, no RNG.

## Acceptance criteria

- [ ] New-save creation no longer replays the historical chain (asserted: fresh create applies a single baseline step).
- [ ] An old save migrated from an earlier schema still migrates identically to today (existing migration tests keep passing; add one if coverage is missing).
- [ ] Snapshot matches the model at HEAD per the toolchain (or the CI guard exists and passes); schema equivalence between fast-path and full-chain saves is proven by test.
- [ ] Rules snapshot bytes unchanged; no existing golden/checksum test changes.

## Verification

Standard AGENTS.md backend sequence: locked restore, Release build, full test suite, `dotnet format --verify-no-changes`. Run migration-focused test classes alone from a fresh process. If CI gains a drift check, wire it into the existing ci.yml verification sequence.

## Out of scope

- Game-rule migration, schema redesign, column changes, catalog persistence (MSS-147), WAL handling (MSS-148), and any sporting behavior.

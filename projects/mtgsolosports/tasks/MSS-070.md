# MSS-070 — Restore Type Cup progression after squad selection and surface lifecycle errors

## Goal

Fix a blocking Season 2 postseason regression: after successfully selecting/revealing Type Cup squads, the Dashboard says "Nothing left to run for this season" and gives no way to start the Type Cup, although its qualification groups and Final have not been played. Restore the authoritative next lifecycle action, provide an obvious route to the tournament, and stop hiding season-status failures behind a false completion message. Preserve the existing save, squads, draw and simulation history.

## Context

- Target repository: `AlexBDevCorner/MtgSoloSports`, branch `main`. Reported 2026-10-10.
- Reproduction: create a new three-feeder-level universe; complete the 25-league Season 2 (800/800 league-stages). Resolve postseason movement, all qualifiers and rebalance. Select and fully reveal the Season 2 Type Cup squads (84 four-athlete teams in the reported save). **Do not run any Type Cup rounds**. Navigate to Dashboard and Cups.
- Actual Dashboard: Season 2 / Stage Complete / persisted phase `CupSelectionResolved`; "Next step" displays only a completed "League play" item followed by **"Nothing left to run for this season."** No Type Cup next action or start button.
- Actual Cups hub: "Type Cup — Season 2 / Squads selected · 84 teams", zero medals/best finish; it confirms selection persisted and no Final has run, but does not offer a visible Play/Continue action.
- Expected: the next backend lifecycle action is `RunTypeCupTeam`, with event progress for `type-cup-team` and a clear **Play Type Cup on Live** entry point. For an 84-team field, the current scalable format draws qualification groups (each <=32 teams), plays them, and advances exactly 32 teams to a fresh Final. The Cup is not complete until Final standings exist; only then can Season 3 start.
- Source inspection points to a likely **masked status-fetch failure**, not proof of a missing tournament engine:
  - `src/MtgSoloSports.Web/src/features/dashboard/useDashboard.ts` catches any non-abort error from `fetchSeasonStatus` and silently changes the result to `null`.
  - `src/MtgSoloSports.Web/src/features/dashboard/seasonFlowSteps.ts` reduces a null status to only the league step; on a complete season `SeasonFlow.tsx` renders "Nothing left to run for this season."
  - `src/MtgSoloSports.Web/src/features/cups/CupsHubPage.tsx` independently swallows `fetchSeasonStatus` errors, thereby hiding its current-event CTA.
  - The backend `Features/Seasons/SeasonLifecycle/SeasonLifecycleEvaluator.cs` correctly describes the `CupSelectionResolved -> RunTypeCupTeam` transition when the Cup selection exists and no Final standings exist.
  - `Features/Seasons/GetSeasonStatus/GetSeasonStatusHandler.cs` does not explicitly call `SaveStore.EnsureMigratedAsync`, whereas several mutation handlers do. Investigate this as a **hypothesis**, especially around migration `20261006233041_AddTypeCupTournamentFormat`; do not assume it is the cause.
  - `Features/Seasons/SeasonLifecycle/PostseasonEvents.cs` computes Type Cup progress, including tournament draw and stages. `Features/Cups/RunTypeCupTeam/RunTypeCupTeamHandler.cs` can auto-create the qualification draw at the start of play.
- We do not yet have the failing HTTP response or application logs from the user's local save. Establish the real backend root cause through a regression test and exception evidence instead of hardcoding the hypothesized diagnosis.
- Related already-completed tasks: MSS-061 (scalable format), MSS-062 (resumable qualifying + Final), MSS-063 (tournament UX). Preserve their functionality.

## Requirements

1. **Find and fix the cause of the missing legal action.**
   - Reproduce this precise persisted state through API/integration tests (completed Season 2, rebalance done, Type Cup squads selected, no Cup rounds or Final standings, >32 teams).
   - Query `GET /api/saves/{saveId}/season-status`. Capture the real HTTP status/exception and fix the underlying failure; examine save migration/version handling, lifecycle evaluation, Cup-state queries and Type Cup tournament progress.
   - The response MUST contain the proper source season, `expectedCup: TypeCup`, `cupSelectionResolved: true`, `cupTeamResolved: false`, `cupComplete: false`, exactly one legal next action `RunTypeCupTeam`, and playable `type-cup-team` event progress. The persisted phase may remain `CupSelectionResolved` until play begins; do not treat that as final.
   - Handle existing saves upgraded from before the Type Cup tournament migration as well as brand-new saves. If schema migration is required, make the status/read flow migration-safe and concurrency-safe using established `SaveStore` mechanisms. Do not bypass migrations, change sporting history or silently repair invalid states.

2. **Do not turn a status-fetch error into a misleading "all done" state.**
   - Keep `fetchSeasonStatus` failures separate from legitimate `null`/unavailable data in `useDashboard` and `CupsHubPage`. Surface an actionable error and Retry/Refresh with diagnostic detail appropriate for the user.
   - Dashboard's season-flow card must not claim no actions remain if the backend status is unavailable. A completed league season is NOT the same as a completed postseason.
   - Prevent an old/stale success response from hiding a newer error; ensure refresh after a mutation reloads status and next action correctly.
   - If the backend explicitly returns no legal action, distinguish genuinely finalized state from an unfinished Cup. Never provide a bypass button that can violate the authoritative lifecycle.

3. **Make the Type Cup start discoverable.**
   - Once squads have been selected, show a clear `Play Type Cup on Live` / `Continue Type Cup` CTA on Dashboard, Cups hub and at the end of the selection reveal (as applicable), linked to the correct save and source season.
   - Live must open the pending `type-cup-team` event before its first round, allowing `Next Round` or `Run remaining rounds`. The first valid play should use the existing deterministic auto-draw behavior (or the existing explicit draw UX, if needed) and then follow each qualification group and the 32-team Final.
   - Navigation/reload must never create a second selection, redraw an already-persisted draw, resimulate completed rounds, or accidentally start Season 3.
   - Preserve the existing direct-Final path for <=32 teams, historical Type Cup editions and current tournament presentation for >32 teams.

4. **Protect saves and sporting invariants.**
   - Preserve all 84 selected squads, their members/ratings and existing permanent nationality rules in the reported class of saves. Do not require the user to recreate the universe.
   - Preserve deterministic RNG, group draw, resume-after-partial-play, persisted round checksums, standings, and Final-only championship honours. Do not change results merely to make the UI progress.
   - Starting Season 3 must remain forbidden until the Type Cup Final completes.

## Architectural direction

- Identify and address the smallest root cause rather than adding a UI workaround for failed status.
- Keep the backend lifecycle/status authoritative; React only presents actions returned by the server.
- Prefer existing vertical slices and direct Endpoint -> Handler, no MediatR. Reuse Type Cup tournament and Live infrastructure from MSS-061 through MSS-063.
- Make failures observable without exposing internal exception stacks to normal UI users. Preserve meaningful diagnostic logs/tests.
- If the regression is due to a migration issue, add focused coverage for old-save upgrade and new-save read paths, including the relevant concurrency/caching behavior.

## Acceptance criteria

- [ ] A completed Season 2 with 84 selected Type Cup teams and zero Type Cup rounds returns HTTP 200 from `season-status` with `RunTypeCupTeam` as the legal next action and valid `type-cup-team` progress.
- [ ] Dashboard shows Type Cup as the next postseason step and a functioning **Play on Live** CTA; it does not show "Nothing left to run for this season."
- [ ] Cups hub exposes a working way into the pending Type Cup; the completed selection reveal offers a clear continuation.
- [ ] Clicking Play opens the correct Season 2 tournament with no rounds played yet. One next-round mutation starts qualification, and running remaining rounds completes the groups and then the 32-team Final in the correct order.
- [ ] The same progression works for a fresh save and a pre-tournament-schema save upgraded through supported migrations without data loss.
- [ ] A failed `season-status` fetch produces an explicit, recoverable error in Dashboard and Cups instead of falsely declaring postseason completion or showing an empty next action.
- [ ] React tests cover success -> refresh, failed fetch -> retry, and navigation after selection; backend tests cover the precise post-selection status and phase transition.
- [ ] Repeated GET/reload does not consume RNG, mutate selection/draw/round history or change sporting outcomes.
- [ ] A partly played tournament can resume; already persisted draw/rounds are not duplicated; no premature start of Season 3.
- [ ] Normal backend tests, frontend tests, typecheck and production build pass.

## Out of scope

- Changing Type Cup squad allocation, number of participating teams, qualification group sizes/advancement quotas, Final scoring or championship honours.
- Reworking the 17 Superleague/feeder qualifier competitions or promotion/relegation.
- Broad Dashboard/Cups redesign unrelated to visibility of the next legal Type Cup action.
- Mutating or deleting the user's save, bypassing the backend lifecycle, skipping Type Cup, or automatically starting Season 3.
- Nonessential visual issues in the recently improved qualifier reveals; these will be reported separately.

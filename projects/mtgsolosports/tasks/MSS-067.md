# MSS-067 — Profile and optimize the normal test suite runtime

## Goal

Bring MtgSoloSports normal verification time down substantially so autonomous workers and CI can run the full required test package repeatedly without spending tens of minutes per pass.

Optimize the test package itself rather than weakening verification. Preserve meaningful coverage and determinism while removing unnecessary database setup, duplicated expensive scenarios, serialization bottlenecks, and tests that belong in opt-in long-running diagnostics instead of the normal suite.

## Context

- Recent autonomous work on MSS-059 showed a full backend test pass taking roughly 30 minutes.
- The worker may need several verification cycles while implementing a task, so this runtime consumes a large fraction of the execution budget and encourages timeouts.
- The repository already contains both normal deterministic tests and deliberately expensive long-run/diagnostic scenarios.
- The objective is not merely to increase workflow timeout. Normal developer and CI feedback should become materially faster.

## Requirements

1. Measure before changing anything.
   - Run the normal backend test suite with timing data.
   - Identify the slowest individual tests, fixtures/classes, and repeated setup paths.
   - Record a reproducible baseline including machine/environment caveats.
   - Distinguish test execution time from restore/build time.

2. Produce a ranked explanation of the main runtime costs.
   Investigate at least:
   - repeated database creation/migration/seeding;
   - full-season or multi-season simulations inside ordinary tests;
   - large catalog/import setup repeated per test;
   - unnecessary sequential execution;
   - fixture lifetime and isolation strategy;
   - expensive HTTP/integration host startup;
   - duplicated end-to-end scenarios covering the same invariant;
   - waits/timeouts/retries or accidental real-time delays;
   - diagnostics or calibration scenarios that should not run in normal CI.

3. Optimize shared test infrastructure before deleting coverage.
   Prefer techniques such as:
   - reusable immutable fixtures where isolation permits;
   - cheaper database reset strategies;
   - transaction/savepoint reset where semantically safe;
   - shared application/test-host lifecycle;
   - deterministic minimal seed datasets for focused tests;
   - replacing broad simulations with narrower pure tests for local invariants;
   - parallel execution where tests are genuinely independent;
   - caching expensive read-only setup.

4. Keep isolation trustworthy.
   - No order-dependent tests.
   - No shared mutable sporting state across tests unless reset deterministically.
   - Tests must still pass when run individually and in the full suite.
   - Parallelization must not introduce flaky database/file/port collisions.

5. Separate genuinely long-running diagnostics from the normal suite.
   - Multi-season calibration, soak, benchmark, and long-run statistical tests may be opt-in when they are not required for every commit.
   - Keep fast deterministic regression tests for the same core invariants in normal CI.
   - Do not hide ordinary correctness tests behind opt-in flags merely to improve the reported number.

6. Avoid duplicated expensive verification.
   Where many integration tests exercise the same expensive setup for small variations, retain representative integration coverage and move narrowly testable rules into fast pure/unit tests where appropriate.

7. Preserve production behavior.
   This task is about test code, test infrastructure, and test/CI organization. Do not change sporting rules or production semantics solely to make tests faster.

8. Add durable timing visibility.
   Provide a documented command or test logger/report that makes slow-test regressions visible in future work.
   It should be practical to identify the slowest tests again without manually instrumenting the suite.

9. Set a performance target based on the measured baseline.
   - Aim for at least a **50% reduction** in normal backend full-suite wall-clock time.
   - Prefer bringing the suite comfortably below **10 minutes** on a GitHub-hosted runner if the measured bottlenecks make that realistic.
   - If the 10-minute target is not realistically attainable without unsafe compromises, document the remaining dominant costs and concrete follow-up work.

10. Check frontend verification too.
    Confirm that frontend typecheck/build/tests are not a comparable bottleneck and optimize obvious avoidable duplication if found, but keep the main focus on the backend suite.

## Acceptance criteria

- [ ] A before/after runtime baseline is documented with the exact commands used.
- [ ] The slowest tests/fixtures and primary causes are identified.
- [ ] Normal backend full-suite runtime is reduced by at least 50%, or a clearly evidenced blocker explains why that target cannot safely be reached.
- [ ] The suite preferably runs in under 10 minutes on a GitHub-hosted runner.
- [ ] No meaningful correctness coverage is removed merely for speed.
- [ ] Long-running diagnostics are separated from normal CI only where they have fast deterministic regression counterparts.
- [ ] Tests remain deterministic, isolated, and individually runnable.
- [ ] Parallel execution, if enabled, is proven not to introduce flaky shared-state failures.
- [ ] A repeatable slow-test timing/reporting mechanism is documented.
- [ ] Normal backend and frontend verification pass after the optimization.

## Verification

1. Capture a clean baseline full-suite run with timings.
2. Run the optimized suite at least three times and compare wall-clock time and failures.
3. Run the slowest previously identified tests individually.
4. Run representative database/integration test classes both alone and as part of the full suite.
5. If parallelism changes, run repeated full-suite passes to detect shared-state flakes.
6. Verify opt-in long-run diagnostics still run successfully when explicitly enabled.
7. Run frontend typecheck/build/tests and record their runtime.
8. Summarize before/after numbers and the top remaining slow tests in repository documentation or the PR.

## Out of scope

- Changing game rules to simplify testing.
- Removing expensive regression scenarios without equivalent fast coverage.
- Reducing worker verification requirements solely by skipping tests.
- General production performance optimization unrelated to the test harness.

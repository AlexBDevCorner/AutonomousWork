# MSS-125 - Fix Windows SQLite file sharing and pooled handles in save operations

## Goal

Fix Windows SQLite file sharing and pooled handles in save operations while preserving existing save data and unrelated behavior.

## Context

- Project: `mtgsolosports`; target: `AlexBDevCorner/MtgSoloSports`.
- Bug scan on 2026-11-03, audited [main revision 321eb36](https://github.com/AlexBDevCorner/MtgSoloSports/tree/321eb367316252ad259aea6b2fc66cc1ce08b6a1). Line numbers refer to that revision.
- On unmodified main, create and open a save, then call SaveStore.DeleteAsync. Windows throws IOException at SaveStore.cs:724 because File.Delete precedes ClearSaveConnections. A normal ExportAsync also fails at SaveBundle.ComputeFileSha256Hex:246: File.OpenRead requests FileShare.Read while pooled SQLite handles still allow writes. CreateCheckpointAsync fails in CopyAndVerifyDatabaseAsync for the same sharing conflict, blocking technical backups and schema migration checkpoints. These failures were reproduced with real production SaveStore methods on Windows, without a concurrently running application or active mutation.

## Potential damage if not fixed

On Windows, you may be unable to export, delete, replace or restore a save even after normal use. Automatic safety backups can also fail, which may prevent an older save from opening after an update. If a later problem damages your save, a failed backup leaves you with fewer ways to recover your progress. The reproduced failures stop these operations; they do not by themselves prove that existing progress has been deleted.

## Requirements

1. Make normal save export, checkpoint creation, deletion, explicit import overwrite and checkpoint replacement work on Windows after ordinary reads and writes have disposed their contexts. Audit both file sharing and pool lifetime; clearing a pool after deleting or replacing a file is too late.
2. Ensure active readers/writers cannot retain invalid handles or write into a removed/replaced database. Coordinate destructive save operations with the established per-save mutation boundary, using internal under-lock helpers where necessary to avoid reentrant deadlocks. Preserve concurrency for ordinary queries.
3. Preserve WAL state, existing overwrite checks, verified recovery copies, isolated save identities and RNG/rules. Do not suppress IOException or delete WAL files as a substitute for a correct snapshot.
4. Add Windows-focused regression coverage for create/open/delete, export/import round trip, checkpoint/restore and overwrite after ordinary pooled reads. Tests must exercise production operations without manually clearing pools before the action under test.

Inspect Persistence/Saves/SaveStore.cs:714-728, 751-783, 805-858, 873-904 and 1414-1453; SaveDbContextFactory.cs; and SaveBundle.cs:53,246. Keep the fix within existing save file orchestration.

# MSS-147 - Give the catalog database a real migration story

## Goal

The catalog database must survive `CatalogAthleteEntity` model changes on existing installs instead of failing at runtime with "no such column", and must stop paying a schema-creation roundtrip on every call.

## Context

- A repository review (2026-11-19) verified the following; re-verify on the live checkout.
- `src/MtgSoloSports/Persistence/Catalog/CatalogStore.cs:65,96,120,132` calls `EnsureCreatedAsync` on every operation. `EnsureCreated` is a no-op on an existing file, so the first entity model change makes every existing `catalog.db` fail at runtime with `no such column`, and every read pays a schema check.
- Saves get full EF Core migrations with checkpoint/rollback (`Persistence/Saves`); the catalog gets none, although a migrations workflow already exists in the solution.
- `Persistence/Catalog/CatalogDbContextFactory.cs:13-15` creates connections without the per-connection pragma interceptor; only the import connection sets `busy_timeout`/`foreign_keys` (`CatalogStore.cs:66`). Read connections run on SQLite defaults.
- The catalog is re-importable (Scryfall import feature exists: `Features/Catalog/ImportFromScryfall`), which bounds the blast radius but does not excuse a silent runtime break.

## Requirements

1. Choose and implement one explicit strategy: either EF Core migrations for `CatalogDbContext` (preferred, mirroring the save flow) or a persisted schema-version check that fails loudly with actionable rebuild guidance. No silent auto-recreate that destroys an existing catalog.
2. Apply schema initialization once (creation/migration path), not on every read; normal reads open a plain connection.
3. Give catalog connections the same per-connection pragma handling as saves (foreign_keys, busy_timeout) via the existing interceptor pattern; document why WAL settings (if any) differ from saves.
4. An existing catalog created by the current schema must keep working after the change without data loss; a model change made *after* this task must produce either a clean migration or a clear failure instructing re-import.
5. Import round-trip still works against a catalog created by the previous version (simulate by creating with the old schema shape or a version row, then exercising the chosen path).

## Architectural direction

- Schema migration and game-rule migration remain separate concepts (AGENTS.md); this task touches only schema. Follow the existing save-migration code style; no generic repositories, no new abstractions beyond what migrations need.

## Acceptance criteria

- [ ] Existing-catalog compatibility is proven by test: a catalog created before the change opens and serves reads/imports after it.
- [ ] No per-operation schema roundtrip: a normal read path issues no DDL (asserted in a handler test).
- [ ] The failure mode for an incompatible future catalog is loud and actionable (test the chosen guard).
- [ ] Catalog connections run with the documented pragmas.

## Verification

Standard AGENTS.md backend sequence: locked restore, Release build, full test suite, `dotnet format --verify-no-changes` (web checks unchanged). Add the focused catalog persistence tests above, running the relevant classes alone from a fresh process.

## Out of scope

- Catalog import logic/classification changes, save-database migrations, Scryfall API behavior, and any sporting outcomes.

# MSS-035 — Use wide-screen space and turn round reveal into a 32-card MTG board

## Goal

Make the desktop app feel at home on a wide monitor, and turn the live/historical round reveal into an enjoyable, image-first MTG card display. The key experience is seeing a full field of 32 **large, recognizable Magic cards** arranged like physical cards on a table (four rows of eight on a sufficiently wide screen), with sporting results attached to each card, rather than scanning tiny artwork in a long results table.

## Context

- Project: `mtgsolosports`; target repository: `AlexBDevCorner/MtgSoloSports`; default branch: `main`.
- User observation from a local wide-monitor run: the entire interface is a narrow centered column surrounded by large unused margins; the round reveal is especially tiny. The desired end state is a spacious, visual card collection/board reminiscent of laying real MTG cards out in childhood.
- Current implementation to inspect: `src/MtgSoloSports.Web/src/styles.css` has `.app { max-width: 1160px; ... }` and globally shared `.card-thumb { width: 40px; height: 40px; object-fit: cover; }`. The shared `RoundReveal` in `src/MtgSoloSports.Web/src/features/reveal/RoundReveal.tsx` renders a tiny spotlight, a full standings table, and a second reveal-feed table. It is used by live events and historical replay.
- Existing reveal presentation is driven by `useRoundReveal.ts` and `revealOrder.ts` over **immutable persisted round placements**. Animated reveal runs from lowest finisher to winner; `reveal.standings` already provides each athlete's progressive `currentRank`, `awardedThousandths`, `displayedScoreThousandths`, `rankDelta`, and `isRevealed`. Keep that behavior and arithmetic authoritative.
- Follow `AGENTS.md`, `docs/technical-design.md`, and `docs/game-rules.md`. Maintain the existing React/TypeScript feature organization and .NET vertical-slice modular monolith; direct `Endpoint -> Handler`, **no MediatR**.

## Requirements

1. **Use the available desktop width across the application.** Replace the narrow fixed `.app` layout with a responsive, substantially wider/near-fluid shell with comfortable edge gutters. On a 1920–2560px desktop, the topbar, navigation, Live event, Dashboard and other page content should visibly use most of the *usable* browser width rather than remaining in a ~1160px column. Keep naturally narrow content (forms, descriptive text, etc.) readable rather than blindly stretching every element. Preserve the existing dark aesthetic and avoid horizontal page overflow or broken navigation at smaller widths.
2. **Make a visual card grid the PRIMARY standings/reveal presentation**, replacing the always-visible standings table as the main focal point for both animated and instant modes. For a standard 32-athlete round on a sufficiently wide desktop, show **8 cards across × 4 rows**, ordered by the current progressive stage standings (rank 1 onward), with sensible spacing and the feel of physical cards laid out on a table. Use a distinct tile for each athlete with a stable React identity, and handle rounds with different athlete counts without empty, hard-coded 32-card assumptions.
3. **Make real card images the hero of each tile.** Display the existing MTG card image as a large, correctly proportioned portrait (approximately 5:7), preserving the **entire card** rather than cropping to a small art square. Don't stretch the artwork, and provide a visually consistent portrait fallback if the image is missing or fails to load. Card images should be large enough that the board looks like a collection of MTG cards rather than a spreadsheet with thumbnails.
4. Each tile must clearly show its current **rank**, athlete/card name (with a usable link/action to the existing athlete profile when available), plus the three existing sporting metrics: **AWARDED** (points from this round, or pending before reveal), **STAGE SCORE** (current progressive stage total), and **MOVE** (signed rank change; clear positive/negative/unchanged treatment). Place metrics in a compact but legible area attached to/below the card image; don't obscure the actual MTG artwork. Use the existing fixed-point formatting helpers and current progressive standings, not newly computed client sporting values. Long names, absent image data and varying metric widths must not break the tiles.
5. **Preserve the suspense of progressive reveal.** Unrevealed entries must be visibly pending (e.g. face-down/placeholder tiles) and must not prematurely expose current-round awards, final current-round ranking or the winner. As each athlete is revealed, visibly reveal/highlight their full-size card and update the board positions and attached metrics from the existing progressive standings. Keep the current latest-revealed spotlight if it genuinely adds drama, but upgrade it to a recognizable card-sized image and ensure it doesn't push the board out of focus. Minimize unnecessary animation and avoid jarring layout jumps.
6. **Adapt deliberately to viewport width.** The target 8×4 board applies when the container is wide enough for genuinely large cards; use fewer columns and appropriately sized cards on ordinary desktops/tablets/phones instead of squeezing eight tiny cards or relying on horizontal page scrolling. At narrower widths, controls must wrap gracefully and metric labels/numbers remain legible. Don't solve the issue by simply increasing the font size inside the existing narrow layout.
7. Preserve **all current replay controls and semantics**: instant/animated mode, lowest-to-winner reveal order, play/pause, replay/restart, step backward/forward, show all, speed, progress, athlete navigation and reduced-motion behavior. The grid must work for both live completed rounds and the History replay via the **shared** `RoundReveal` component. Keep full detailed result fields (base/bonus/final and rank transition) available in a secondary disclosure/details view or accessible table instead of losing information; avoid forcing users to scroll through two giant always-open tables below the visual board.
8. Maintain accessibility: visible keyboard focus and button labels, readable metric text and color-independent movement signs, appropriate accessible names/alt treatment for image/fallback, truthful progress announcements, and an accessible instant/minimal-motion experience for `prefers-reduced-motion`.
9. This is a **presentation-only** change. Refreshing, animating, changing speeds, stepping or replaying must continue to show immutable persisted results without simulation calls, RNG consumption, database mutations or changes to any sporting rules. Reuse existing data/formatting hooks and feature-scoped components/CSS; no new UI framework or broad frontend rewrite.

## Architectural direction

- Start with `src/MtgSoloSports.Web/src/styles.css` and the shared `RoundReveal.tsx`, extracting feature-scoped card-tile/grid styling or a small component as appropriate. Do not globally change `.card-thumb` dimensions and inadvertently blow up compact thumbnails in unrelated pages; create dedicated reveal-card image/tile styles.
- Drive tile identity and values from `reveal.standings` and `reveal.revealedFeed` as appropriate; carefully separate still-pending information from revealed results. Retain `useRoundReveal` as the owner of local playback state.
- Prefer CSS Grid with breakpoint/container-aware columns and responsive sizing; test actual wide-desktop proportions rather than only checking whether CSS compiles. An attractive 8×4 finished board and a readable in-progress reveal are both required.
- Avoid adding an image proxy, new card-data fetches, a design-system migration or backend schema changes for a frontend presentation problem. Preserve existing legitimate Scryfall image references and graceful fallback.

## Acceptance criteria

- [ ] At a 1920px-wide and a 2560px-wide desktop browser viewport, the application uses substantially more horizontal space than before, with comfortable margins, working navigation and no unrelated broken layouts.
- [ ] A 32-athlete reveal on a sufficiently wide desktop presents **exactly eight large card tiles per row, in four rows** when all 32 are shown; the full card portrait, name, rank, AWARDED, STAGE SCORE and MOVE are readable at ordinary browser zoom.
- [ ] The board is the dominant visual results view, not a list of 40px thumbnails or two always-open results tables. Full detailed round data remains discoverable without cluttering the main presentation.
- [ ] During an animated reveal, the latest athlete's real card image is prominent, revealed/pending states are obvious, unrevealed future results aren't spoiled and progressive ranks/scores/movement match the existing persisted presentation data.
- [ ] Instant/show-all mode displays all athletes and correct final values in the grid; play/pause, restart, step ±1, speed and progress remain correct and work on the new visual layout.
- [ ] The **same implementation** behaves correctly in Live event and History replay; selecting an athlete still opens the correct existing profile.
- [ ] A normal desktop, narrower tablet and phone viewport display sensible smaller-column layouts with readable metrics, no squashed card images and no horizontal page overflow.
- [ ] Missing/broken images, long names, fewer-than-32 placements, keyboard interaction and reduced-motion settings have graceful behavior.
- [ ] Automated tests cover reveal presentation state and any extracted pure display logic where practical. The PR includes before/after or after-only screenshots for wide desktop (including complete 32-card board and a partial reveal) and a narrow viewport, plus a short account of manual playback/replay checks.
- [ ] The full repository verification succeeds. No sporting logic, persistence or unrelated architecture changes.

## Out of scope

- No changes to scoring, reveal ordering rules, sporting simulation, database/save data or Scryfall catalog import.
- No new 3D tabletop engine, drag-and-drop collection manager, physical card physics, sound effects or AI commentary.
- No broad redesign of page-specific business features beyond making the shared application shell responsive and avoiding regressions.
- No unrelated component/framework migration or new server-side endpoints.

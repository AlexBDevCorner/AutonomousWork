# MSS-124 - Show a busy state and block conflicting interaction during stage completion

## Goal

Make background stage calculation clear to the user and prevent conflicting actions or navigation while it runs. Keep the UI protected until it has refreshed the authoritative result.

## Context

- Project: `mtgsolosports`.
- Target repository: `AlexBDevCorner/MtgSoloSports`.
- The user clicked **Complete stage 12 for all 25 leagues** on Dashboard. Calculation runs in the background, but the rest of the UI remains interactive. The user has avoided clicking elsewhere; no corrupted save or incorrect sporting result has been reported.
- In `src/MtgSoloSports.Web/src/features/dashboard/SeasonFlow.tsx`, `runNext` owns a local `running` flag. The triggering button is disabled and changes to **Completing…**, but the adjacent **Go to Live** link remains active.
- `DashboardPage.tsx` also renders `FastForwardSeason`, which has its own operation state. The shell and navigation do not receive the stage-completion busy state.
- `runNext` invokes the refresh callback and then clears its local flag. `useDashboard.ts` refreshes asynchronously and retains the last loaded data. Protect the refresh interval as well as the mutation request.
- MSS-074 already handles the final league-stage transition into postseason. Preserve that behavior.

## Requirements

1. Immediately show a clear, persistent busy message when Dashboard stage completion starts, such as **Completing stage 12 for all 25 leagues…**. Use a loading overlay or equivalent interaction guard consistent with the existing dark UI. An indeterminate indicator is sufficient; do not invent percentages, round counts or an ETA.
2. While the operation is pending, prevent repeat submission and conflicting actions for the active save. This includes fast-forward and other simulation controls, **Go to Live**, in-app navigation and switching saves. The guard must cover keyboard activation as well as pointer/touch input; a visual overlay alone is insufficient.
3. Keep the protection active through the authoritative progress/status refresh. Once refreshed data is available, remove the busy UI and render the correct next stage or postseason action. Do not briefly enable controls derived from the old snapshot.
4. Handle mutation failure and refresh failure explicitly. Show an actionable error and a recovery path without leaving an endless spinner or permanently locked interface. If the mutation succeeded but refresh failed, retry must reload state rather than submit the completed stage again. For an interrupted request with an uncertain outcome, recheck authoritative state before enabling another mutation.
5. Keep operation ownership stable for its lifetime. Navigation must not dismiss the guard while work is still pending. Account for the existing router's Back/Forward behavior without claiming that closing/reloading the browser cancels server work. After a browser reload, load authoritative state normally.
6. Make the busy message accessible to assistive technology. Keep focus away from disabled background controls and restore useful focus when work finishes or recovery becomes available. Respect reduced motion and narrow viewports.
7. Add focused behavioral tests with deferred promises for both calculation and refresh. Cover rapid repeated activation, conflicting controls/navigation, keyboard interaction, successful completion, request failure and refresh-only retry.

## Architectural direction

- Start with `features/dashboard/SeasonFlow.tsx`, `DashboardPage.tsx`, `useDashboard.ts` and `FastForwardSeason.tsx` under `src/MtgSoloSports.Web/src/`.
- Inspect `features/shell/`, `features/routing/router.tsx`, existing loading/notice components and the MSS-074 dashboard tests before choosing where the busy state belongs.
- Use the smallest shared state boundary needed to protect Dashboard and its enclosing save navigation. Reuse existing components, CSS and native browser behavior. Avoid introducing a generic operation framework or a UI dependency.
- Scope this task to Dashboard stage completion and the controls/navigation that can conflict with it. Other long-running workflows only need changes where required to respect this guard.
- Keep backend simulation, persisted results and RNG behavior unchanged. This is local single-user UX protection, not a cross-tab or distributed locking project.

## Acceptance criteria

- [ ] Clicking **Complete stage N for all L leagues** immediately displays a visible, accessible busy state.
- [ ] During a deliberately delayed request, repeated activation sends one mutation, and conflicting controls, navigation and save switching cannot execute through pointer or keyboard input.
- [ ] Resolving the mutation while delaying refresh keeps the interaction guard active; stale stage controls do not become actionable.
- [ ] Successful refresh removes the guard and shows authoritative next-stage/postseason state, including completion of stage 32.
- [ ] A failed request provides usable recovery. A failed refresh after a successful mutation retries reads without repeating the mutation.
- [ ] The guard cannot be dismissed by normal in-app navigation or Back/Forward while the operation is pending, and it does not leave the app stuck after completion or error recovery.
- [ ] Desktop and narrow layouts remain usable, focus is handled correctly, and reduced-motion users receive a clear loading state.
- [ ] Focused frontend behavior tests and required repository checks pass.

## Out of scope

- Changes to simulation rules, sporting results, RNG, persistence or backend API contracts.
- Server-side job infrastructure, cross-tab locking, polling/progress endpoints or cancellation.
- A redesign of Dashboard, the shell or all application loading states.
- Retrofitting every Cup, Live or other long-running workflow with a new operation system.
- Implementing this task as part of its creation or promoting it to `ready`.

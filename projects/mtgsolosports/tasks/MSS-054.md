# MSS-054 — Restore near-instant athlete profile loading and make it scale with long saves

## Goal

Restore the athlete profile experience to near-instant loading and keep it fast as a save accumulates many seasons, Cup events, stories, records, and historical rounds.

The fix must address the current architectural cause of the regression rather than only hiding it with a spinner or adding speculative indexes. In particular, opening one athlete must no longer trigger the expensive **global Records calculation for the entire save**, and secondary profile sections must not block rendering of the core athlete profile.

The result should have bounded, athlete-focused read work for the athlete page and should remain responsive on long-running saves.

## Context

- Project: `mtgsolosports`; target repository: `AlexBDevCorner/MtgSoloSports`; default branch: `main`.
- Athlete profiles used to feel effectively instant, but now have a noticeable delay after recent history/records additions.
- Current frontend path in `src/MtgSoloSports.Web/src/features/athletes/useAthleteProfile.ts` performs these reads sequentially:
  1. `fetchAthleteProfile(...)`;
  2. `fetchAthleteStories(...)`;
  3. `fetchRecords(...)`;
  4. only then sets the profile page to loaded.
- The athlete page uses the full Records response only to compute career record holdings with:
  `records.records.filter(record => record.holders.some(holder => holder.athleteId === athleteId))`.
- The general Records endpoint is much more expensive than that requirement. `GetRecordsHandler` loads global career-record inputs and scoring-record inputs for the whole save. The scoring path reads historical round/Cup/qualifier/team-round data and decodes persisted payloads.
- The athlete page does **not** need the global scoring-record calculation just to show which career records this athlete holds.
- The core athlete profile itself already uses projections such as `AthleteCareers` and `AthleteSeasonSummaries`, which is the right general direction for read performance.
- Existing athlete-oriented indexes are already present on many projection/Cup tables. Do not assume that adding indexes alone fixes the regression.
- Two smaller query-shape opportunities are visible in the current model:
  - `Movements` is filtered by `SaveAthleteId` on the profile path but has no athlete-leading index.
  - athlete stories use `WHERE SaveAthleteId = ? ORDER BY Id DESC LIMIT ...`; the current simple `SaveAthleteId` index may be improved by a composite athlete/id index if the SQLite query plan shows benefit.
- Some secondary endpoints call `SaveStore.EnsureMigratedAsync`, which checks pending migrations for the save. Treat repeated migration checks as a possible secondary cost to measure, not as the assumed primary cause.
- Follow `AGENTS.md`, the existing vertical-slice architecture, direct Endpoint → Handler pattern, EF Core/SQLite conventions, and current frontend routing/state conventions.

## Requirements

1. **Remove the full global Records endpoint from the athlete profile loading path.**
   - Opening an athlete profile MUST NOT call `GET /api/saves/{saveId}/records`.
   - Athlete-profile rendering MUST NOT invoke `GetRecordsHandler`, `ScoreRecordLoader`, or any equivalent whole-save scoring-record calculation.
   - Opening an athlete MUST NOT decode historical round/Cup/qualifier/team-round payloads merely to determine that athlete's career record holdings.

2. Add an athlete-focused way to retrieve the record information actually needed by the profile.
   - A dedicated endpoint such as `GET /api/saves/{saveId}/athletes/{athleteId}/record-holdings` is acceptable.
   - Including a small record-holdings projection in the existing profile response is also acceptable if it keeps the core profile query fast and the ownership boundary clean.
   - Return only the information needed by the athlete profile, not the complete Records page response.

3. The athlete-specific record-holdings implementation must scale with save history.
   - Do not load all normalized historical rows into memory and then run the existing global record calculator only to filter one athlete.
   - Prefer narrow SQL aggregates, existing projections, or a small persisted/read-optimized record projection.
   - If introducing a persisted projection/read model is the cleanest solution, it must be updated from authoritative sporting state and remain deterministic/rebuildable.
   - A solution that merely moves the current global `fetchRecords` call to another endpoint is not acceptable.

4. Preserve the current career-record semantics exactly.
   - If multiple athletes tie a record, all tied holders must remain valid.
   - The athlete page must show the same career record holdings that the existing Records page considers authoritative.
   - Do not change record definitions, scoring rules, tie rules, or historical sporting data.

5. Decouple **core profile readiness** from secondary sections.
   - The athlete identity/card, career summary, season history, honours, movement history, Cup selections/history, and other data already returned by the core athlete profile endpoint should render as soon as that request succeeds.
   - Stories and record holdings must not keep the entire page in the global loading state.
   - A slow or failed stories/record-holdings request must not make an otherwise valid athlete profile appear unavailable.

6. Load independent secondary sections concurrently where practical.
   - Do not keep the current strict `profile -> stories -> records` waterfall.
   - Stories and athlete-specific record holdings should begin without waiting for one another once save/athlete identity is known.
   - Preserve abort/cancellation behaviour when navigating between athletes.

7. Give secondary sections their own deliberate loading/error behaviour.
   - Avoid replacing the current delay with layout jank or a page-wide spinner.
   - The main athlete page should become usable while stories/record holdings are still resolving.
   - A failure in a non-critical secondary section may degrade that section gracefully without discarding the loaded profile.

8. Profile the **core athlete endpoint** after removing the global Records dependency and optimize any remaining material bottlenecks.
   - Inspect generated SQL/query plans for the athlete profile against a long-running save.
   - Do not blindly merge everything into one giant EF `Include` graph or cartesian join.
   - Prefer narrow projections and a small number of predictable indexed queries.

9. Add/adjust indexes that are justified by the actual athlete query shapes.
   - Add an athlete-leading index for `Movements` appropriate for the current profile query, e.g. beginning with `SaveAthleteId` and supporting its ordering/filter shape.
   - Evaluate `StoryEvents (SaveAthleteId, Id)` for the newest-N athlete story query and add it if the SQLite plan benefits.
   - Review athlete-leading indexes used by Cup history/honours/profile reads and add only missing indexes that materially improve those paths.
   - Add indexes through the normal EF migration/model configuration path.
   - Avoid duplicate/redundant indexes where an existing composite index already covers the query prefix.

10. Reduce avoidable profile-query work where safe.
    - Examples worth evaluating include:
      - replacing full-season-id materialization in projection completeness checks with cheaper SQL existence/count logic;
      - avoiding loading complete Season/League dictionaries when only the movement rows' referenced values are needed;
      - avoiding repeated reads of the same athlete/Cup/team data within one profile request;
      - selecting only columns required for DTO mapping.
    - These are optimization candidates, not permission to change sporting behaviour or corruption checks.

11. Investigate repeated `EnsureMigratedAsync` calls on read-only secondary endpoints.
    - Measure whether pending-migration checks contribute meaningfully to athlete-page latency.
    - If they do, eliminate redundant checks with a safe design, for example a per-save/current-schema migration-verified state or a single well-defined migration boundary when a save is opened.
    - Any optimization MUST still correctly migrate an old save before a handler relies on the new schema.
    - Do not trade correctness/recoverability for a small latency win.

12. Preserve old-save compatibility and fallback behaviour.
    - Athlete projection fallback for saves created before the projections existed must continue to work.
    - Schema migrations must remain safe and idempotent.
    - The optimization must not require deleting/recreating existing saves.

13. Add regression tests that protect the new performance architecture.
    - Frontend tests must prove the page no longer waits for stories/record holdings before exposing the successfully loaded core profile.
    - Frontend/API tests must prove the athlete page no longer requests the global `/records` endpoint.
    - Backend tests must prove athlete-specific record holdings match existing career-record semantics, including ties.
    - Add a test/guard that the athlete record-holdings path does not read/decode scoring round payloads or invoke the scoring-record loader.
    - Add migration/index tests where the project convention supports them.

14. Add lightweight performance verification for a long-running save.
    - Use a representative save with many seasons/events or generate equivalent fixture data.
    - Compare before/after request timings for:
      - core athlete profile;
      - stories;
      - athlete record holdings;
      - overall time until the core profile becomes usable.
    - Prefer query count / rows read / endpoint timing evidence over fragile hard CI millisecond thresholds.
    - Record the measurements in the PR description or a small evidence document consistent with existing project practice.

15. Keep the global Records page functional.
    - This task is not permission to remove detailed scoring records or reduce information available on the Records page.
    - Shared lower-level logic may be refactored if useful, but the Records page must preserve its existing outputs.

## Architectural direction

Treat this as a **read-path redesign**, not a cosmetic loading-state fix.

### A. Separate the athlete page into critical and secondary reads

The core profile request should be the critical path. Once it succeeds, render the athlete page.

Stories and record holdings are separate read concerns and should have their own state. A reasonable frontend shape is:

- core profile: blocking only for the initial athlete shell/content;
- stories: independent secondary query;
- record holdings: independent secondary query.

Do not create a single `Promise.all` whose completion still gates the whole page. Parallel requests are good, but the page must become usable when the critical request finishes.

### B. Create an athlete-specific career-record read path

The current anti-pattern is:

`athlete page -> global /records -> load whole save -> calculate all career records + all scoring records -> filter to one athlete`

Replace it with something conceptually like:

`athlete page -> athlete record-holdings read model/query -> small response`

Possible good implementations include:

1. **SQL aggregate/query approach**
   - Query the athlete's relevant projected values.
   - Query only the aggregate maxima/minima needed for the defined career record keys.
   - Return the keys where the athlete matches the authoritative record value.
   - Use normalized/projection tables, not decoded round payloads.

2. **Persisted career-record projection**
   - Maintain current career record values/holders as derived read data when authoritative sporting state changes.
   - Athlete lookup becomes an indexed holder query.
   - The projection must be deterministic, rebuildable, and covered by tests.

Choose the approach that best fits the existing codebase and write frequency, but MUST avoid whole-save historical replay/decompression on profile reads.

Do not mix the newer detailed **scoring records** into athlete-profile record holdings unless the UI explicitly starts displaying those records in a future task. This task should not expand the athlete page's feature scope.

### C. Optimize the existing core profile after the major fix

The profile handler currently performs several small sequential EF queries. That is acceptable if they are narrow and indexed; SQLite does not benefit from forcing unrelated collections into a huge join.

Use actual SQL/query-plan evidence before consolidating queries. Focus on:
- athlete-leading indexes;
- avoiding full-table/dictionary reads where targeted joins/projections are simpler;
- removing duplicate reads;
- preserving `AsNoTracking()`;
- projecting only columns that are consumed.

### D. Keep projection updates on the write side where appropriate

If the chosen solution adds a record-holdings projection, update it when sporting state changes rather than rebuilding it when a user opens a profile. Reads should stay cheap as history grows.

This follows the existing successful pattern of `AthleteCareers` and `AthleteSeasonSummaries`.

## Acceptance criteria

- [ ] Opening an athlete profile no longer calls the global `/api/saves/{saveId}/records` endpoint.
- [ ] Opening an athlete profile does not invoke `GetRecordsHandler` or `ScoreRecordLoader`.
- [ ] Opening an athlete profile does not decode round/Cup/qualifier/team-round payloads for record holdings.
- [ ] The core athlete profile becomes visible/usable as soon as its own request succeeds, without waiting for stories or record holdings.
- [ ] Stories and record holdings load independently and do not share the page-wide loading state.
- [ ] Failure of stories does not discard a successfully loaded athlete profile.
- [ ] Failure of record holdings does not discard a successfully loaded athlete profile.
- [ ] Athlete-specific career record holdings match the authoritative Records-page career record results.
- [ ] Tied record holders are handled correctly.
- [ ] Athlete record-holdings work scales using targeted aggregates/projections rather than materializing whole-save history.
- [ ] Existing detailed/scoring Records page functionality remains unchanged.
- [ ] `Movements` has an athlete-leading index appropriate for the profile query.
- [ ] Athlete-story indexing is reviewed and improved if the query plan shows a benefit.
- [ ] No redundant index is added where an existing index already covers the query.
- [ ] Projection fallback/old-save compatibility still works.
- [ ] Existing save databases migrate safely without recreation.
- [ ] Frontend tests protect non-blocking profile rendering and removal of the global Records request.
- [ ] Backend tests protect athlete-specific record semantics and prove the scoring-record payload path is not used.
- [ ] Before/after evidence demonstrates that the expensive whole-save Records calculation is no longer on the athlete-page critical path.
- [ ] A long-running save with substantial historical data still produces a responsive athlete profile without latency growing in proportion to all historical round payloads.

1. Run the standard backend build/test commands from `AGENTS.md`.
2. Run the standard frontend typecheck/test/build commands from `AGENTS.md`.
3. Use browser dev tools on an athlete profile and verify there is **no** request to `/records`.
4. Verify the core athlete content renders before deliberately slowed stories/record-holdings responses complete.
5. Deliberately fail the stories request and verify the athlete profile remains usable.
6. Deliberately fail the record-holdings request and verify the athlete profile remains usable.
7. Open an athlete known to hold a career record and compare profile holdings with the Records page.
8. Verify an athlete tied with another athlete for a record is still shown as a holder.
9. Exercise a save with many seasons and Cup events; capture endpoint timings/query evidence before and after.
10. Verify the athlete record-holdings request does not query/decode league/Cup/qualifier/team round payloads.
11. Inspect SQLite `EXPLAIN QUERY PLAN` (or equivalent EF/SQLite diagnostics) for:
    - athlete movements;
    - newest athlete stories;
    - Cup/profile history queries;
    and verify the intended indexes are used.
12. Open an older save that requires migration and confirm it still migrates successfully and the profile loads.
13. Reopen an already-current save repeatedly and verify no unnecessary migration-related regression remains on the hot read path.
14. Verify the global Records page still shows career records, scoring records, and record history correctly.

## Out of scope

- Changing sporting rules, scoring, promotion/relegation, Cup rules, RNG, or simulation outcomes.
- Removing or simplifying detailed scoring records from the global Records page.
- Adding new categories of records to the athlete profile.
- Rewriting the entire persistence layer or replacing SQLite.
- Introducing distributed caching, Redis, or external infrastructure for a local per-save read-performance problem.
- Hiding latency with longer animations/spinners instead of reducing the work.
- Broad unrelated frontend redesign of the athlete profile.

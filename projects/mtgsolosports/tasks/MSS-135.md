# MSS-135 - Add the manual chat journalist workflow and persistent stage article archive

## Goal

Make "Write the latest Superleague stage review" a documented, repeatable local agent workflow that fetches fresh evidence, writes an article in chat, saves it with its sources and preserves editorial continuity across chats, without scheduled automation or an AI integration inside the game.

## Context

- Project: `mtgsolosports`; target: `AlexBDevCorner/MtgSoloSports`, branch `main`.
- The user will initiate every review by writing in chat after a Superleague stage. The agent uses MSS-133 for one verified snapshot and MSS-134 for stage evidence and historical investigation.
- The intended article covers the stage's rounds, standout performances and championship consequences, connected to previous coverage and prior seasons where supported.
- The game remains the authoritative source for results. Saved articles and short editorial notes preserve prior interpretations, predictions and ongoing storylines; they are not a replacement for querying the evidence.
- Deliver repository-owned instructions/templates/helpers. Do not install skills globally, create real user chats/projects, provision account connections or invoke a paid model service from application code.

## Requirements

1. Provide a self-contained journalist workflow guide/instruction file and a local workspace template. Explain how to start a local agent chat with access to the helper and archive, configure the loopback game URL and explicit save ID once, and request an article. Use the existing helper from the first request; no manual bundle export/upload or recurring job should be required.
2. Define the default request as the latest completed Superleague stage, including all its rounds and awarded championship points. Also document an explicit historical request. Style, article length and emphasis are simple local preferences; do not invent a new settings framework or prescribe a specific subscription/model.
3. Specify the per-request sequence: acquire a fresh snapshot, resolve and state the exact target, obtain stage evidence, read relevant prior coverage, investigate selected questions on the same snapshot, write/check the article, show it in chat, then save article/evidence metadata and update continuity notes. On acquisition failure, report the problem; offline use requires explicit selection and disclosure of snapshot freshness.
4. Use a save-ID/season/stage archive identity, with a readable directory layout, article Markdown, compact source facts/metadata and a season notebook/index. Store snapshot fingerprint, covered cutoff, source/evidence format versions and generation metadata so the article's factual basis remains identifiable after the working database is refreshed.
5. Provide the minimal deterministic archive/context helper needed to find earlier coverage and commit an article with matching evidence metadata. Constrain writes to the configured archive; reject target/evidence identity mismatches. Do not overwrite another save's article or notebook, existing human edits, or a prior draft silently. A repeated request for the same stage must be an explicit revision, with the prior text recoverable.
6. Read bounded relevant context by default, such as recent stage reviews and the season notebook. Use targeted lookups for older seasons/athletes; do not load the full archive for every request. For historical reviews, exclude later articles and notebook entries that reveal later outcomes. Make dated/scoped entries or build the context from earlier eligible coverage instead of trusting a current unscoped season summary.
7. Keep factual results separate from editorial interpretation and speculation. Prior predictions can be revisited as prior predictions; they must not become asserted facts. Require checking scores/gaps/titles and scoped first/best/record claims against MSS-134 evidence. Do not invent interviews, quotations, injuries, motives or incidents absent from source data.
8. Address missing prior coverage, missed stages, first review of an established save and new seasons. Default to the requested/latest stage and disclose gaps, rather than automatically creating reviews for every uncovered stage. A new chat must be able to reconstruct continuity from the files without relying on another chat's transcript.
9. Define behavior when the game advances after acquisition, or a save is restored/replayed: retain the original article cutoff/snapshot provenance and detect conflicting evidence for an existing save/season/stage. Do not merge incompatible timelines silently. Require a deliberate new revision/archive choice and preserve earlier text and provenance.
10. Keep articles/evidence/notebooks as durable user-owned local files; working snapshots/cache remain replaceable and generated data stays untracked by default. Preserve human article edits in subsequent context. Do not automatically create one full database copy per article, push user data to GitHub or publish elsewhere.
11. Document exactly what local access is needed for download, read-only database queries and writable article output. Keep existing sandbox/approval boundaries intact; do not promise no approvals on every host or broaden global permissions. The normal path needs no Docker administration, new service, Drive connection or game-container change.
12. Include executable PowerShell one-liners, example initial and follow-up chat prompts, an example directory layout and a concise operator troubleshooting guide. Provide a clearly labeled illustrative article/evidence example from a small test fixture; do not present fixture content as reporting on the user's real save.
13. Add focused checks for archive identity, source matching, safe repeat/revision behavior and preservation of manual edits, save/season isolation, future-context exclusion and restored-history conflicts. Perform a documented end-to-end rehearsal of two stage requests plus a revision and an explicit historical request. No paid model or real account credentials may be required by CI.

## Architectural direction

Keep deterministic acquisition/query/archive operations in the existing small helper. The agent does the editorial writing through chat; avoid an in-app "generate article" feature, model API calls or a rigid prose generator. Use ordinary Markdown and a small versioned metadata format for user-owned files. A repository-local journalist guide/workspace instruction is sufficient; an optional skill must remain repository-owned and must not modify global agent configuration. Reuse existing docs/report conventions and link the new workflow from the appropriate README/report documentation.

## Acceptance criteria

- [ ] The guide and template let a new local agent chat execute "Write the latest Superleague stage review" with one-time save configuration.
- [ ] The agent can acquire evidence, return an article in chat and save it with exact save/season/stage provenance and a bounded continuity update.
- [ ] The next review and a fresh chat use earlier saved coverage; historical requests exclude future editorial context and later sporting outcomes.
- [ ] Revisions, manual edits and changed/restored history preserve prior content and cannot silently mix saves, stages or incompatible evidence.
- [ ] First-use, missed-stage, season-transition, offline and unavailable-app behavior are documented.
- [ ] Focused helper tests and the two-stage/revision/historical rehearsal are recorded; examples are clearly identified as fixture examples.
- [ ] No scheduler, model-service integration, global configuration edits, Drive changes or external publication is introduced.

## Verification

Run focused archive/context tests and MSS-133/MSS-134 integration checks, then relevant target AGENTS.md quality gates. Record exact commands and completed results. With generated test data, acquire a first completed stage and archive an illustrative review; advance to another stage and verify retrieved context includes the earlier edited article; revise explicitly and confirm recovery of prior text. Run an earlier historical request and inspect every supplied context file for future-outcome leakage. Test two saves with identical names, absent prior articles, season rollover, unavailable app and conflicting evidence after restore. Document the human chat rehearsal separately from deterministic test assertions; do not claim subjective writing quality was established by an automated test.

## Out of scope

- Scheduled/automatic article generation, automation setup, notifications or background monitoring.
- Embedding an LLM/model API in the game, subscription/usage optimization, new UI or editorial publishing platform.
- Google Drive changes, automatic cloud uploads, GitHub publication of articles or modifying other backlog tasks.
- Simulation/rule changes, importing/restoring saves, forensic reconstruction of missing historical data or global Codex settings/skill installation.

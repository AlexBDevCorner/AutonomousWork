# MSS-126 - Prevent exports and recovery checkpoints from omitting committed WAL data

## Goal

Prevent exports and recovery checkpoints from omitting committed WAL data while preserving existing save data and unrelated behavior.

## Context

- Project: `mtgsolosports`; target: `AlexBDevCorner/MtgSoloSports`.
- Bug scan on 2026-11-03, audited [main revision 321eb36](https://github.com/AlexBDevCorner/MtgSoloSports/tree/321eb367316252ad259aea6b2fc66cc1ce08b6a1). Line numbers refer to that revision.
- SaveStore.CheckpointWalAsync at line 1275 executes PRAGMA wal_checkpoint(TRUNCATE) through ExecuteSqlRawAsync and ignores SQLite's result row. A busy checkpoint can return normally without copying all committed frames. ExportAsync then reads live metadata, hashes the main database and zips that file in separate unsynchronized steps. Reproduction: checkpoint a save named Before; hold a deferred read transaction after selecting Before; on another connection commit Name=After; export while that reader remains open. The manifest says After, but the embedded save.db says Before. This was reproduced after diagnostic-only changes in an isolated copy disabled pooling and permitted shared file reads, removing MSS-125's earlier Windows failure. The snapshot algorithm itself was unchanged. The diagnostic edits were then reverted. The same ignored-checkpoint/raw-copy path is used by technical checkpoints.

## Potential damage if not fixed

A backup can appear to succeed while leaving out progress that the game has already saved. Restoring that backup or moving it to another computer could take you back to an older state and lose newer results. Its description can even show a newer state than the data inside it, so you may not notice the missing progress until you need the backup. If it is your only remaining copy, that progress may be unrecoverable.

## Requirements

1. Build export and recovery checkpoint artifacts from one consistent committed database snapshot. Embedded database, checksum, manifest and checkpoint sidecar must describe that same snapshot.
2. Treat a busy or incomplete WAL checkpoint explicitly. Use an appropriate SQLite snapshot/backup mechanism or verify checkpoint completion and fail safely; never silently publish a main-file copy that omits committed frames.
3. Coordinate snapshot capture with simulation writes and other save-file operations. Preserve lock ordering because checkpoint creation is also invoked from already-locked bulk/migration paths. Do not hold a global lock across unrelated saves.
4. Add a deterministic regression with a pinned WAL reader, a later committed write, and an attempted export/checkpoint. An exported artifact must include the documented committed boundary or fail explicitly without emitting a success artifact. Add coverage for a mutation interleaving metadata/hash/copy.

## Architectural direction

Inspect SaveStore.cs:751-783, 873-904, 943-1010, 1275-1279 and Persistence/Saves/SaveBundle.cs. Preserve existing portability format and immutable sporting data. A more permissive FileStream share mode alone fixes neither this bug nor concurrent-copy integrity. Follow target AGENTS.md and docs/testing.md; direct vertical slices, deterministic sporting math, no MediatR.

## Acceptance criteria

- [ ] Pinned-reader regression cannot return a successful stale export with a newer manifest.
- [ ] Checksum, embedded database and manifest/sidecar match one snapshot.
- [ ] Concurrent simulation/export/checkpoint remains consistent and resumable.
- [ ] A failed capture leaves live data and prior verified checkpoints intact.

## Verification

Add focused SQLite integration tests, then run SaveExportImportTests and SaveCheckpointTests plus required backend checks. Validate both Windows and Linux. Reproduction uses only a fresh universe and a metadata update; no full-season setup is needed.

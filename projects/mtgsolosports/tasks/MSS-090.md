# MSS-090 — Optionally auto-publish season reports after completed stages

## Goal

Remove the need to click Publish after each completed stage by offering **opt-in automatic Google Drive publishing** of the current season dossier and universe almanac. Reports should eventually reflect every committed sporting checkpoint without allowing Google/network problems to affect the game.

## Context

- Project `mtgsolosports`, target `AlexBDevCorner/MtgSoloSports` (`main`).
- Depends on completed MSS-089 (Google account authorization, Drive destination mapping, idempotent `Publish now` for current dossier/almanac). Reuse its publisher; do not create a second upload implementation or OAuth model.
- MtgSoloSports supports stage-by-stage simulation as well as fast/bulk simulation. A completed **global stage** should publish once from durable, committed results, not once per round or once per individual feeder league. Some commands can simulate multiple stages or seasons at once.
- App runs locally, sometimes inside Docker; automatic sync works only while the app is running and authorized. A failed/offline upload must not fail, roll back or delay sporting progression.

## Requirements

1. Add an **Automatically publish after each completed stage** toggle, **off by default**, on Reports/Drive settings. Display linked account/destination and last successful published season, stage and state.
2. Trigger based on a durable **completed global stage or equivalent finalized event/save-state boundary**, after the simulation commit. Detect completion irrespective of command path: interactive progress, complete-stage-for-all-leagues, and bulk/fast simulation. Avoid false triggers for a completed round, partial league-stage or still-rolling transaction.
3. Enqueue a bounded publish request for the current season dossier and almanac through the MSS-089 publisher; never make network calls inside simulation transactions or wait for Google Drive before responding to a completed sporting command.
4. Coalesce burst requests (e.g. bulk simulation of dozens of stages) so the most recent durable state is eventually published, not dozens of stale versions. Serialize publishes per save/destination, and prevent racing uploads from overwriting a newer state with an older report.
5. Track requested vs successfully published checkpoint/fingerprint in application-level persistent settings, **outside the save SQLite sporting data**. On app restart or reconnect, detect pending changes and offer retry/automatic catch-up; never silently imply success when offline or credentials are expired. Do not schedule polling or uploads for disconnected/disabled saves.
6. Retry transient failures with capped backoff and clear status; permanent auth/permission errors pause publishing and prompt reconnect/reconfiguration. Preserve manual `Publish now` as an override/retry action and allow cancellation/disabling automatic mode without deleting uploaded files.
7. Show simple UI statuses: `Up to date`, `Publishing`, `Pending`, `Failed`, `Disconnected` and the latest successfully synced season/stage. Keep status accurate across route reload/container restart; never show a green success status for an unsuccessful upload.
8. Handle new season creation: create a new season dossier with its new stable filename; retain previous-season docs and update the almanac. Handle transitions around qualifiers/Cups/season finalization without marking unfinished data as official. Do not publish an older season to the filename of a newer one.
9. Keep publication isolated by save and destination; no cross-save content leaks. Monitor/report failures without leaking OAuth tokens or full report content to logs. No unexpected new Google permissions.
10. Add deterministic tests for event detection, duplicate events, task coalescing, manual vs auto race, bulk simulation, restart recovery, disabled toggle, expired credentials and stage checkpoint consistency.

## Architectural direction

- Build a minimal post-commit notification/outbox or durable checkpoint observer appropriate to the existing single-process local app; not a distributed job platform. The job observes immutable persisted sporting boundaries and uses the existing Reports publisher.
- Prefer publishing latest stable snapshot over building snapshots in the simulation mutation path. Ensure at-least-once requests with idempotent Drive writes rather than exactly-once illusions.
- Limit concurrent network operations; keep cancellation and bounded retry discipline. Publishing is an optional side effect of read-only report generation, never part of sporting correctness.

## Acceptance criteria

- [ ] When auto mode is enabled, finishing global Stage N eventually updates the existing current-season report and almanac without a button click.
- [ ] When disabled or disconnected, no automatic uploads occur.
- [ ] Simulation can complete normally with network offline, slow or unauthorized; checkpoint stays pending/failed and user can retry.
- [ ] Multiple rounds, partial stages, repeated notifications and bulk stage simulation do not create duplicate Drive files or stale overwrites.
- [ ] New seasons create appropriately named dossiers and preserve historical files.
- [ ] Restart/reconnect can reconcile an unpublished committed checkpoint; UI status reflects truth.
- [ ] Tests cover event triggers/coalescing/status and ensure save/RNG/scoring remain untouched.

## Verification

Run all required backend/frontend gates from `AGENTS.md`. Verify manually with mock Drive: complete one round, one feeder stage, a global stage; simulate multiple stages rapidly; switch off auto mode; disconnect account; simulate offline; restart; reconnect; and confirm exact destination file ID/count and newest stage metadata. Manual `Publish now` must continue to work.

## Out of scope

- Continuous real-time sync during rounds or sub-stage progress.
- Uploading an entire historical archive after every completed stage.
- Cup/team and broad historical export catalog publishing (MSS-091).
- Google Cloud hosted workers, permanent background processing when MtgSoloSports is shut down, ChatGPT Project file synchronization or any changes to scoring/simulation.

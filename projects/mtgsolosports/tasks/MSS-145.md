# MSS-145 - Make save deletion safe and surface failed or damaged saves in the UI

## Goal

Deleting a save must require explicit confirmation and every failure must be visible to the user; a save that exists on disk but cannot be read must appear as a damaged entry rather than silently vanishing from the list.

## Context

- A repository review (2026-11-19) verified the following; re-verify on the live checkout.
- `src/MtgSoloSports.Web/src/features/saves/SavesPage.tsx:151-169`: one click on Delete irreversibly destroys an entire universe with no confirmation step.
- `src/MtgSoloSports.Web/src/features/saves/useSaves.ts:51-59`: `remove` has no catch; the caller's `.catch(() => {})` swallows the rejection. The comment claiming "list refresh surfaces failures" is false - no refresh happens. A 500/409 leaves the row intact with zero user feedback.
- `src/MtgSoloSports.Web/src/features/saves/savesApi.ts:73-79`: `deleteSave` throws a plain `Error`, losing the status code that `ApiError`/`apiErrorMessage` are designed to surface (`importSave` right below does it correctly).
- `src/MtgSoloSports/Persistence/Saves/SaveStore.cs:738-741`: `ListAsync` logs and silently drops unreadable saves, so a broken save disappears from the UI with only a server log.
- The codebase already has a two-step confirm pattern to reuse (`confirmEntire` in `features/live/LiveEventView.tsx`).
- Frontend tests exist colocated (`features/saves/*.test.ts`) using `node --test` + mounted-component tests; there is currently no error-path coverage for deletion.

## Requirements

1. Add a two-step confirmation for save deletion (reusing the existing confirm pattern and styling; accessible, keyboard-operable).
2. Surface delete failures: `deleteSave` throws `ApiError` (status + message), the hook exposes an error state, the page shows the error via the existing error styling and refreshes the list so the true state is visible.
3. `ListSaves` returns damaged saves as explicit placeholder entries (name/id marked unreadable with a short reason), not silent omissions; keep logging. Do not attempt repair - AGENTS.md forbids silent repair; the entry just has to be visible with the option to delete or restore a checkpoint if one exists.
4. The Saves page renders damaged entries distinctly (no open action; delete/restore offered as applicable) without a page redesign.
5. Preserve current happy-path behavior and styling; no new dependencies.

## Architectural direction

- Backend change stays inside `Features/Saves/ListSaves` + `Persistence/Saves/SaveStore.ListAsync` (contract gains an optional unreadable flag/reason field, keeping existing fields stable). Frontend changes stay inside `features/saves`. Follow AGENTS.md: animation-only state stays in React; no sporting state is touched.

## Acceptance criteria

- [ ] Deleting a save requires confirmation; cancelling keeps the save.
- [ ] A failing delete (409/500) shows the error message and the list reflects the true state afterward.
- [ ] An unreadable save file appears as a damaged entry with reason, and does not disappear.
- [ ] Colocated frontend tests cover confirm gating, failed-delete error state, and damaged-entry rendering; a backend test covers the damaged placeholder contract through the real pipeline.

## Verification

Standard AGENTS.md sequence: locked restore, Release build, full backend suite, `dotnet format --verify-no-changes`, web `npm ci`, `test`, `typecheck`, `build`. Add the new focused tests listed above.

## Out of scope

- Checkpoint creation/restore mechanics, save repair, migration changes, redesign of the saves page beyond the listed states, and any sporting behavior.

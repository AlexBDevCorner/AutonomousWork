# MSS-122 - Reduce backend test runtime through reusable setup and establish enforceable testing guidance

## Goal

Implement a substantial reduction in normal backend test runtime by eliminating repeated expensive setup, while preserving deterministic simulation, database isolation, and meaningful correctness coverage. Deliver working test-infrastructure improvements, migrate existing expensive consumers, publish reproducible before/after measurements, and document concrete rules and examples that prevent future tests from recreating the same bottleneck. An investigation, recommendations, or documentation-only change does not complete this task.

## Context

- Control project: `mtgsolosports`. Target repository: `AlexBDevCorner/MtgSoloSports`, branch `main`.
- The user reports approximately **21 minutes** for the backend test package. Treat this as an observed symptom, not a reproducible benchmark; establish a fresh baseline on the worker's actual checkout and hardware.
- This is a follow-up to completed MSS-067, not a repetition of its report. `docs/test-performance-baseline.md` records an older 946-test suite reduced from 33.7 minutes to approximately 14:49-15:37 through prepared-save reuse. Its 394 pure `SimulationKernel` tests reportedly took only 0.4 seconds combined. Those are historical measurements, not current results.
- The earlier report identified repeated full-season SQLite simulations, multi-season lifecycle drains, qualifier execution, catalog seeding, and HTTP test-host creation as the dominant costs. It explicitly identified a real Season 2 template as a possible next improvement.
- Existing reusable infrastructure includes `tests/MtgSoloSports.Tests/Features/SharedSaveTemplates.cs`, `TestSaveStores.cs`, and `PostseasonTestSaves.cs`. Templates already include completed Season 1, selected Color Cup, synthetic qualifier setup, and Season 1 plus postseason. Read the actual implementations before extending them.
- Current candidate consumers include `Features/Qualifiers/Mss075FullCompletionTests.cs`, `Mss075PartialCompletionTests.cs`, `Mss075ResumeTests.cs`, and `Mss075RepeatSafetyTests.cs`. They fork completed Season 1 and then call `PostseasonTestSaves.DrainToActionAsync(..., "RunQualifier")`, repeating a potentially expensive lifecycle prefix. Also inspect `Features/Seasons/TransitionRevealLifecycleTests.cs`, `EventProgressTests.cs`, `SeasonLifecycleTests.cs`, and current Reports/Athletes/History/Cups/API tests. These are investigation starting points, not a predetermined diagnosis or an instruction to replace every lifecycle test.
- `scripts/test-timing.py` already reads TRX results. Reuse and improve it where necessary instead of introducing a second reporting stack. Verify its test-class grouping against real TRX definitions; do not assume names always include a namespace or that splitting a display name identifies the class correctly.
- `.github/workflows/ci.yml` currently runs backend restore, build, and tests before the remaining verification steps. Restore/build costs and runner differences must be distinguished from test execution.
- Priority `1000` is the maximum supported priority. The user explicitly authorized this task to be `ready` immediately. No dependency on unfinished feature work is required; optimize the implementation present when this task is dispatched.

## Requirements

### 1. Establish a current, reproducible baseline

1. Before changing test behavior or infrastructure, run the normal Release backend suite with TRX output and measure elapsed test execution separately from restore/build. Record target commit, SDK/runtime, operating system, processor count, memory, runner type, relevant test configuration, test counts/outcomes, and whether optional long-run flags are enabled. Do not expose secrets or unrelated environment values.
2. Rank at least the 20 slowest test cases and 10 slowest test classes. Inspect their helpers and separate expensive setup from the behavior under test. Explain fixture/template initialization costs, whether initialization happens once per process or repeatedly, and how parallel contention affects recorded durations. Summed test durations are not suite wall-clock time.
3. Audit repeated database creation/migrations, catalog creation/import, complete seasons, postseason and qualifier lifecycle prefixes, template forks and file copies, HTTP host startup, waits/retries, and unnecessary serialization. Inspect new tests added after MSS-067 rather than assuming the previous findings explain today's entire runtime.
4. Produce a ranked implementation plan inside the task's work, then implement the safe high-impact items. Record which candidates were converted, retained, or rejected and why. Do not finish by handing the optimization back as future work.

### 2. Implement reusable, authentic starting states

5. Prefer extending `SharedSaveTemplates` and the existing checkpointed fork helpers. Build each expensive reusable starting state at most once per test process and give each consumer an independently mutable database in its own temporary root.
6. Where measurements confirm repeated lifecycle setup, add the smallest useful set of additional prepared states. Candidates include a real Season 2 league-complete state, automatic-movement-complete/qualifier-pending state, qualifier-complete/rebalance-pending state, or a later event boundary genuinely reused by several tests. Choose states from measured consumers, not a speculative matrix of every possible phase.
7. Build authentic lifecycle templates through the same production handlers used by existing integration scenarios. Preserve real persisted metadata, memberships, standings, immutable round history, RNG state, rule versions, and legal-next-action state. Do not replace real historical integration data with synthetic rows when those facts are part of the assertion. Existing explicitly synthetic fixtures remain appropriate for focused tests that do not claim end-to-end provenance.
8. Preserve safe SQLite snapshot handling. Reuse established locking and WAL checkpoint/copy behavior; never copy a database while uncheckpointed committed data or another mutation can be omitted. Verify source templates cannot be mutated by consumers and that fork operations neither modify sporting results nor advance RNG.
9. Make lazy construction safe under parallel first access. Failed construction must not publish a partially initialized template; handle temporary-root cleanup and failed retries sensibly. Avoid deadlocks between dependent templates, global locks around whole tests, unbounded template growth, and sharing live database contexts/connections across tests.
10. Preserve seed-specific and rules-specific tests. A canonical template may serve seed-independent assertions, but must not silently replace pinned golden seeds, rule versions, or genuinely distinct sporting scenarios. If more than one seed/version is necessary, keep cache keys explicit and bounded; do not build a generic fixture framework.

### 3. Migrate existing tests, not just introduce new helpers

11. Convert the measured highest-cost repeated setup paths to suitable template forks, including the newer qualifier/status/resume/repeat-safety family where equivalent real starting states are possible. The action and assertions that establish the named behavior must still execute in each test.
12. Audit other significant contributors across lifecycle, reports, records, athletes, history, cups, and API tests. Reuse prepared data for tests whose subject is a read model, response, report, or transition after that data exists. Avoid simulating full seasons merely to assert a field or small projection.
13. Preserve the trigger and failure mode of each regression. Maintain a conversion inventory mapping changed tests/classes to their original setup, replacement setup, behavior still executed, assertions preserved, and retained end-to-end coverage. Consolidate genuinely redundant scenarios only when the coverage argument is explicit and verifiable.
14. API endpoint tests must continue invoking the endpoint under test through the real HTTP pipeline. Seeding a private database through a prepared template is appropriate when save creation/import/simulation is incidental setup. Tests of creation/import/simulation endpoints must still exercise those endpoints themselves.
15. Share immutable catalogs or test hosts only where measured benefit justifies it and existing factory isolation supports it. Keep per-test saves roots and configuration independent, reset mutable host state, and handle cleanup. Never trade a few seconds for order dependence, shared mutable saves, or cross-test filesystem/port collisions.
16. Keep at least one normal-suite real path for from-scratch universe creation through the critical lifecycle transitions being replaced as setup. Keep required fast-versus-manual, step-versus-bulk, resume, transaction/RNG, persistence/replay, and sporting-invariant proofs. A test whose action is a full season still needs to run that action; a template must not precompute the answer the test claims to verify.

### 4. Deliver and prove an actual speed improvement

17. Primary target: reduce the same normal backend suite's elapsed wall-clock time by **at least 50%** versus the fresh baseline on comparable hardware. Aim for **under 10 minutes** for the full required backend suite on a GitHub-hosted runner. Treat a few-minute focused developer loop as a usability goal, not permission to redefine the full-suite denominator.
18. Measure the optimized suite in three consecutive independent test processes, with template caches cold at process start. Compare their median wall-clock time with the fresh baseline and publish all three results, test counts/outcomes, and the remaining slowest cases/classes. Do not claim improvement from running a warm in-process cache, removing build from only one side, using faster hardware, reducing the test set, or moving cases out of the measured suite.
19. The 50% goal is an engineering target, not permission to weaken tests. If it cannot safely be reached, completion still requires implemented high-impact optimizations, a measured material reduction, and specific evidence explaining the remaining irreducible work and the exact target shortfall. A report-only result, marginal unmeasured cleanup, or a list of unimplemented obvious setup-reuse opportunities is not acceptable.
20. Do not improve the headline by disabling/skipping ordinary tests, returning early, reducing required seeds or simulation lengths without equivalent proof, broadening opt-in gates, removing assertions, increasing timeouts, or disabling parallelism globally. Genuine soak/calibration runs may retain existing opt-in behavior; any additional reclassification needs a named retained correctness counterpart and an explicit before/after accounting independent of setup savings.
21. Keep the full required backend suite as a PR check. A convenient focused command may supplement it. Do not replace required coverage with a small default subset or move correctness proofs to a nightly-only workflow as the solution to this task.

### 5. Make runtime costs visible in normal CI

22. Reuse the TRX reporting script and add a concise ranked slow-test summary to CI output or the GitHub job summary. Preserve failure propagation from `dotnet test`; timing/reporting steps must not turn a failed test job green.
23. Capture/upload TRX results and the compact timing summary when available, including on test failure. Use a bounded artifact retention period, meaningful names, and no save databases, catalog dumps, secrets, or huge binary files. Missing results should be reported honestly and must not obscure the original test failure.
24. Ensure reporting reliably groups parameterized tests and classes using TRX metadata rather than ambiguous display-name parsing. If the script changes, add a small synthetic TRX self-check/fixture covering actual class grouping, repeated/parameterized cases, durations, and missing/malformed results as appropriate. Do not add a telemetry service or brittle per-test timing assertions to ordinary correctness tests.

### 6. Write guidance that future contributors and agents will follow

25. Add a discoverable testing guide, for example `docs/testing.md`, and a concise normative testing section in target `AGENTS.md` linking to it. Add a short link from the README or existing contributor/testing entry point. Update `docs/test-performance-baseline.md` with a clearly dated MSS-122 section while preserving the historical MSS-067 measurements.
26. The guide must explain how to choose between a pure kernel test, feature-handler/database test, HTTP contract test, and end-to-end lifecycle proof. State when prepared saves are required for incidental expensive setup and when a fresh from-scratch simulation is necessary because it is the subject of the test.
27. Document every supported prepared state's exact sporting boundary, seed/rule assumptions, authentic versus synthetic provenance, next legal actions, builder dependencies, per-process lifetime, and consumer cleanup responsibilities. Show how to fork, mutate only the fork, and seed an API factory correctly.
28. Include executable examples adapted from the final implementation: a focused pure test; a template-backed feature test with safe cleanup; an HTTP read/contract test using seeded data; and a real lifecycle/equivalence test that must retain its simulation. Prefer brief excerpts from working repository tests over imaginary APIs or a new example framework.
29. Document how to add or extend a template safely, preserve independent test execution and parallel isolation, avoid copying live WAL state, handle initialization failure, and keep rule-version/seed coverage intact. Explain that templates are generated for the current test process, not checked-in opaque database snapshots.
30. Add a practical author/reviewer checklist: identify the assertion's smallest valid starting state; search existing templates before adding expensive setup; justify a new full-season/multi-season run; keep the named action under test; preserve regression trigger, seeds, RNG and assertions; avoid network/clock dependencies; run the changed class alone; inspect timing impact. New avoidable full-season setup should be rejected during review.
31. Provide copyable commands for normal verification, an individual class/test filter, TRX capture and ranking, and existing opt-in diagnostics. State expected suite budgets as measured guidance, distinguish focused feedback from required full verification, and explain how to investigate a regression without relying on noisy hard millisecond thresholds.

## Architectural direction

- Follow target `AGENTS.md` and its applicable local skills. Keep vertical slices, direct Endpoint -> Handler calls, the pure `SimulationKernel`, versioned deterministic RNG, fixed-point sporting math, and atomic result/RNG persistence unchanged.
- Expected production-code changes: none. Work primarily in `tests/MtgSoloSports.Tests/Features/`, `scripts/test-timing.py`, `.github/workflows/ci.yml`, `docs/`, `AGENTS.md`, and a contributor-entry-point link. Justify changes outside those areas and keep them minimal.
- Extend the existing prepared-save/fork design rather than adding a generic repository/service, a new test framework, a fixture DSL, or broad inheritance hierarchies. Keep genuinely shared test setup in test code; feature-specific setup stays close to its feature.
- Templates are immutable after publication. Every mutating test operates on an isolated fork. Sporting randomness never comes from a clock, nondeterministic ordering, GUIDs, or unversioned random generators.
- Preserve historical result payloads, save/schema compatibility, golden outputs, persisted rules, and sporting invariants. Do not modify expected results merely to accommodate a faulty fixture.
- The worker implements this single task on the workflow-prepared `autonomous/MSS-122` branch, makes meaningful local commits, and follows `autonomous-worker-git-boundary`. Publication remains the recovery/publisher step's responsibility; never modify the control checkout, dispatch other tasks, or publish directly from the model session.

# MSS-043 — Run MtgSoloSports locally with Docker Compose and prevent Windows/Linux casing regressions

## Goal

Provide a simple, reliable `docker compose up --build` experience for running the entire MtgSoloSports application locally on Windows (Docker Desktop/WSL2) and Linux. Build and run the application in a Linux container environment to make ordinary local startup consistent with Linux CI, while proactively catching the filesystem/import-casing problems that have repeatedly broken the Windows checkout. Keep existing non-Docker development viable.

## Context

- Project: `mtgsolosports`; target repository: `AlexBDevCorner/MtgSoloSports`; default branch: `main`.
- Current root `README.md` documents two host processes: `dotnet run --project src/MtgSoloSports` on port 5180, plus `npm run dev --prefix src/MtgSoloSports.Web` on port 5173. The Vite configuration proxies `/api` to `http://localhost:5180` and builds production assets to `src/MtgSoloSports/wwwroot`. There is no root Docker Compose setup today.
- Stack: .NET 10 ASP.NET Core backend, Node 22-compatible React/TS/Vite 7 frontend, one SQLite database per save, and a separate catalog SQLite file. Existing `SaveStorageOptions` defaults to `saves`; `CatalogStorageOptions` defaults to `catalog/catalog.db`. Both should use persistent Docker volumes in container mode.
- Linux GitHub Actions already performs .NET restore/build/test/format plus frontend install/typecheck/build. The repo previously had a local blank page caused by a `RevealBoard` import/export mismatch. The current tree uses `RevealBoard.tsx` for the component and `revealBoardHelpers.ts` for pure helpers. Inspect current source and any current branch regressions rather than assuming a specific old error is still present.
- **Crucial limitation:** Linux containers alone do NOT solve incorrect import casing or a case-insensitive Windows host checkout. A container image built from a Windows checkout with missing/collapsed case-only paths can inherit the problem; live source bind mounts from `C:\...`/NTFS usually retain host filesystem limitations. Treat a Linux-native image filesystem, exact-case checks, and Windows/WSL checkout instructions as distinct parts of the solution.
- Follow `AGENTS.md`, `docs/technical-design.md`, and existing CI style. Product architecture remains vertical-slice Endpoint -> Handler with **no MediatR**. This is primarily developer infrastructure/documentation, not a gameplay feature.

## Requirements

1. Add a root-level `compose.yaml` (or `docker-compose.yml`) and appropriate Dockerfile(s) supporting a **documented, single-command default**: `docker compose up --build` builds Linux images and starts the app without installing host Node or .NET SDK. The normal/default mode must serve both the React app and API from the containerized application with browser-accessible localhost address and documented ports. A multi-stage build (Node 22 frontend + .NET 10 build/publish + ASP.NET runtime) serving compiled Vite output through the existing ASP.NET host is a good default; an equivalently simple and reliable implementation is acceptable.
2. The default reliable mode MUST copy source into Linux image layers and use files within container/image filesystems. Do **not** bind-mount the Windows host source tree or host `node_modules`/build output into the default container path. Add appropriate `.dockerignore` for `.git`, `control/`, `node_modules`, build artifacts, local SQLite files, and confidential local material without excluding files needed for frontend/backend build. Keep Linux path casing consistent in every `COPY`, import and entrypoint.
3. Persist save databases, catalog DB and data needed for normal offline reuse in named Docker volumes (or equivalent explicit persistent Linux volume), configuring `Saves__SavesRoot` and `Catalog__CatalogPath` appropriately. `docker compose down` / container rebuilds must preserve cards and existing universes; explicitly document that `docker compose down -v` is destructive. Containers should run development/local app settings, bind the ASP.NET listener to `0.0.0.0`, and expose only needed host port(s). Do not bake user data or credentials into the image.
4. Provide a pragmatic **optional development mode** if feasible for fast frontend/backend changes (e.g., Compose profile/override): a Vite server accessible on localhost, an ASP.NET backend address reachable from the Vite container via Compose service DNS, documented source-refresh/rebuild behavior, and dependencies isolated from host `node_modules`. For live source mounts, specifically require/recommend a repository checkout *inside the WSL2 Linux filesystem* (e.g., `~/src/MtgSoloSports`, not `/mnt/c/...`) on Windows and explain the tradeoff: HMR mounts from NTFS do not guarantee Linux case sensitivity. If a reliable hot-reload mode cannot be implemented without fragile cross-platform assumptions, document a reliable image rebuild/edit loop instead of shipping a misleading mode. The default one-command mode takes priority.
5. Proactively guard against casing regressions: audit current tracked paths and relative frontend import specifiers for exact-case compatibility and resolve any **demonstrated** case-only conflict with a distinct, portable filename or correctly cased import as appropriate. Add an inexpensive repo check or CI safeguard that detects tracked file/directory paths colliding under case-insensitive comparison and validates relevant local imports against actual tracked filename casing; rely on the existing Linux frontend typecheck/build as additional enforcement. Ensure a clean Windows checkout has no tracked pairs differing only in case. Avoid fake fixes such as clearing Vite cache indiscriminately or changing `git config core.ignorecase` as a supposed universal remedy.
6. Update README's **recommended local run** with exact copy/paste commands for `docker compose up --build`, access URL, log viewing, restart after source changes, `docker compose down`, persistence, and how to opt into dev/HMR mode (if added). Describe prerequisites Docker Desktop + WSL2 Linux containers on Windows, equivalent Docker Engine/Compose on Linux, WSL-native clone guidance for casing reliability, and troubleshooting when a Windows checkout already has an invalid/mixed module graph. Retain the original direct `dotnet` + Vite option as an alternative. Explain that containerization surfaces/prevents environment differences but **does not silently correct bad imports or recover lost case-only files**.
7. Add automated validation: `docker compose config`; production Docker image build on the existing Ubuntu CI or a dedicated appropriately cached job; start/health-smoke the application and check a representative `/api` endpoint plus a direct deep-linked React route (SPA fallback) so the built production UI and API work from the same host. Include the exact-case/collision guard in CI, preserve existing backend and frontend gates, and keep the added CI cost reasonable. Use a smoke endpoint requiring no imported catalog or created save (e.g. `/api/catalog/stats`) and deterministic HTTP readiness retries rather than arbitrary sleeps.
8. Document and manually verify a clean Docker Desktop Windows run and a Linux run when available, including an image rebuild, save/catalog persistence after restart, and import/build behavior. If Windows execution is not available in the autonomous worker, explicitly say so in the PR, report Linux CI evidence, and supply precise steps the user can run on Windows without pretending it was tested there.
9. Keep the Docker setup compatible with standard localhost use of all current routes (including routed athlete profiles, standings, history and Cups), Scryfall import over outbound HTTPS, per-save SQLite, and export/import flows; avoid requiring Kubernetes, cloud resources, or new services.

## Architectural direction

- Prefer one straightforward production-like local Compose service using a reproducible multi-stage Docker build. Optional development services should be isolated in a profile/override, not complicate `docker compose up --build`.
- Confirm the existing ASP.NET static-file/SPA fallback actually serves `wwwroot` after publishing; place frontend compiled assets in the final image's expected `wwwroot` and avoid accidentally overwriting them during `dotnet publish`.
- Use Linux filesystem volumes for persistent SQLite state. If non-root runtime user permissions need attention, create/chown data directories at image-build time or use a narrowly scoped startup strategy; do not solve it by running everything privileged.
- Preserve current frontend Vite port/proxy for non-Docker development. If optional Docker dev mode runs separate services, use `api` (or the actual service name) rather than `localhost` as the container-to-container proxy target, while browser requests continue to use the published localhost port.
- Inspect actual repository paths before renaming files, as there may no longer be a current casing bug in the default branch. Keep any necessary casing corrections small and verify Windows-friendly filenames.

## Acceptance criteria

- [ ] From a clean clone, `docker compose up --build` starts Linux-containerized MtgSoloSports and serves the working React UI and backend via a documented localhost address without host .NET/Node setup.
- [ ] Visiting an SPA deep link directly/refreshing it works alongside `/api` requests and static MTG card/image assets; Scryfall catalog import is still reachable.
- [ ] A catalog and created save survive `docker compose down` followed by `docker compose up --build` and an image rebuild; normal cleanup does not delete user data.
- [ ] The default Compose mode does not mount Windows source, `node_modules`, or host build outputs over the Linux image filesystem.
- [ ] The exact-case/collision safeguard runs in CI and fails on a deliberately introduced mismatched local import or a case-only tracked filename pair (use a disposable test/fixture, never commit an intentional bug).
- [ ] Documentation distinguishes default built-image workflow from any optional live-reload workflow and clearly addresses WSL2 Linux filesystem checkout versus NTFS bind mount limitations.
- [ ] CI validates Compose syntax, Linux image build and HTTP smoke checks, and existing .NET/frontend test/build quality gates remain green.
- [ ] README's original host-based workflow is preserved as an alternative. No gameplay, state-machine, scoring, RNG, or persistence-schema changes are introduced.
- [ ] The PR contains actual Linux verification results plus either Windows smoke results or transparent, reproducible Windows verification steps.

## Verification

Run from target repository root:

```bash
docker compose config -q
docker compose build
docker compose up -d
docker compose ps
docker compose logs --no-color
# Confirm configured localhost UI URL and a public GET /api/catalog/stats.
# Confirm direct refresh of a save-scoped SPA route returns the React shell.
docker compose down
docker compose up -d --build
# Confirm persisted catalog/save data from earlier run remains accessible.
docker compose down
```

Run the new casing check command added by this task, including disposable intentional-negative fixtures, then the existing repository verification:

```bash
dotnet restore MtgSoloSports.slnx --locked-mode
dotnet build MtgSoloSports.slnx --configuration Release --no-restore
dotnet test MtgSoloSports.slnx --configuration Release --no-build --no-restore
dotnet format MtgSoloSports.slnx --verify-no-changes --no-restore
npm ci --prefix src/MtgSoloSports.Web
npm run test --prefix src/MtgSoloSports.Web
npm run typecheck --prefix src/MtgSoloSports.Web
npm run build --prefix src/MtgSoloSports.Web
```

Report CI image-smoke/casing results and any Windows-only manual steps honestly in the PR.

## Out of scope

- No Kubernetes, deployment/cloud infrastructure, container registry publication or production hosting setup.
- No conversion of SQLite to a server database, no game rules/RNG changes and no unrelated UX or simulator feature work.
- No assumption that Docker alone repairs incorrect tracked filenames/imports or prevents Windows filesystem limitations with NTFS source bind mounts.
- No broad refactoring of frontend module layout unrelated to proven case portability.

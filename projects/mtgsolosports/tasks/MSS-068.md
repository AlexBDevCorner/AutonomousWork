# MSS-068 — Fix Standings and History blank-page crashes caused by React hook order

## Goal

Restore the Standings and History pages for newly created and existing universes. Both pages must render correctly while data is loading and after asynchronous data arrives, without violating React's Rules of Hooks. Add a real render/rerender regression test so this class of bug is caught in CI instead of reaching users.

## Context

- Target repository: `AlexBDevCorner/MtgSoloSports`, current `main`.
- Reproduction reported 2026-10-09:
  1. Start the application at `http://localhost:8080`.
  2. Create a new universe.
  3. Complete the first global stage for all 24 leagues. Dashboard remains usable, showing Season 1 / Stage 2 of 32.
  4. Open **Standings** (`/saves/:saveId/standings`): the page becomes entirely blank.
  5. Open **History** (`/saves/:saveId/history`): the same blank page occurs.
  6. Browser console reports `Uncaught Error: Minified React error #310` on both pages (React rendered more hooks than on the previous render).
- Code inspection of current `main` identifies concrete hook-order violations:
  - `src/MtgSoloSports.Web/src/features/standings/StandingsPage.tsx` has early returns for initial loading, missing seasons and invalid selections **before** `useMemo` calls for `tierGroups` / `tierSections`.
  - `src/MtgSoloSports.Web/src/features/history/HistoryPage.tsx` has early returns for loading/error/empty seasons **before** the `competitionGroups` `useMemo`.
  - On the initial render, these hooks are skipped. When the async season request resolves, the next render calls them, changing the hook count.
- Existing frontend tests cover much of the data and source/layout structure, but do not adequately verify a mounted component transitioning from its loading state to populated data. `npm run typecheck` and `npm run build` alone cannot catch this.
- Browser console also shows `MaxListenersExceededWarning` and `ObjectMultiplex ... orphaned data for stream` in `contentscript.js`. These appear to originate from an injected browser/extension content script. They are **not** evidence of an app-owned issue and must not distract from the React crashes.

## Requirements

1. Fix both confirmed hook-order violations. Ensure that **every React hook is called in the same order on every render**, including loading, error, empty, invalid URL/selection and populated states.
2. Make hook dependencies and fallback data safe while async queries have not yet resolved. Do not introduce render loops, stale selections, or unintended API calls as a side effect of moving hooks or extracting child components.
3. Preserve Standings functionality: season/league/view selection, tier grouping (Superleague and Feeder 1/2/3), tables, stage matrix, and URL-driven navigation.
4. Preserve History functionality: season/competition/stage/round selection, tier grouping, event replay, and links to related pages. Newly created universes with only one completed stage must work, not just finished seasons.
5. Add automated regression coverage that **mounts React components and changes their async data state over multiple renders** (or an equivalent browser-level test). It must fail against the old hook-order behavior and pass after the fix. Static source-string assertions alone are insufficient.
6. Cover both routes with loading -> populated and loading -> error/empty transitions. Include a new-universe/in-progress-season scenario and a route re-entry/navigation scenario. Ensure no uncaught hook-order error and no blank page.
7. Inspect closely related pages for the same explicit pattern of hooks appearing after loading/error early returns. Fix any identical, demonstrably broken pattern found, but keep the review focused. Do not broadly refactor the frontend.
8. Investigate the `contentscript.js` warnings only as a low-priority diagnostic. Check whether they reproduce with browser extensions disabled or a clean browser profile. If extension-injected, document that finding and **do not attempt to fix an external extension from application code**. If app-owned warnings are identified, fix only trivial, directly related issues; otherwise record follow-up separately.

## Architectural direction

- Prefer moving memoized derivations before early returns with safe default input, or extracting a child component with its own consistent hook lifecycle.
- Never silence the React warning or alter the global React runtime to hide the problem.
- Keep asynchronous fetching, URL state and persisted simulation data semantics unchanged.
- Keep regression tests deterministic, offline and fast enough for ordinary frontend CI. The existing frontend currently uses Node's test runner and does not have a browser component-testing framework; introduce the lightest practical render-level testing setup rather than relying on file-content checks.
- Do not modify sporting calculations, save data, migrations, or league rules.

## Acceptance criteria

- [ ] Standings and History render after creating a universe and completing the first stage for all 24 leagues (Season 1, Stage 2/32).
- [ ] Navigating to each page shows content, controls, or an appropriate loading/empty/error message, never an unexplained blank viewport.
- [ ] No React #310, hook-order warning, or uncaught exception is triggered on initial load, async completion, navigation back/forward, or route re-entry.
- [ ] All hooks on each affected component have unconditional, stable invocation order across their render paths.
- [ ] Valid Standings and History filters, tier groups, stage/round selection and deep links still behave correctly.
- [ ] An automated render/rerender regression test catches the previous failure for both routes and is run by the normal frontend test workflow.
- [ ] Existing relevant frontend tests, TypeScript typecheck and production build pass.
- [ ] The status of `contentscript.js` warnings is documented, without claiming extension-owned warnings were fixed by the app.

## Out of scope

- Reworking the overall UI layout or navigation design.
- Changing simulation, league structures, rankings, Cups, or history persistence.
- Replacing the application's general data-fetching architecture.
- Browser extension or wallet-injection code changes.
- Large-scale frontend refactors not required to fix a verified hook-order violation.

# MSS-042 — One-click fast-forward of the remaining league season to postseason

## Goal

Add an obvious one-click way to fast-forward **all remaining league stages of the current season across all active leagues** so a user can quickly generate realistic persisted season results and then inspect/test the Superleague movement, qualifier, Cup selection and Cup competitions step by step. This is a testing and convenience shortcut, not a separate sporting mode. Its default stop point must be **after Stage 32 league results are persisted and before any postseason action runs**.

## Context

- Project: `mtgsolosports`; target repository: `AlexBDevCorner/MtgSoloSports`; default branch: `main`.
- Currently the Live UI exposes Next Round and Complete Stage for an individual league. The Dashboard shows season progress and a "Next action / Available simulation" panel but does not provide a prominent one-click way to finish all remaining league stages.
- **Backend bulk support already exists**: `POST /api/saves/{saveId}/seasons/complete-season` in `Features/Simulation/CompleteSeason` completes the current season's remaining global stages, delegates to the same stage/round kernel as interactive simulation, persists stage boundaries, and intentionally stops before postseason. Reuse it; do not recreate a client-side loop of hundreds of per-round HTTP calls.
- **A different endpoint**, `POST /api/saves/{saveId}/simulate-seasons` with `{ "seasons": 1 }`, also exists; it runs the entire postseason, Cups and next-season start. **Do not use this for the default fast-forward action**, because it would skip the qualifier/Cup boundaries the user wants to inspect.
- Existing `POST /api/saves/{saveId}/seasons/advance-to-next-event` progresses one legal lifecycle boundary. `dashboardApi.ts` already exposes `fetchSeasonStatus` and `advanceToNextEvent`; inspect the existing UI lifecycle navigation so fast-forward hands control back to the normal postseason flow.
- Per `docs/game-rules.md`, each league season has 32 stages of 16 rounds. The global stage gate requires all active leagues to complete a stage before advancing. Season 1 has eight feeder leagues; Season 2 onward includes the Superleague. Qualifier and Color/Type Cups are **postseason** events, not mid-season stages.
- Follow `AGENTS.md` and `docs/technical-design.md`: feature-local vertical slices, direct Endpoint -> Handler, **no MediatR**; deterministic RNG and persisted immutable replay are mandatory.

## Requirements

1. Add a clearly labeled **"Fast-forward league season"** action prominently near current-season progress / "Available simulation" on the save-scoped Dashboard (and optionally a contextual entry point from Live). Explain in the UI that it completes the **remaining league stages for every league** and **stops before movement, qualifiers and Cups**, so those events can be inspected separately.
2. Make the action available when the current season has unfinished league stages, including a fresh save and an in-progress season with some already-simulated rounds/stages. Run only the remaining work; do not wipe/restart the current season or redo existing persisted results. Hide/disable the action with a correct explanation if Stage 32 is already complete or the save is already in a postseason/next-season transition.
3. Show a deliberate confirmation before initiating this substantial mutation, stating the current season, remaining stages if known, that all active leagues will advance, and that saved results cannot be undone through the UI. A technical save checkpoint is optional existing functionality, **not** a prerequisite and not an automatic rollback promise.
4. Call the existing `complete-season` backend operation once for the selected **route-scoped save ID**, rather than looping from React. Display an unmistakable running/busy state; prevent duplicate submissions and conflicting simulation controls in that tab while it runs. Do not invent per-stage live progress if the endpoint only returns a final result; an indeterminate busy indicator and current starting cursor are fine.
5. On success, show an accurate compact summary using the response (season, stages completed, before/after global-stage cursors), refresh all relevant Dashboard/save progress and legal-next-action state, and provide discoverable next steps to inspect final league tables and advance the postseason **one event at a time**. Existing Live, History, standings and Cups queries must show the newly persisted data without requiring browser reload. If relevant pages have separate query/cache state, invalidate/refetch it in the established way.
6. Handle backend conflict (another simulation active or illegal current phase), errors, navigations/reloads, and long-running requests gracefully. A failed or interrupted request must not falsely display "completed"; offer a refresh/recheck of authoritative server state and allow retry only if there are still remaining stages. Do not promise that dismissing UI or aborting a request reverses already committed stages. Respect the existing per-save backend mutation lock and safe stage-boundary persistence.
7. Preserve all existing league/bonus/RNG semantics and lifecycle boundaries. Fast-forward results for an identical seeded save and starting state must match manual completion across all leagues, including a partially played stage. Do not automatically trigger movement, a qualifier, Cup selection/events, bonus aging, or the next-season transition.
8. Keep the user experience clear at Season 1 versus later seasons: after fast-forward, the normal next action may create the inaugural Superleague in Season 1; normal later seasons proceed through movement -> qualifier -> feeder rebalancing -> appropriate Color/Type Cup events. The shortcut must not conceal or bypass these event screens.

## Architectural direction

- Prefer a small `dashboard` UI/action/API addition (or a reusable narrowly scoped simulation client where appropriate). Inspect `DashboardPage.tsx`, `dashboardApi.ts`, `useDashboard.ts`, save-scoped routing, and existing lifecycle controls before adding duplicate state management.
- Reuse `CompleteSeasonHandler` and existing response/progress DTOs. Change backend code only if a demonstrated integration or robustness issue requires a targeted adjustment; do not add new simulation algorithms.
- Backend remains authoritative. A successful response is not the only source of truth following a disconnect; refetch season progress/status after any ambiguous result.
- Keep a single save-scoped pending action state and avoid cross-tab/localStorage save confusion introduced by the routing feature.

## Acceptance criteria

- [ ] From a fresh save, clicking and confirming "Fast-forward league season" completes all remaining league stages for all eight Season 1 feeder leagues in one UI operation, with no manually repeated Round/Stage clicks.
- [ ] In a later season, the same action handles every active feeder league and the Superleague. Beginning from a partially completed stage, it preserves prior rounds and produces complete final standings without duplicates.
- [ ] It stops exactly at completed league Stage 32. **No postseason action has executed**: the user can inspect final standings, then run the next lifecycle event and see the correct inaugural movement (Season 1) or automatic movement/qualifier path (later seasons), followed by Cup selection and events using existing controls.
- [ ] The button has clear scope, confirmation and busy/disabled states; duplicate clicks do not launch duplicate simulations. Error/conflict/interrupted cases do not claim success and can be reconciled by refreshing backend state.
- [ ] The success view displays real counts/cursors from the response; Dashboard, stage tables, History and Cups/lifecycle navigation reflect persisted results without a forced hard reload.
- [ ] For seeded identical starting saves, bulk completion matches manual progression on final standings, bonus state, persisted history and final RNG boundary. Include at least one partial-stage regression scenario and preserve existing backend bulk tests.
- [ ] Add focused frontend tests for button visibility, confirmation, selected save ID, pending/error/success state and progress refresh; document a manual happy-path check for Season 1 and Season 2/postseason handoff.
- [ ] Full existing repository verification succeeds.

## Out of scope

- No automatic postseason execution from this new button, no configurable multi-season batch UI and no silent start of the next season. A separate explicit "simulate entire season including postseason" experience can be considered later.
- No scoring/bonus/qualifier/Cup-selection rule changes, no new RNG algorithm, no history rewrite and no resimulation of completed events.
- No live streaming stage-by-stage backend progress API, WebSockets or complex background job infrastructure solely for this shortcut.
- No unrelated Live reveal redesign, standings-table redesign, global frontend rewrite or work in other projects.

# MSS-039 — Fix multi-face Scryfall color classification and prevent colored creatures entering Colorless

## Goal

Ensure that the Colorless league contains only creatures that are genuinely colorless under the existing MtgSoloSports sporting-color rules. Fix the catalog import/classification defect that currently lets some colored multi-face creatures enter Colorless, and add regressions that cover representative real Scryfall layouts without incorrectly excluding legitimate colorless creatures.

## Context

- Project: `mtgsolosports`; target repository: `AlexBDevCorner/MtgSoloSports`; default branch: `main`.
- Follow `AGENTS.md`, `docs/game-rules.md`, and `docs/technical-design.md`. The architecture is a vertical-slice modular monolith, direct Endpoint -> Handler, **no MediatR**. Keep simulation deterministic and existing fixed-point scoring unchanged.
- The game's eight sporting colors use **printed card color**, NOT color identity or a naive reading of colored mana symbols. Hybrid mana has the game's existing Hybrid precedence; Devoid is Colorless; double-faced/transform cards use the front face. Preserve these documented rules.
- A real user's Colorless league screenshot included **Defacing Duskmage // Vandal's Edit** (white/black creature front), **Honorbound Page** (white), and **Sasaya, Orochi Ascendant** (green). These are incorrect Colorless entrants. The same screenshot also included legitimate Colorless entries such as **Brood Butcher** and **Kozilek's Sentinel** (Devoid), **Arcane Proxy** and **Phyrexian Fleshgorger** (normally colorless artifacts with colored Prototype costs), and ordinary colorless artifact creatures. Do not "fix" this by removing all visually colored or all alternate-cost cards.
- A code inspection of current `main` found a strong candidate: `src/MtgSoloSports/Features/Catalog/ImportCatalog/BulkCatalogParser.cs` `ExtractFrontFace()` always chooses `card_faces[0]` when present and maps `front.Colors ?? []`. It similarly supplies empty strings for other missing face fields. `SportingColorClassifier.Classify()` then interprets zero colors as Colorless. However, a missing `colors` property on an individual face is **not** evidence that the card is colorless; Scryfall's field placement differs by layout. This is a hypothesis to reproduce against representative real bulk entries, not permission to assume every layout can simply fall back to the top-level color array.
- Inspect `BulkCardRecord.cs`, `BulkCardFace.cs`, `SportingColorClassifier.cs`, the manual `ImportCatalog` and `ImportFromScryfall` paths, `BulkCatalogParserTests.cs`, `BulkJsonLinesParserTests.cs`, catalog persistence, and save creation/snapshots. The existing `DoubleFaced_UsesFrontFaceOnly` fixture has colors explicitly populated on each face, so it does not exercise the missing-face-colors case. Catalog refreshes must not silently change existing saves.

## Requirements

1. **Reproduce and document the actual failure.** Inspect representative Scryfall bulk-data records for the three reported false-Colorless entrants (and relevant alternate layouts/printings). Include a compact sanitized/offline test fixture or precisely equivalent fixture matching the *actual relevant Scryfall field placement* for each case. Record which fields are present, absent, or explicitly empty, and explain how the current parser handles them before changing behavior.
2. **Resolve printed/front-face color correctly for every supported layout.** Distinguish a truly present empty color array (legitimate Colorless) from a missing/unresolved color field. Handle cards with `card_faces` using Scryfall's layout-specific field semantics. Use top-level colors only when they actually represent the game-rule-appropriate face/card; do not accidentally combine colors from a reverse face of a transform card. Do not infer printed color solely from mana cost, color identity, or artwork: color indicators, characteristic-defining effects, and other exceptional cards must retain correct treatment.
3. **Preserve all existing sporting rules and candidate eligibility.** Preserve front-face creature eligibility, token exclusion, Devoid -> Colorless, Hybrid precedence, genuinely colorless Eldrazi/artifacts, Prototype creatures' normal printed colors, colored artifacts, and front-face handling for transform/flip/special layouts. Do not misclassify any colored card just because its face omits a field.
4. **Handle unresolved metadata safely.** An absent/ambiguous color must never default to Colorless. Choose a deterministic and observable handling policy based on real Scryfall data (e.g. safely derive where unambiguous; otherwise reject the problematic candidate with an actionable diagnostic). Preserve legitimate zero-color cards. Avoid allowing input-printing order to make a misclassified first printing permanently win duplicate collapse; if applicable, ensure later valid data cannot be undermined by a malformed printing.
5. **Cover both import paths.** The automatic Scryfall bulk import and manual JSON-array import must use the same corrected normalization/classification. Keep the existing quotas (at least 256 unique eligible athletes per sporting color), import failure safety, shared-catalog replacement semantics, and import statistics intact.
6. **Add focused regression tests using realistic offline fixtures** for Defacing Duskmage // Vandal's Edit (Multicolor), Honorbound Page (White), Sasaya, Orochi Ascendant (Green), a transform card with genuinely face-specific colors, a real Colorless card with empty colors, Devoid-colored-mana creatures, and a colorless Prototype artifact with a colored alternate cost. Test absent versus explicitly empty colors, imported unique-athlete collapse across printings where relevant, and an end-to-end catalog import/classification boundary; prove reported cards cannot be drawn into new Colorless league populations.
7. **Explain impact on existing saves.** Audit the existing catalog versus persisted athlete snapshots in saves. A corrected catalog/reimport must affect *future* save creation but **must not silently reshuffle or rewrite current leagues, prior round results, history, bonuses or immutable snapshots**. Add a concise user-facing troubleshooting/recovery note (README or existing relevant docs) identifying how to refresh the catalog, confirm the fix, and get a correctly classified new universe; explicitly state whether affected old saves remain unchanged. Do not promise that catalog refresh repairs existing universes.

## Architectural direction

- Prefer fixing the existing catalog import data-extraction boundary and adding narrow classifier invariants instead of changing simulation, league-generation rules or React reveal rendering.
- Work from actual Scryfall bulk-data shape, not invented assumptions about every multi-face layout. Keep normalization deterministic and testable without network access.
- Existing `SportingColorClassifier` can remain a pure function that receives resolved, non-null color data; prevent missing/ambiguous metadata from being converted to `[]` upstream. Preserve the current direct Endpoint -> Handler pattern if endpoints need changes.
- A user observed the symptom in an existing save, but root cause may be the catalog imported earlier. Diagnose accordingly.

## Acceptance criteria

- [ ] The three screenshot counterexamples classify as Multicolor (Defacing Duskmage), White (Honorbound Page), and Green (Sasaya), using representative actual Scryfall bulk-record shapes.
- [ ] Missing face-level colors are never automatically equivalent to an explicitly empty color array; supported layouts choose the correct authoritative colors without accidentally using a reverse face.
- [ ] A Colorless catalog candidate is genuinely colorless under `docs/game-rules.md` (including Devoid); appropriate colored, Hybrid and Multicolor candidates stay out of Colorless.
- [ ] Devoid, Prototype, normal colorless artifacts, transform/flip layouts, colored artifact cards, printed color indicators where applicable, and different-printing collapse have regression coverage.
- [ ] Manual and automatic imports yield the same classification for equivalent card records; failures/quotas cannot corrupt an existing healthy shared catalog.
- [ ] New saves built after a corrected import cannot select any of the three reported colored cards for the Colorless league.
- [ ] Existing saved history and seeded/deterministic simulation remain unchanged; a clear recovery path is documented for saves already created with bad athlete snapshots.
- [ ] The PR documents the reproduced root cause, representative field shapes, catalog reimport implications, and test results.

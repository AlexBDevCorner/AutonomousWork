# MSS-040 — Replace button-only navigation with real browser routes and deep links

## Goal

Make MtgSoloSports behave like a real browser application: every main page and athlete profile has its own stable, copyable URL, ordinary navigation uses genuine links, and users can open multiple creature profiles and screens in separate browser tabs without losing context.

## Context

- Project: `mtgsolosports`; target: `AlexBDevCorner/MtgSoloSports`; default branch: `main`.
- Current `src/MtgSoloSports.Web/src/App.tsx` controls navigation with local React `view` and `selectedAthleteId` state. `features/shell/AppShell.tsx` renders every navigation item as a `button` that calls `onNavigate`. Live/History/Records/Cups/Dashboard pass `onSelectAthlete` callbacks instead of real profile links. Thus the browser URL does not identify the page/athlete, Ctrl/Cmd-click and middle-click do not work, refresh loses the screen, and browser Back/Forward is not meaningful.
- The existing app is local ASP.NET Core + React/TypeScript/Vite; Vite proxies `/api`. Follow `AGENTS.md`, `docs/technical-design.md` and existing feature-local conventions. Preserve the direct Endpoint -> Handler architecture; **no MediatR**.
- A follow-up task (MSS-041) adds a first-class league standings page and will use the routing/link conventions defined here; do **not** build that new standings UI in this task.

## Requirements

1. Introduce genuine, addressable client-side routing, with stable readable paths for Saves, Dashboard, Live event, History, Records/HoF, Cups, and individual athlete/creature profiles. Encode the save identifier in save-scoped routes and the athlete identifier in profile routes. Example route shapes (adjust consistently if needed): `/saves`, `/saves/:saveId/dashboard`, `/saves/:saveId/live`, `/saves/:saveId/history`, `/saves/:saveId/records`, `/saves/:saveId/cups`, `/saves/:saveId/athletes/:athleteId`. The root `/` should resolve to a sensible existing-save or Saves landing page.
2. Replace **navigational** buttons and callback-only athlete opens with semantic anchors/router links throughout the existing shell and relevant Live, reveal/results, Dashboard, History, Records and Cups screens. Keep buttons for actual actions (simulate, reveal, import, selectors, etc.). Do not use `window.open` as a substitute for native browser link behavior. Keyboard navigation, visible focus, accessible current-page indicators, and normal mouse/context-menu interactions must work.
3. A creature name/card/standings entry that navigates to an athlete profile should point at the **correct athlete in the correct save**, permitting multiple profiles side by side in different tabs. Navigation back to the referring screen should be sensible, but should not assume every profile was entered from Live or require in-memory `onBackToLive` history. Directly opening a profile URL must work.
4. Direct URL entry, reload, bookmarked links, Back/Forward and switching among existing pages must load the correct state without a prior in-app click. Ensure Vite development and ASP.NET Core's built frontend packaging both serve the React entry point for valid UI routes while leaving `/api`, static assets, and server errors unaffected.
5. Route-specific save IDs are authoritative for requests and page context. One browser tab selecting another save must not silently redirect or mutate a different tab's explicit save-scoped URL via shared `localStorage`. Preserve the existing last-selected-save convenience only as a fallback for entry/landing flows. Handle deleted/nonexistent save IDs, malformed athlete IDs, missing selection and unavailable profiles with useful recoverable UI, not a white screen or wrong-save data.
6. Keep page-specific context where meaningful: support a URL-backed selection for the Live league and allow an independently opened History view to restore its selected season/competition/stage/round when represented in a link, or use a clearly documented consistent minimal scheme. Query-string-based detail selection is fine. Changes to navigation must not reset the selected persisted Live round unexpectedly or autoplay a reveal.
7. Prepare a clear documented convention for future route extensions, including a save-scoped league standings detail route to be used by MSS-041, without implementing that future page. Use a conventional lightweight router if appropriate; avoid hand-written fragile URL parsing and a wholesale frontend rewrite. Ensure internal navigational elements work as standard links and share URL-building helpers where reused.

## Architectural direction

- Start with `App.tsx`, `features/shell/AppShell.tsx`, existing athlete-entry components and the web host's SPA fallback. Migrate page state from the transient `View` / `selectedAthleteId` combination to routes while preserving existing feature boundaries.
- Keep save-scoped API calls explicit by route save ID. Prefer route params/query state for shareable navigation context and preserve existing per-feature presentation-only reveal state.
- Avoid re-fetching/re-simulating sporting data merely for navigation. Never alter immutable saved results, RNG, bonuses or progression.
- Migration may require a small backwards-compatible adjustment to callback props; keep feature changes narrowly scoped and avoid creating multiple competing navigation mechanisms.

## Acceptance criteria

- [ ] Main navigation exposes real distinct URLs; the address bar matches the displayed page, and Back/Forward navigate correctly.
- [ ] From current standings/reveal/history/dashboard/records/cups where athlete links exist, Ctrl/Cmd-click, middle-click, context-menu Open in new tab, and copying the link all open the intended athlete profile for the correct save. Two different creature profiles and Live/History can coexist in different tabs.
- [ ] Pasting a profile link into a fresh tab and reloading it works in both Vite development and the ASP.NET Core-hosted built UI; unrelated `/api` routes continue functioning.
- [ ] Root/no-save, nonexistent save, invalid athlete, changed save, and missing profile flows show a usable state without cross-tab selection leakage or a blank page.
- [ ] Navigational controls are real links and actions remain buttons; active-page semantics, keyboard access and focus remain usable on desktop and mobile.
- [ ] Existing manual-by-default Live reveal, selected round, persistence, Cup/History/Records/Profile screens and simulation commands do not regress.
- [ ] Add focused frontend routing/link tests where feasible and document manual evidence of copied URL, new tab, refresh, Back/Forward and cross-save-tab behavior.
- [ ] Full repository verification succeeds; no unrelated UI overhaul or sporting-rule change.

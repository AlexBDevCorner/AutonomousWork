# MSS-055 — Fix Type Cup squad allocation so capped athletes do not receive selection priority

## Goal

Fix Type Cup squad selection so a permanent Type Cup nationality is treated strictly as an **eligibility restriction**, not as a selection privilege.

The current allocator can lock a type's squad to four lower-rated capped/exclusive athletes and leave stronger uncapped athletes unselected. It can also prefer capped athletes by an overwhelming artificial cost bonus. This produces materially weaker squads such as Wizard and can leave a high-ranked multi-type athlete such as Mockery of Nature out of every eligible team.

The allocator must continue to maximize the number of valid four-athlete Type Cup teams and respect permanent nationality, while selecting the strongest sensible squads from the eligible field and using multi-type preference only to resolve genuine allocation conflicts.

## Context

- Project: `mtgsolosports`; target repository: `AlexBDevCorner/MtgSoloSports`; default branch: `main`.
- The bug is in `src/MtgSoloSports/SimulationKernel/Cups/TypeCupAllocation.cs`.
- `EligibleTypesFor` already enforces the permanent-nationality rule correctly: a capped athlete is eligible only for the capped nationality; an uncapped athlete remains eligible for its printed creature types.
- The current `AllocateOptimal` path calls `CollectGuaranteedTeams`. A type with at least four athletes who are eligible for only that viable type is immediately finalized from those athletes and removed from the global allocation problem.
- This is safe for proving that the **team exists**, but not for choosing the **best squad**. Four capped/exclusive athletes can therefore freeze a weak roster even when stronger uncapped athletes are eligible for the same type.
- `ComputeAssignmentCost` separately gives uncapped athletes a `1_000_000_000` cost penalty. This makes capped status dominate preference, type rank, and rating, so weak capped athletes are intentionally favoured over stronger uncapped athletes.
- The legacy `PickFour` greedy path contains the same capped-first assumption and should not preserve contradictory semantics even if it is not currently used by the public `Allocate` path.
- Existing documentation already describes the intended rule:
  - `docs/game-rules.md` §15: capped nationality becomes permanent after participation; uncapped multi-type athletes prefer the type where they rank higher; global allocation should maximize valid teams.
  - `docs/technical-design.md` §17: capped athletes **can only represent** their permanent nationality.
- The documentation does **not** say that capped athletes are guaranteed a squad place or should outrank stronger uncapped athletes.
- Observed real-save examples:
  - **Wizard** selected capped athletes rated approximately `0.522, 0.396, 0.312, 0.305` while leaving several stronger eligible uncapped Wizards unselected, including athletes around `0.387, 0.371, 0.353, 0.340, 0.321, 0.318`.
  - **Mockery of Nature** is an uncapped Eldrazi Beast, ranked #1 Eldrazi / #2 Beast in the observed selection report, yet was not placed on either team while lower-rated capped athletes filled both squads.
- Follow `AGENTS.md`, the deterministic SimulationKernel rules, fixed-point selection scoring, and the existing vertical-slice architecture.

## Required semantics

1. **Permanent nationality is eligibility only.**
   - A capped Wizard may represent Wizard and may not represent any other printed type.
   - Being capped for Wizard MUST NOT grant extra selection priority over an uncapped Wizard.
   - No scoring/cost term may exist solely to reward capped status.

2. **Maximize the number of valid teams first.**
   - Preserve the existing cardinality requirement: field as many valid four-distinct-athlete teams as possible.
   - Do not regress overlap handling where multi-type athletes are needed to keep several teams viable.

3. **Within a maximum-cardinality solution, squad quality must matter.**
   - A higher-rated eligible uncapped athlete must not be left unassigned while a lower-rated capped athlete occupies the same type merely because the lower-rated athlete is capped.
   - Selection rating/type rank should drive who actually makes a squad once team-count feasibility is protected.
   - Multi-type preference remains useful for deciding **which eligible team** should receive an uncapped athlete when several assignments are otherwise viable.

4. **Preference must not become a benching penalty.**
   - An uncapped athlete preferring another type must still be allowed to represent this type when that produces a stronger valid squad and the athlete would otherwise be unassigned.
   - Relative-type preference should resolve allocation conflicts, not function like a second nationality lock.

5. **Determinism must remain unchanged as a property.**
   - Equivalent input state must always produce the same allocation.
   - Continue using ordinal/fixed-point deterministic tie-breaking; no RNG, floating point, GUID ordering, clock, or database-order dependence.

## Requirements

1. Remove or redesign the `CollectGuaranteedTeams` shortcut so it cannot finalize a roster from four exclusive/capped athletes before stronger eligible candidates are considered.
   - It is acceptable to retain a fast path only if it proves team existence without freezing the actual four selected athletes.
   - Prefer letting the existing connected-component/global solver choose the roster; independent singleton components are cheap enough to solve normally.

2. Remove capped-selection priority from `ComputeAssignmentCost`.
   - Delete the artificial billion-point uncapped penalty or replace the objective with one that contains no capped-status reward.
   - Capped legality must come entirely from the eligibility graph produced by `EligibleTypesFor`.

3. Rework min-cost/objective ordering as needed so the allocator has this effective priority:
   1. maximum number of valid teams;
   2. strongest overall legal squad selection based on the existing Type Cup selection rating/type ranking;
   3. sensible multi-type relative-rank preference when resolving competing legal placements;
   4. deterministic tie-breakers.
   - The exact numeric encoding may differ, but capped status MUST NOT appear as a positive selection factor.

4. Ensure an athlete that is stronger for a type is not excluded simply because weaker candidates are single-type/capped.
   - "Exclusive" means the athlete has fewer placement options; it does not mean the athlete owns a squad slot.

5. Review `PickFour` and any other Type Cup allocation helper for capped-first ordering.
   - Remove contradictory capped-first selection behaviour even if the helper is currently legacy/test-only.
   - Do not leave two different semantic models in the kernel.

6. Keep `EligibleTypesFor` permanent-nationality behaviour intact.
   - A capped athlete must still never be allocated to another type.
   - An uncapped athlete must remain eligible for all valid distinct printed creature types.

7. Preserve maximum-team overlap behaviour.
   - Existing scenarios where a shared athlete must be moved away from its preferred type to allow two teams to field must still work.
   - Do not replace the global solver with a per-type greedy top-four implementation.

8. Preserve the existing selection rating calculation and normalization.
   - Do not change 35/30/25/10 weights, fixed-point math, bonus/performance/form/prestige inputs, or ranking display as part of this task.

9. Keep Type Cup selection reports truthful.
   - Selected members, type ranks, assignment reasons, and "called up ahead of higher-ranked ..." explanations must reflect the corrected allocation.
   - After the fix, the report should no longer explain a weaker selection purely as a consequence of cap status.
   - If reason labels such as `Capped` currently imply selection priority rather than eligibility, adjust wording/logic so they remain accurate.

10. Add regression tests that directly reproduce the failure patterns.

## Required regression tests

At minimum add kernel tests covering all of the following:

### A. Four weak capped athletes do not lock the squad

Create one viable type with:
- four capped/exclusive athletes;
- at least two stronger uncapped athletes also eligible for that type.

Assert that the strongest legal four are selected and one or more weak capped athletes are left out.

This test must fail against the current `CollectGuaranteedTeams` behaviour.

### B. Cap is a restriction, not a bonus

Construct a case that reaches the min-cost/global assignment path with:
- a lower-rated capped athlete;
- a higher-rated uncapped athlete eligible for the same type.

Assert that capped status by itself does not make the weaker athlete win the slot.

This test must fail against the current `1_000_000_000` capped-priority cost.

### C. Strong multi-type athlete is not stranded

Model the Mockery-of-Nature pattern:
- one strong uncapped athlete eligible for two viable types;
- both types have enough other athletes to field teams;
- lower-rated capped/exclusive athletes exist on both sides.

Assert:
- the strong athlete is selected by exactly one eligible team;
- it is not left unassigned merely because both teams can already field four capped/exclusive athletes;
- all maximum-cardinality teams still form.

### D. Preference still resolves real conflicts

Preserve/add a scenario where one multi-type athlete cannot serve both teams and its relative type rank matters.

Assert that preference influences **which team receives the athlete** without turning into a reason to leave a clearly stronger athlete benched when a legal squad slot exists.

### E. Permanent nationality remains strict

Keep the existing rule that a capped athlete can represent only its permanent nationality and verify the fix does not relax this constraint.

### F. Existing maximum-cardinality overlap cases remain green

Keep the current tests such as:
- shared athletes still permit two teams when feasible;
- non-viable distractor types do not reduce the number of fielded teams;
- same four athletes shared by two types still produce only one team.

## Architectural direction

The cleanest shape is to keep **eligibility** and **selection preference** separate:

- Eligibility graph:
  - capped athlete -> exactly one permanent-nationality type;
  - uncapped athlete -> all valid printed types.
- Team-set solver:
  - maximize the number of four-athlete teams globally.
- Roster assignment inside that maximum team set:
  - choose the strongest legal selected athlete set;
  - use multi-type relative-rank preference to decide placement where athletes compete across teams;
  - use deterministic ordinal/rating tie-breaks.
- Capped state should not be part of the assignment score because its entire meaning has already been expressed by the eligibility edges.

Avoid the current pattern where a feasibility optimization (`CollectGuaranteedTeams`) also chooses the permanent roster. A team being guaranteed to **exist** is not equivalent to four particular athletes being guaranteed to **play**.

If a lexicographic min-cost encoding is used, make the priorities explicit and tested rather than relying on magic constants that accidentally dominate sporting quality.

## Acceptance criteria

- [ ] A Type Cup nationality restricts eligible teams but gives no selection bonus.
- [ ] A type with four capped/exclusive athletes is not automatically frozen to those four.
- [ ] Stronger eligible uncapped athletes can displace weaker capped athletes.
- [ ] A higher-rated eligible athlete is not left unassigned solely because a weaker athlete is capped/exclusive.
- [ ] The Mockery-of-Nature-style dual-type case selects the strong athlete for exactly one eligible team instead of neither.
- [ ] Wizard-style squads no longer retain weak capped #9/#10-ranked athletes when materially stronger eligible athletes are available and can legally fill those places.
- [ ] Maximum number of fielded Type Cup teams is preserved.
- [ ] Multi-type conflicts are still resolved globally rather than greedily per team.
- [ ] Relative type preference still has a deterministic role in deciding multi-type placement.
- [ ] Permanent nationality remains strict: capped athletes can never represent another type.
- [ ] Type Cup selection rating formula and fixed-point scoring are unchanged.
- [ ] Selection report ranking/outcome/reason data matches the corrected allocation.
- [ ] Legacy capped-first helper behaviour is removed or made consistent with the corrected rules.
- [ ] Regression tests cover weak capped lock-in, capped-cost priority, dual-type stranded athlete, overlap/max-cardinality, preference, and nationality.
- [ ] Existing Type Cup kernel/API tests pass.

## Out of scope

- Changing the Type Cup selection rating weights or normalization formula.
- Changing active bonus, season performance, recent form, or career prestige calculations.
- Changing when an athlete becomes permanently capped.
- Allowing a capped athlete to change nationality.
- Changing Type Cup competition scoring, rounds, medals, honours, or titles.
- Changing Color Cup selection.
- Introducing RNG or probabilistic squad selection.
- Broad UI redesign of the Type Cup reveal/report beyond any wording needed to make corrected allocation reasons accurate.

# MB-012 — Add UCL Fantasy league standings slash command and change-only scheduled notifications

## Goal

Add league standings support for UEFA Champions League Fantasy to MandarinBotNet. Users must be able to request the latest table using `/uclstandings`, while a scheduled job checks the configured UCL league and posts to Discord **only after a meaningful change in the standings**. Repeated polls with identical results must remain silent, even across bot restarts.

## Context

- Project: `mandarinbotnet`; target: `AlexBDevCorner/MandarinBotNet` (default branch `main`).
- Existing UCL functionality is limited primarily to public UEFA feed-based deadlines, under `DiscordBot.UclFantasy/`; it already has `IUclFantasyClient`, resilient `HttpClient` registration, `UclDeadlineNotificationJob`, and related tests.
- Existing FPL standings slash commands, jobs and notification infrastructure offer patterns for formatting, Quartz registration, configurable targets, and SQLite checkpoints.
- MB-011 fixes repeated unchanged *FPL* classic standings and introduces/extends semantic change tracking per successfully delivered Discord target. Reuse its mechanism where appropriate, but do not change FPL behavior in this task.
- The user tested the following UCL classic league leaderboard GET URL in a fresh **Incognito** browser session without signing in, and confirmed that it returns league data:
  `https://gaming.uefa.com/en/uclfantasy/services/api/Leagues/25247707/leagueleaderboard?optType=1&phaseId=1&matchdayId=1&vPageChunk=25&vPageNo=1&vPageOneChunk=25&leagueID=25247707&buster=qb8msw8gn1786610121299`
- Configured UCL league numeric ID: `25247707`. Its existing join link is defined as `UclLeagueUrl` in `DiscordBot/Commands/BotHelpMessageCompositionService.cs`.
- This is an **observed anonymously accessible endpoint**, not a documented compatibility guarantee. Parameter semantics and current-season response structure should be validated during implementation. Google OAuth, UEFA sign-in, cookies, and headless browser automation are not required for the observed request.
- UEFA may restrict automated access in its terms; do not bypass access controls. Keep requests moderate and configurable and document operational limitations.

## Requirements

### 1. Fetch complete UCL standings

1. Add a read-only UCL league standings client/service using the existing typed `HttpClient`, timeout, retry and cancellation patterns. Reuse existing UCL infrastructure where sensible.
2. Use the verified endpoint and league ID above as the starting point. Keep the league ID configurable (e.g. `Bot__UclFantasy__LeagueId=25247707`) rather than embedding it in business logic.
3. Investigate which query parameters are mandatory. Do not require or generate a new Google/UEFA login; remove the `buster` only if a request without it succeeds. Do not assume `phaseId=1`, `matchdayId=1`, or `optType=1` has the same semantic meaning forever; obtain current values from relevant source data or validated response/configuration as needed so that standings stay current across matchdays.
4. Follow all available standings pages, using total members/page information where available. Bound requests with a configurable or defensible maximum; never treat a partial or inconsistent multi-page fetch as a complete table. Handle empty, malformed, unauthorized/rate-limited, and transient responses safely.
5. Normalize each member using stable identities, team/manager names, rank, overall points, matchday points, and any available useful rank-change metadata. Preserve ties and deterministic ordering. Keep transport models separate from the presentation model.

### 2. Add `/uclstandings`

1. Register a dedicated `/uclstandings` slash command in the existing Discord command system, independent of FPL's `/standings`.
2. On every invocation, fetch and show current standings even when nothing changed since the previous request. Include league name/identity, ranks, team names, and points; show current matchday and movement information only when data supports it.
3. Display the complete standings using a Discord-appropriate bounded/paginated response (for example, an optional page argument). Do not silently truncate members, exceed Discord limits or require a privileged role for ordinary read-only access.
4. Fail gracefully with useful user-facing messages if UEFA is unavailable or the data is invalid. Manual command requests must not alter scheduled notification change checkpoints.

### 3. Schedule notifications *only* on changes

1. Add a Quartz job with enable flag and configurable cron expression, using the existing `Europe/Riga` scheduling model. Default to polling about every **15 minutes** when enabled; tracked configuration stays disabled by default. Do not send a Discord message on every scheduled execution.
2. On a successful poll, compute a deterministic semantic representation of the **complete** standings before composing text: include stable league/season/round identity where meaningful, members, rank/order, points, and other actual user-visible league changes. Ignore source timestamps, `buster`, request ordering, decorative/randomized wording and other non-standings metadata.
3. Send a scheduled summary only if this semantic snapshot differs from the last successfully announced snapshot **for that notification target**. Changes to points, rankings, participants, names, or relevant matchday results qualify. An unchanged top three does *not* excuse changes elsewhere in the league; compare the complete table.
4. A new deployment with no previous state should record a safe baseline **without sending an unsolicited initial standings post**. Subsequent real changes should trigger one announcement per target. Persist baseline/publication state across restarts using the existing SQLite infrastructure.
5. Update a target's published baseline only after successful delivery to that target. Isolate partial failures: a failed target can retry, while a target that already received the change stays silent. Recognize A -> B -> A as two genuine changes (do not use a permanent 'ever seen this hash' suppression set).
6. An API failure, incomplete pagination, invalid/empty transient response, scheduler rerun or process restart must never replace the good baseline or cause spurious notifications. Handle overlapping runs without duplicate delivery.
7. Make the scheduled message useful: state the league and latest standings, highlight changed ranks/points/participants where available, and present at least a concise leaderboard view. If relevant changes are outside the displayed leaders, summarize/highlight those changes rather than announcing an unchanged-looking table. Respect Discord length constraints and existing notification target settings.
8. Preserve existing per-channel notification routing, mention policy, and idempotent publishing. No @everyone ping by default. Record explicit job outcomes such as `SkippedUnchangedStandings`, delivered, failed, and source unavailable in logs, without posting 'no changes' messages.

### 4. Configuration and documentation

1. Expose the league ID, schedule enable/cron, appropriate page/request bounds, and any other required read-only UCL options through the established `Bot` configuration model; validate necessary settings when this feature is enabled.
2. Document `/uclstandings`, how to enable the scheduled job and its notification targets, the default poll interval, the anonymous endpoint assumption, and the initial silent baseline in `docs/bot-configuration.md`. Update the bot help text as appropriate.
3. Keep any API-specific decisions (query-option mapping, latest matchday detection, pagination) documented and backed by focused tests or captured non-sensitive fixtures, so a future UEFA API change is diagnosable.

## Architectural direction

- Prefer `DiscordBot.UclFantasy/` for the UCL HTTP/standings models, fetch service, message composer and Quartz job, and follow existing command registration patterns in `DiscordBot/`.
- Examine the outcome of MB-011 before implementing state tracking. Reuse the existing SQLite-based notification persistence, semantic snapshot techniques and per-target delivery model rather than inventing an independent database or polling daemon.
- Keep the slash command read-only and stateless regarding announcement suppression. Source retrieval and semantic comparison should be independently unit-testable.
- Use tests with mock/fake HTTP handlers and Discord transports. The test suite must not depend on live UEFA, Discord, Google, or a particular matchday.
- Avoid unrelated changes to FPL jobs, other UCL deadline reminders, EventWatch, or Discord infrastructure.

## Acceptance criteria

- [ ] `/uclstandings` is registered and can fetch current league `25247707` standings anonymously through a configured read-only API client.
- [ ] The command displays meaningful rank/team/points data and allows all league members to be viewed without hitting Discord response limits.
- [ ] The fetcher handles multiple pages, duplicate/tied ranks, invalid payloads, and error statuses without silently reporting a partial table as complete.
- [ ] Matchday/phase-specific parameters are validated and handled for current standings; the feature does not hard-code matchday 1 as 'current' forever.
- [ ] A configurable, disabled-by-default Quartz job can poll approximately every 15 minutes.
- [ ] The first valid scheduled snapshot initializes state silently, then an actual standings change sends one notification per configured target.
- [ ] Identical results on successive polls and after restart produce no additional messages, regardless of volatile metadata, ordering, or message wording.
- [ ] Changes to non-podium entries also trigger a notification and are reflected in the message.
- [ ] A -> B -> A is treated as genuine changes; delivery failure for one target does not affect another target's checkpoint or suppress its retry.
- [ ] Failure, partial pagination or malformed data cannot overwrite the last good snapshot or cause false alerts.
- [ ] The slash command always returns the latest data and does not change the scheduled announcement baseline.
- [ ] Jobs and commands retain existing notification routing, logging, help/documentation and safe default configurations.
- [ ] Deterministic tests cover data parsing, pagination, parameter handling, semantic change detection, initial baseline, retries/per-target isolation, restarts and command behavior.
- [ ] Build, tests and format verification succeed.

## Verification

Run from the MandarinBotNet repository root:

```sh
dotnet restore MandarinBotNet.sln --locked-mode
dotnet build MandarinBotNet.sln --configuration Release --no-restore
dotnet test MandarinBotNet.sln --configuration Release --no-build --no-restore
dotnet format MandarinBotNet.sln --verify-no-changes --no-restore
```

Add integration-style tests with recorded/redacted fixture JSON for two pages of the standings and compare scheduled runs:

1. A (first valid fetch) -> no Discord post, baseline stored.
2. A again (including a changed timestamp, buster, or response order) -> no post.
3. B (change in points/rank of a member outside the top three) -> one post per target, with the changed member visible in summary.
4. B again and B after app restart -> no post.
5. A again -> one new post per target.
6. Delivery to target 1 succeeds and target 2 fails -> target 2 retries without resending to target 1.
7. Bad API response or missing page -> no state update and no post.
8. `/uclstandings` works on both changed and unchanged snapshots without touching scheduled notification state.

During manual verification, validate the configured league ID, query parameter semantics, current matchday behavior and complete pagination against the real UEFA API. Do not make this live check a dependency of CI.

## Out of scope

- Google OAuth integration, session cookies, browser automation or account credentials.
- Squad/transfer management, lineup inspection, private account information or any write calls to UEFA.
- Full FPL feature parity (achievements, managers' profiles, advanced live insights, chips, historical backfill, H2H); these can be separate tasks.
- Redesign of existing FPL standings, reminder jobs, or the Discord notification framework.
- Posting identical standings daily or posting a 'no changes' Discord status message.
- Circumventing UEFA authentication, rate limits, bot restrictions or contractual access controls.

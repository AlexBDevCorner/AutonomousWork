# MB-006 — Use Discord-native timestamps in scheduled deadline reminders

## Goal

Update MandarinBotNet's scheduled FPL and UEFA Champions League fantasy deadline
notifications to use Discord-native timestamp markup instead of manually
formatting a Riga-local deadline plus a custom calculated remaining duration.

Discord should render the deadline in each user's own local timezone and render
the relative countdown itself. This makes deadline reminders clearer for users
outside Latvia and avoids maintaining duplicate timezone/countdown formatting
logic in the bot.

## Context

- Project: `mandarinbotnet`.
- Target repository: `AlexBDevCorner/MandarinBotNet`.
- Default target branch: `main`.
- Discord supports native timestamp markup in the form `<t:UNIX:STYLE>`.
- The existing interactive `/deadline` command already uses a native relative
  timestamp:
  - `DeadlineCommandHandler.FormatDeadline()` converts
    `deadline.DeadlineUtc` to Unix seconds;
  - it emits `<t:{timestamp}:R>`.
- The scheduled deadline notifications do not currently use Discord-native
  timestamps:
  - `PremierLeagueNotificationJob` calls
    `PremierLeagueMessageCompositionService.ComposeDeadlineReminder()`;
  - `UclDeadlineNotificationJob` calls
    `UclFantasyMessageCompositionService.ComposeDeadlineReminder()`.
- `PremierLeagueMessageCompositionService.ComposeDeadlineReminder()`
  currently:
  - converts the deadline to the configured Riga timezone;
  - formats a Russian absolute date/time;
  - calculates the remaining duration itself through
    `DateTimeUtility.GenerateRemainingDaysMessageInRussian()`.
- `UclFantasyMessageCompositionService.ComposeDeadlineReminder()` currently:
  - converts the deadline to the configured Riga timezone;
  - formats a Russian absolute date/time;
  - calculates remaining hours/minutes itself.
- Discord-native timestamps are preferable for these notifications because
  Discord can display the same deadline according to each user's locale and
  timezone and can keep the relative value current on the client side.

## Requirements

1. Change the scheduled FPL deadline reminder composed by
   `PremierLeagueMessageCompositionService.ComposeDeadlineReminder()` so the
   actual deadline is represented using Discord-native timestamp markup.

2. Change the scheduled UCL deadline reminder composed by
   `UclFantasyMessageCompositionService.ComposeDeadlineReminder()` in the same
   way.

3. Generate Discord timestamp values from the actual UTC deadline using
   `DateTimeOffset.ToUnixTimeSeconds()`. Formatting must be culture-independent.

4. Each scheduled reminder must include both:
   - an absolute Discord timestamp for the deadline, using a suitable absolute
     style such as `<t:UNIX:F>`;
   - a relative Discord timestamp using `<t:UNIX:R>`.

5. The message must no longer depend on a hard-coded/display-specific Riga time
   to communicate when the deadline occurs. Discord's absolute timestamp should
   be the primary deadline representation so each user sees it in their own
   timezone.

6. Remove the custom remaining-time calculation from the scheduled reminder
   output where it is used only to produce text such as:
   - the FPL Russian remaining-days/hours message;
   - the UCL manually calculated `X ч Y мин` countdown.

   Discord's `:R` timestamp must be used for the user-facing relative
   countdown instead.

7. Preserve the existing purpose and recognizable wording of both reminders:
   - FPL reminders must still clearly identify that the next FPL gameweek
     deadline is approaching;
   - UCL reminders must still clearly identify the Champions League fantasy
     matchday deadline.

8. Preserve the existing scheduled-notification behavior outside message
   composition, including:
   - reminder eligibility windows;
   - 24-hour and 1-hour notification types;
   - Quartz scheduling;
   - notification targets;
   - deduplication/checkpoint behavior;
   - retry/error handling.

9. The interactive `/deadline` command must continue to work and continue to
   use Discord-native timestamps. This task must not regress its existing
   relative timestamp output.

10. If a small shared timestamp-formatting helper makes the implementation
    cleaner, it may be introduced and reused by the scheduled reminders and
    `/deadline`. Do not create a larger formatting abstraction unless needed.

11. Update automated tests for the FPL and UCL message composers so they assert
    the exact Discord timestamp markup generated from known deadlines.

12. Test at least:
    - a known FPL deadline produces the expected Unix timestamp in both the
      absolute and relative Discord forms;
    - a known UCL deadline produces the expected Unix timestamp in both forms;
    - daylight-saving changes do not alter the Unix timestamp representation;
    - scheduled reminder text no longer contains the old manually calculated
      remaining-duration output;
    - `/deadline` still contains its native relative timestamp.

13. Update user-facing documentation only if existing documentation describes
    the scheduled deadline timestamp/countdown formatting in a way that becomes
    incorrect after this change.

## Architectural direction

Keep this as a message-composition change. The deadline providers, eligibility
logic, jobs, scheduling, notification publisher, and persistence/checkpoint
behavior already provide the correct UTC deadline and should not be redesigned.

The intended message structure is conceptually:

```text
<competition-specific reminder text>
Дедлайн: <t:UNIX:F>
Осталось: <t:UNIX:R>
```

Exact Russian wording may remain consistent with the current bot personality.
The important behavior is that Discord receives native timestamp markup rather
than a pre-rendered Riga-local date/time and a bot-calculated countdown.

Use the same Unix timestamp for both absolute and relative forms. Do not convert
the deadline to a local timezone before generating the Unix value.

Prefer a small focused implementation. A shared helper is reasonable if it
removes obvious duplication between the existing `/deadline`, FPL reminder,
and UCL reminder paths, but introducing a new general-purpose date/time
framework is not justified.

## Acceptance criteria

- [ ] Scheduled FPL deadline notifications contain an absolute Discord
      timestamp generated from the real FPL deadline.
- [ ] Scheduled FPL deadline notifications contain a relative
      `<t:...:R>` timestamp for the same deadline.
- [ ] Scheduled UCL deadline notifications contain an absolute Discord
      timestamp generated from the real UCL deadline.
- [ ] Scheduled UCL deadline notifications contain a relative
      `<t:...:R>` timestamp for the same deadline.
- [ ] The bot no longer manually renders Riga-local time as the primary deadline
      representation in scheduled FPL/UCL reminders.
- [ ] The scheduled reminders no longer manually calculate user-facing
      remaining days/hours/minutes where Discord `:R` provides that value.
- [ ] FPL and UCL reminder eligibility and scheduling behavior are unchanged.
- [ ] Notification deduplication/checkpoint behavior is unchanged.
- [ ] The interactive `/deadline` command still emits Discord-native relative
      timestamps.
- [ ] Tests verify exact Unix timestamp markup for deterministic known
      deadlines.
- [ ] Tests cover deadlines across different Riga UTC offsets/DST periods and
      prove the Unix timestamp remains based on the UTC instant rather than on
      formatted local time.
- [ ] `dotnet build MandarinBotNet.sln` succeeds.
- [ ] `dotnet test MandarinBotNet.sln` succeeds.

## Verification

Run in the target repository:

```sh
dotnet build MandarinBotNet.sln
dotnet test MandarinBotNet.sln
```

For deterministic unit tests, use known `DateTimeOffset` deadline values and
assert that the composed message contains both:

```text
<t:EXPECTED_UNIX:F>
<t:EXPECTED_UNIX:R>
```

Also verify that the scheduled FPL and UCL message tests no longer expect the
old manually formatted Riga-local countdown strings.

Verify the existing `DeadlineCommandHandlerTests` continue to pass and still
prove that `/deadline` emits a native `<t:...:R>` timestamp.

## Out of scope

- Changing FPL or UCL deadline data sources.
- Changing how upcoming deadlines are selected.
- Changing 24-hour or 1-hour reminder eligibility windows.
- Changing Quartz schedules or job frequency.
- Changing Discord channels/guild targets.
- Changing notification deduplication or delivery checkpoints.
- Adding Discord embeds, buttons, components, or interactions.
- Rewriting unrelated date/time formatting elsewhere in MandarinBotNet.
- Changing the bot's configured timezone for features that still legitimately
  need Riga-local time.
- Changing unrelated FPL, UCL, price-change, EventWatch, deployment, or
  AutonomousWork behavior.

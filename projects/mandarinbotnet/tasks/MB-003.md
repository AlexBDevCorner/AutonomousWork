# MB-003 — Add reusable Riga FC ticket-sale monitoring and Discord alerts

## Goal

Add a small reusable EventWatch capability to MandarinBotNet that checks Riga FC's
official website every 10 minutes for evidence that tickets for the Riga FC vs
Atalanta match are on sale and sends useful Discord notifications exactly once.

The implementation should solve the Atalanta use case now without turning
MandarinBotNet into a general-purpose web-scraping platform.

## Context

- Project: `mandarinbotnet` (`projects/mandarinbotnet/project.yaml`).
- Target repo: `AlexBDevCorner/MandarinBotNet`.
- Default target branch: `main`.
- MandarinBotNet already has the required platform pieces:
  - Quartz scheduling through
    `MandarinBotNet/Extensions/MandarinBotQuartzExtensions.cs`;
  - centralized schedule definitions in
    `DiscordBot.Common/Jobs/JobSchedules.cs`;
  - configuration and startup validation in
    `DiscordBot.Common/MandarinBotOptions.cs` and
    `DiscordBot.Common/MandarinBotOptionsValidator.cs`;
  - resilient HTTP-client patterns;
  - Discord delivery through
    `IDiscordNotificationPublisher`;
  - persisted notification checkpoints that prevent duplicate delivery.
- This feature is not Fantasy Premier League or UCL Fantasy functionality.
  It should have its own domain boundary.
- The initial watch is:
  - ID: `riga-fc-atalanta-2026`;
  - title: `Riga FC vs Atalanta tickets`;
  - match term: `Atalanta`.
- Official Riga FC pages to inspect in the MVP:
  - `https://rigafc.lv/`
  - `https://rigafc.lv/kalendars/`
  - `https://rigafc.lv/jaunumi/`
- Riga FC pages can expose ticket links using Latvian text such as
  `Biļetes`.
- Do not directly poll Biļešu Serviss in this task. The intended detection path
  is the official Riga FC website; a detected outbound ticket URL can still be
  included in the Discord notification.

## Requirements

1. Introduce a dedicated `DiscordBot.EventWatch` project targeting the same
   .NET version as the solution and reference it from the application and test
   projects as needed.
2. Keep the EventWatch domain independent from FPL and UCL projects. Core
   EventWatch models must not depend on Quartz, Discord.Net, or HTML DOM types.
3. Support configured event watches with at least:
   - `Enabled`;
   - stable `Id`;
   - human-readable `Title`;
   - one or more `MatchTerms`;
   - a dedicated list of Discord `Targets` using the existing
     `NotificationTargetOptions` shape (`GuildId`, `ChannelId`,
     `MentionEveryone`). Each watch owns its targets; EventWatch MUST NOT
     automatically publish to the general `Bot:Notifications:Targets` list.
4. Add an EventWatch Quartz schedule to the existing schedule configuration:
   - default cron: `0 0/10 * * * ?`;
   - repository default must be disabled;
   - when enabled, at least one valid enabled watch must exist;
   - watch IDs must be non-empty and unique;
   - titles and match terms must be non-empty;
   - every enabled watch must have at least one valid dedicated Discord target;
   - every EventWatch target must have non-zero `GuildId` and `ChannelId`;
   - existing cron/startup validation patterns must be followed.
5. Include the initial repository configuration for
   `riga-fc-atalanta-2026`, searching for `Atalanta`. The configuration
   structure must allow this watch to use a different Discord channel from the
   bot's existing general notification targets. Repository defaults must not
   contain real Discord guild/channel IDs.
6. Implement a typed or otherwise DI-managed Riga FC HTTP client that retrieves
   the homepage, calendar, and news pages separately. It must:
   - use the existing resilient HTTP-client conventions where practical;
   - send a truthful MandarinBotNet user agent and accept HTML;
   - propagate cancellation;
   - fail observably on non-success HTTP responses rather than returning an
     empty page;
   - not follow or crawl arbitrary links discovered in page content.
7. Parse HTML into stable structured observations rather than comparing whole
   page checksums. At minimum expose:
   - source URL;
   - normalized visible text;
   - anchor text;
   - absolute anchor URL;
   - enough nearby context to associate a link with the relevant match.
8. Use a real HTML parser such as AngleSharp (centrally versioned if a new
   package is introduced). Regex must not be the primary HTML parser.
9. Detection must be semantic and resilient to unrelated layout changes.
   It must not depend on fragile DOM paths such as nth-child selectors.
10. Detect exactly two signal kinds in the MVP:
    - `Announcement`: the relevant match is mentioned together with clear
      ticket-sale wording;
    - `TicketLinkAvailable`: the relevant match context contains an
      actionable ticket link.
11. Match detection for the initial watch is case-insensitive on `Atalanta`.
    Do not require the word `Riga` because the source is Riga FC's official
    site.
12. Ticket-sale vocabulary should cover the useful Latvian/English forms,
    including at least:
    - `biļete`, `biļetes`, `biļešu`;
    - `ticket`, `tickets`;
    - `pārdošanā`, `iegādāties`, `pirkt`.
13. The detector must not notify for:
    - a plain Atalanta fixture with no sale information;
    - an unrelated or historical Atalanta mention;
    - an Atalanta mention combined only with a generic site-wide `Biļetes`
      navigation link;
    - unrelated page changes.
14. If the same observation proves both sale announcement and direct ticket
    availability, emit both logical signal kinds. They are independently useful
    user events.
15. Add two centralized notification types, equivalent to:
    - `event-watch-announcement`;
    - `event-watch-ticket-link`.
16. Publish through the existing `IDiscordNotificationPublisher`; do not build
    a second notification persistence/deduplication store. The publisher must be
    called only for the dedicated targets configured on the matching EventWatch
    definition, not for `Bot:Notifications:Targets`.
17. Use a stable source identifier derived from the watch ID, for example
    `event-watch:riga-fc-atalanta-2026`. It MUST NOT contain detection time,
    polling time, or other per-run data.
18. Existing notification checkpoints must ensure:
    - one Announcement can be delivered once per configured EventWatch target;
    - one TicketLinkAvailable can later be delivered once per configured
      EventWatch target;
    - subsequent identical polling runs do not repeat either notification;
    - failed delivery can still be retried according to the existing publisher
      semantics.
19. Compose actionable Discord messages:
    - Announcement message identifies the watched event and official Riga FC
      source URL;
    - TicketLinkAvailable message includes the detected ticket URL and source
      URL;
    - existing `MentionEveryone` behavior from `NotificationTargetOptions`
      may be used for these notification types rather than introducing a new
      mention mechanism;
    - `MentionEveryone` is configured independently for this watch's dedicated
      target(s), so enabling it for the ticket alert does not change unrelated
      bot notifications.
20. Implement `EventWatchJob` as a Quartz `IJob` and register it through the
    existing `AddMandarinBotScheduling()` path.
21. Prevent overlapping EventWatch executions with the normal Quartz
    non-concurrent-execution mechanism.
22. One failing Riga FC page must not prevent the remaining official pages from
    being evaluated. One failing Discord target must not prevent attempts to
    deliver to the other configured targets.
23. The job must log structured operational information sufficient to diagnose:
    - watch ID;
    - source fetch outcome;
    - number/type of detected signals;
    - delivery outcome.
    Entire HTML documents must never be logged.
24. Add representative offline HTML fixtures and automated parser/detector tests.
    Tests must include at least:
    - Atalanta absent -> no signal;
    - Atalanta present without ticket wording -> no signal;
    - Atalanta plus generic navigation `Biļetes` -> no signal;
    - sale announcement -> Announcement;
    - associated ticket link -> TicketLinkAvailable;
    - announcement plus ticket link -> both;
    - case-insensitive Atalanta matching;
    - duplicate observations from multiple Riga FC pages collapse to one logical
      signal per kind.
25. Add automated tests for:
    - configuration defaults and validation, including required per-watch
      targets and invalid zero guild/channel IDs;
    - proof that EventWatch uses only its own configured targets and does not
      fall back to or broadcast through `Bot:Notifications:Targets`;
    - EventWatch Quartz registration and 10-minute cron;
    - HTTP success/failure/cancellation behavior;
    - absolute/relative link normalization;
    - notification source identifier stability;
    - one-time delivery behavior for both signal kinds.
26. Add at least one vertical-slice test using fake Riga FC HTTP responses and a
    fake notification publisher proving this sequence:
    1. no sale information -> no notification;
    2. sale announcement appears -> one Announcement;
    3. unchanged page -> no duplicate;
    4. direct ticket link appears -> one TicketLinkAvailable;
    5. unchanged page -> no duplicate.
27. Register EventWatch services through a small EventWatch-specific service
    collection extension rather than adding a long list of individual
    registrations to the application composition root.
28. Update `docs/bot-configuration.md` (or the current equivalent configuration
    document if it has been renamed) with:
    - how to enable/disable EventWatch;
    - the 10-minute cron value;
    - the initial Atalanta watch configuration;
    - how to configure its dedicated `GuildId`, `ChannelId`, and
      `MentionEveryone`;
    - environment-variable examples for deployment, such as
      `Bot__EventWatch__Watches__0__Targets__0__GuildId`,
      `Bot__EventWatch__Watches__0__Targets__0__ChannelId`, and
      `Bot__EventWatch__Watches__0__Targets__0__MentionEveryone`;
    - the fact that repository defaults remain disabled and contain no real
      Discord IDs.
29. Existing bot behavior and existing scheduled jobs must remain unchanged when
    EventWatch is disabled.

## Architectural direction

Model the capability around reusable domain concepts rather than an
`AtalantaTicketJob`. A suitable shape is:

- `EventWatchDefinition`
- `EventWatchSignal`
- `EventWatchSignalKind`
- `EventWatchService`
- `IEventWatchSource`
- `RigaFcEventWatchSource`
- `RigaFcClient`
- `RigaFcPageParser`
- `EventWatchSignalDetector`
- `EventWatchMessageCompositionService`
- `EventWatchJob`

A reasonable dependency direction is:

`MandarinBotNet -> DiscordBot.EventWatch -> DiscordBot.Common`

Keep source-specific website knowledge inside the Riga FC source/client/parser.
Configuration should describe what event to watch and where that watch should
notify; it does not need to expose Riga FC page URLs for this first
implementation.

Model Discord routing at the watch level. A representative configuration shape
is:

```json
"EventWatch": {
  "Watches": [
    {
      "Enabled": true,
      "Id": "riga-fc-atalanta-2026",
      "Title": "Riga FC vs Atalanta tickets",
      "MatchTerms": [ "Atalanta" ],
      "Targets": [
        {
          "GuildId": 0,
          "ChannelId": 0,
          "MentionEveryone": true
        }
      ]
    }
  ]
}
```

The zero IDs above are placeholders only; real IDs belong in deployment/runtime
configuration. EventWatch MUST use these per-watch targets and MUST NOT inherit
or enumerate the general `Bot:Notifications:Targets` collection.

Prefer generic semantic extraction (visible text, anchors, nearby context) over
site-layout-specific selectors. Whole-page hashing is explicitly discouraged
because unrelated scores, news, videos, and galleries can change frequently.

Reuse existing Discord notification checkpoints as the persistent state for the
MVP. Do not add an EventWatch database table merely to remember that a
notification was already sent.

The implementation should be reusable enough to add another
`IEventWatchSource` or another configured watch later, but no generic crawler,
browser automation, plugin system, or user-editable scraping DSL is required.

## Acceptance criteria

- [ ] `DiscordBot.EventWatch` exists as a separate domain project and the
      solution builds successfully.
- [ ] Repository defaults contain a disabled EventWatch schedule with cron
      `0 0/10 * * * ?`.
- [ ] Repository configuration contains the
      `riga-fc-atalanta-2026` watch with a dedicated-target configuration
      shape but no committed real Discord IDs.
- [ ] EventWatch notifications are routed only to the target(s) configured for
      that watch and are not broadcast to `Bot:Notifications:Targets`.
- [ ] When EventWatch is disabled, no EventWatch Quartz job is registered.
- [ ] When enabled, the job checks the three official Riga FC pages every
      10 minutes without overlapping itself.
- [ ] A normal Atalanta fixture mention does not generate a ticket alert.
- [ ] A qualifying sale announcement generates one Announcement notification
      per target.
- [ ] A qualifying direct ticket link generates one TicketLinkAvailable
      notification per target and includes the actionable URL.
- [ ] Re-running against unchanged qualifying content produces no duplicate
      notification.
- [ ] Announcement and TicketLinkAvailable can each be delivered once for the
      same watch.
- [ ] No direct Biļešu Serviss polling is introduced.
- [ ] One failed Riga FC source does not suppress successful evaluation of the
      other official Riga FC sources.
- [ ] Existing MandarinBotNet jobs/tests continue to behave unchanged.
- [ ] Automated unit/integration tests cover the required positive and
      false-positive cases.
- [ ] Configuration documentation explains how to enable the feature.
- [ ] `dotnet build MandarinBotNet.sln` succeeds.
- [ ] `dotnet test MandarinBotNet.sln` succeeds.

## Verification

Run in the target repository:

```sh
dotnet build MandarinBotNet.sln
dotnet test MandarinBotNet.sln
```

Also verify the implementation with the automated vertical-slice fixture
sequence required above.

For a real non-destructive smoke check, enable EventWatch in a local or deployed
test configuration and run one scheduled/manual job execution. Confirm that:

1. the Riga FC homepage, calendar, and news sources are fetched;
2. the job logs source outcomes and detected signal counts without logging raw
   HTML;
3. no Discord notification is sent when no qualifying sale signal exists;
4. configure the Atalanta watch with a test Discord target distinct from the
   normal bot notification target and confirm any controlled test delivery path
   selects only that EventWatch target;
5. disabling EventWatch removes the scheduled EventWatch job on the next
   process start.

Do not fabricate a production ticket-sale page or send a synthetic production
`@everyone` alert merely to prove the positive path; the positive path is
covered by offline fixtures/tests.

## Out of scope

- Direct polling/scraping of Biļešu Serviss.
- Browser automation for Riga FC or ticket-provider pages.
- Instagram, Facebook, X, or other social-media API integration.
- Google/Bing/news-search fallback monitoring.
- Generic web-crawler or scraping-framework infrastructure.
- A user-configurable scraping DSL or arbitrary user-supplied URLs/selectors.
- A new EventWatch persistence database/table solely for notification
  deduplication.
- Changes to AutonomousWork dispatcher/reviewer/reconciler behavior.
- Changes to unrelated FPL/UCL feature behavior.
- Automatically enabling the feature in a production environment or changing
  production secrets/configuration outside the repository.
- Adding secondary sources; create a follow-up task if additional Riga FC
  pagination/API discovery or an acceptable Biļešu Serviss machine-readable
  source is later required.

# MB-011 — Stop repeating unchanged FPL classic league standings on Discord

## Goal

Prevent MandarinBotNet's scheduled **classic FPL league standings** notification
from sending effectively identical Discord posts on consecutive days. Publish
when there is a meaningful change in the league results, not merely because
the FPL API updates a timestamp or the message composer selects another
congratulatory phrase. Keep the job scheduled and retain genuine new updates.

## Context

- Project: `mandarinbotnet`; target repository:
  `AlexBDevCorner/MandarinBotNet`, branch `main`.
- User-provided Discord screenshots from 5, 6, 7, and 8 October 2026 show
  four consecutive 17:00 posts from Hug Bot for
  `🏆 Лига Пельменных Обнимашек`.
- All four report the same podium: Antony The Beaver 319,
  FC Laimdots 295, FC Jam 249. All congratulate Antony The Beaver for
  74 points in the most recent gameweek. Only the wording of the
  congratulations varies.
- `DiscordBot.FantasyPremierLeague/Jobs/PremierLeagueClassicStandingsInformationJob.cs`
  currently uses `ClassicStandingsResponse.LastUpdatedData` as
  `sourceIdentifier` for `PublishOnceAsync`. This deduplicates identical
  timestamps, **not identical standings**. The API timestamp can change
  without a meaningful difference in the posted result.
- The same job selects a random congratulations variant using
  `Random.Shared.Next(PremierLeagueMessageCompositionService.ClassicCongratulationsVariantCount)`.
  Random wording must not count as a new event.
- The existing `StandingsPublicationEligibilityService` checks whether
  source data was recently updated; that is a freshness check rather than
  a comparison against the last standings delivered.
- Delivery and per-channel idempotency are implemented in
  `DiscordBot.Common/Notifications/DiscordNotificationPublisher.cs`,
  `NotificationDeliveryCoordinator.cs`, and
  `SqliteNotificationCheckpointStore.cs`.
- `PremierLeagueH2hStandingsInformationJob` uses a different
  `MatchesPlayed` identifier. Do not accidentally change H2H semantics.

## Requirements

1. **Publish the classic standings only on meaningful changes.**
   - Compare the current league result against the most recently
     **successfully published** classic standings state for each Discord
     notification target.
   - A change in `LastUpdatedData`, the scheduler run date, current time,
     or random congratulations variant is **not** sufficient.
   - If the league table, relevant scores, and gameweek winner information
     represented in the post are unchanged, send nothing.
   - If rank/order, total points, current gameweek points, participants or
     relevant winner/tie information changes, the new snapshot is eligible
     for publication. Preserve genuinely new gameweek results where their
     event/round identity matters. Use the existing FPL models and
     authoritative API data; do not infer new gameweeks from wall-clock days.

2. **Use a stable, deterministic representation of meaningful results.**
   - Compute change identity before composing or randomizing the text.
   - Base comparison on normalized structured league data, with stable
     manager identifiers and consistent ordering. Capture all fields that
     materially affect the published result or its winner/rank commentary;
     exclude volatile timestamps, formatting and randomly selected phrases.
   - Distinguish classic league identity and, where needed, season/gameweek
     identity so different leagues/seasons/rounds do not mask each other.
   - An identical API snapshot must produce the same semantic comparison
     outcome regardless of response enumeration order or bot restart.
   - Avoid hashing the final rendered Discord message.

3. **Persist the last delivered state per target.**
   - Survive repeated scheduled runs, process restarts and deployments that
     preserve the existing SQLite state volume.
   - Keep each configured guild/channel independent. A successful send
     to channel A must not silence the same meaningful update for channel B.
   - Advance the last-delivered state only after actual successful delivery.
     If fetching, composing or delivery fails, the update must remain
     eligible for retry; handle partial target failures independently.
   - Reuse/extend the existing notification checkpoint infrastructure and
     SQLite persistence where practical; do not introduce a separate
     external database, cache, background scheduler or service.
   - Compare against the **latest** published snapshot, not merely whether
     a snapshot fingerprint has ever appeared: A -> B -> A must recognize
     the final return to A as a real change. Preserve existing
     `PublishOnceAsync` safeguards and avoid introducing delivery races
     or repetitive sends after restart.
   - Choose a safe and documented initial baseline for existing installations
     without stored standings snapshots. One initial publication is
     acceptable; the same unchanged snapshot must then remain silent.

4. **Keep the job's existing user-facing behavior when an update is real.**
   - Preserve the Russian standings message, podium, gameweek winner/tie
     congratulations and ranking movement commentary.
   - The random congratulations variants may remain for **newly published**
     updates, but cannot by themselves cause publication.
   - Do not change the cron schedule to suppress duplicates; the job should
     still check on its normal schedule.
   - Preserve the existing empty/invalid-data and API-failure behavior.
     In particular, a transient empty or malformed result must not replace
     a good baseline and suppress the next real update.
   - Keep the manual `/standings` command on-demand: it must return
     current information on every invocation regardless of scheduled
     notification suppression.

5. **Make skipping observable without Discord spam.**
   - Record a clear job result/log when the result is unchanged and no
     notification is sent (for example `SkippedUnchangedStandings`).
   - Keep existing useful delivered/skipped/failed per-target reporting.
     Do not post a "nothing changed" notice to Discord.

## Architectural direction

Start with `PremierLeagueClassicStandingsInformationJob`, the
`ClassicStanding` response model, the existing notification checkpoint
store and the relevant test suites under `DiscordBot.Tests/PremierLeague`
and `DiscordBot.Tests/Notifications`.

Prefer a small, testable semantic snapshot/comparison component and
per-target persisted last-successful-publication state in the established
SQLite notification storage. Keep source freshness distinct from whether
the results have changed. Preserve the existing publisher's retry and
per-target isolation behavior.

Do not solve this with an in-memory static variable, date-based cooldown,
a change to the random phrase selection, or merely replacing
`LastUpdatedData` with a content-hash source identifier in the existing
"ever delivered" checkpoint set (which would incorrectly suppress A -> B -> A).

## Acceptance criteria

- [ ] Running the classic standings job on 5, 6, 7, and 8 October-style
      snapshots (same podium, scores, 74-point winner, different API update
      timestamps and randomized text) publishes the unchanged results
      only once per configured Discord target.
- [ ] Re-running with an unchanged snapshot after restarting the process
      remains silent; SQLite persistence is exercised in tests.
- [ ] A genuine rank change, point change, entrant change, gameweek score
      change, winner/tie change or meaningful new round can be announced.
- [ ] Unstable input ordering and message variant choice do not cause
      extra notifications.
- [ ] A -> B -> A is recognized as two changes after initial A; the
      returned A result is not permanently suppressed.
- [ ] One target successfully notified and another target failing does not
      suppress the failed target's retry or duplicate the successful one.
- [ ] Failed delivery does not commit the new published baseline.
- [ ] No data/invalid API result does not overwrite the last good snapshot.
- [ ] Unchanged skips are identifiable in job logs/results, not sent to
      Discord.
- [ ] Scheduled classic league messages retain their existing Russian
      formatting and meaningful winner/movement details when changes occur.
- [ ] The `/standings` command remains an unrestricted on-demand snapshot,
      and unrelated H2H, recap, live insights, and other notification jobs
      remain unchanged.
- [ ] Build, tests and formatting verification succeed.

## Verification

1. Add focused tests for semantic equivalence and changes (including
   timestamp-only and randomized-text-only differences, ranking, scores,
   entries, winners, tied winners, a new gameweek and A -> B -> A).
2. Add job/persistence tests using the real SQLite checkpoint mechanism
   where appropriate, covering multiple channels, retries after failure,
   restart persistence and invalid/empty responses.
3. Verify that four back-to-back scheduled executions with the example
   snapshot send **one** Discord message, while the next actual standings
   change sends exactly one more per configured destination.
4. Verify `/standings` still returns a snapshot regardless of scheduled
   publication state.
5. Run from the MandarinBotNet repository root:

```sh
dotnet restore MandarinBotNet.sln --locked-mode
dotnet build MandarinBotNet.sln --configuration Release --no-restore
dotnet test MandarinBotNet.sln --configuration Release --no-build --no-restore
dotnet format MandarinBotNet.sln --verify-no-changes --no-restore
```

## Out of scope

- No reformatting or redesigning the Discord standings message.
- No changes to the 31 existing congratulatory text variants, except where
  required to prevent them influencing duplicate detection.
- No changes to FPL scores, winner rules, league calculations or API polling
  frequency.
- No redesign of the H2H standings job or other notification types.
- No global notification framework rewrite, new hosted services or external
  state infrastructure.
- No channel-wide spam filter or suppression of manual Discord commands.

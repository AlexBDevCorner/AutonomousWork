# MB-008 — Add EventWatch diagnostics and a safe live Riga FC smoke test

## Goal

Make the Riga FC ticket-monitoring feature verifiable in production instead of
requiring users to trust that a silent background job is working.

Add manual EventWatch diagnostics for the real fetch/parser/detector and Discord
delivery paths, and add a separate temporary smoke-test watch that can trigger
against ticket-related content that is already visible on Riga FC's website.

The smoke test must be completely isolated from the real
`riga-fc-atalanta-2026` watch so testing can never mark the future Atalanta
notification as delivered.

## Context

- Project: `mandarinbotnet`.
- Target repository: `AlexBDevCorner/MandarinBotNet`.
- Default target branch: `main`.
- EventWatch currently checks Riga FC's homepage, calendar, and news every
  10 minutes.
- The production Atalanta watch is:
  `riga-fc-atalanta-2026`.
- Real EventWatch notifications are checkpointed by watch-derived source
  identifier plus notification type, which correctly prevents duplicates but
  also means a fake test must never reuse the production watch identity.
- Current automated tests cover the detector and vertical notification flow,
  but there is no manual production diagnostic command.
- A production misconfiguration, Discord permission problem, HTTP/parser
  regression, or Riga FC markup change could therefore leave the feature
  silently producing no notification.

### Current live smoke-test candidate

Verified on **2026-09-23** on Riga FC's public calendar:

- Riga vs Kairat Almaty
- 15 October 2026, 19:45
- Skonto stadions
- the match entry currently exposes a **Tickets** action

Use `Kairat` as the primary temporary smoke-test match term while this entry
remains present.

Suggested isolated watch identity:

`riga-fc-smoke-kairat-2026`

This identity must never share a checkpoint source identifier with
`riga-fc-atalanta-2026`.

If the Kairat entry is no longer present by implementation time, choose another
currently visible Riga FC event that has ticket wording/action on the existing
EventWatch source pages. Keep the same principle: the smoke watch must target a
known-positive live page condition rather than weakening the detector or
matching arbitrary site-wide text.

## Requirements

### 1. Add an EventWatch status diagnostic

Add a Discord command for manually inspecting EventWatch health.

Preferred command shape:

`/eventwatch status`

The exact command structure may follow the repository's existing Discord command
architecture, but it must be discoverable and documented.

The status command must use the real production EventWatch components and report
enough information to diagnose the full detection side without publishing a
notification or mutating delivery checkpoints.

At minimum report:

- whether EventWatch scheduling is enabled;
- configured enabled watch IDs/titles;
- the configured source pages being checked;
- whether the live Riga FC collection completed;
- number of observations collected;
- per enabled watch:
  - configured match terms;
  - number/kinds of currently detected signals;
  - source URL for detected signal evidence where safe/useful;
- a clear healthy/no-signal result when fetch and parsing worked but no
  qualifying signal exists;
- a clear failure result if collection/parsing fails.

Do not dump raw HTML or excessive external page content into Discord or logs.

Running `/eventwatch status` must not:

- publish normal EventWatch alerts;
- mark announcement/ticket-link checkpoints delivered;
- alter scheduled EventWatch state.

### 2. Add a Discord delivery test

Add a manual command for verifying that EventWatch can actually deliver to its
configured dedicated targets.

Preferred command shape:

`/eventwatch test`

The test must:

- use the real EventWatch target configuration;
- use the real Discord destination resolution/sending path as far as practical;
- send a clearly labelled test message;
- identify which EventWatch target was tested;
- honor safe Discord mention behaviour and **must not use @everyone** for the
  test message even if the production EventWatch target has
  `MentionEveryone=true`;
- return a useful result to the invoking user when delivery succeeds/fails.

The test must be repeatable.

It must not consume or collide with either production EventWatch notification
checkpoint:

- `event-watch-announcement`
- `event-watch-ticket-link`

for `riga-fc-atalanta-2026`.

If the existing publisher requires checkpointed delivery, use an isolated test
source identifier / test notification identity that is unique and safe to rerun,
or add the smallest focused diagnostic path needed. Do not weaken duplicate
suppression for normal scheduled notifications.

### 3. Add a separate live smoke-test watch

Provide a separate configurable EventWatch definition for the known-positive
Riga FC page content.

Primary configuration while it remains current:

- ID: `riga-fc-smoke-kairat-2026`
- Title: a clearly labelled smoke/test title
- Match term: `Kairat`
- dedicated EventWatch target
- `MentionEveryone=false`

The smoke watch must be **disabled by default** in tracked configuration so a
checkout/deployment cannot unexpectedly publish test messages.

Document the environment-variable configuration needed to enable it temporarily.

The smoke watch must use the normal scheduled EventWatch path. When enabled
against a currently matching Riga FC page, it should therefore exercise:

Riga FC HTTP fetch
→ HTML parser
→ EventWatch detector
→ scheduled EventWatch job
→ notification publisher
→ configured Discord channel
→ notification checkpoint

This is intentionally stronger than the manual delivery test because it proves
the real external source/detector path works in the deployed application.

### 4. Keep smoke-test checkpoints isolated

The smoke test and production Atalanta watch must have independent source
identifiers/checkpoints.

A successful Kairat smoke test must have no effect on whether a future Atalanta
announcement or ticket-link alert can be delivered.

Add explicit regression coverage for this.

### 5. Document the production validation procedure

Update `docs/bot-configuration.md` with a short EventWatch verification
procedure:

1. configure the real EventWatch target;
2. run `/eventwatch test` and verify the expected Discord channel receives the
   test message;
3. run `/eventwatch status` and verify the Riga FC sources are reachable and
   parsed;
4. temporarily enable the isolated live smoke watch;
5. verify the scheduled job sends the smoke notification;
6. disable the smoke watch again;
7. leave the real Atalanta watch enabled.

Explicitly warn not to repurpose `riga-fc-atalanta-2026` for test data because
that could consume its real notification checkpoints.

## Implementation direction

Keep this focused within the existing EventWatch and Discord command
architecture.

Reuse:

- `RigaFcEventWatchSource`;
- `EventWatchSignalDetector`;
- `EventWatchService`;
- `IDiscordNotificationPublisher` / existing Discord destination handling;
- existing EventWatch configuration and validation.

Do not create a second independent scraper or a separate notification subsystem.

For `/eventwatch status`, prefer a small diagnostic service/model over putting
HTTP/parsing logic directly into the Discord command handler.

For `/eventwatch test`, prefer the existing delivery abstractions while
guaranteeing that the synthetic test cannot poison production checkpoints.

For the live smoke watch, use normal EventWatch configuration. Do not special
case `Kairat` in the detector implementation.

## Acceptance criteria

- [ ] A user can run `/eventwatch status` and see whether the live Riga FC
      source collection/parsing is functioning.
- [ ] Status distinguishes a healthy "no qualifying signal" result from a
      collection/parsing failure.
- [ ] Running status does not send EventWatch notifications or mutate delivery
      checkpoints.
- [ ] A user can run `/eventwatch test` and receive a clearly marked test
      message in the configured EventWatch Discord target.
- [ ] The manual delivery test is repeatable.
- [ ] The manual test never emits `@everyone`.
- [ ] Manual testing cannot consume the production Atalanta announcement or
      ticket-link checkpoints.
- [ ] A disabled-by-default isolated live smoke watch is available and
      documented.
- [ ] The smoke watch uses a watch ID different from
      `riga-fc-atalanta-2026`.
- [ ] With the current Kairat calendar entry available and the smoke watch
      enabled, the regular scheduled EventWatch path produces at least one
      qualifying smoke notification.
- [ ] Re-running the unchanged smoke watch does not repeatedly spam the channel;
      normal checkpoint suppression still applies.
- [ ] A successful smoke-watch checkpoint does not suppress either future
      Atalanta notification type.
- [ ] Existing Atalanta detection and duplicate suppression remain unchanged.
- [ ] Documentation includes the end-to-end production validation procedure and
      the environment variables/configuration required for the temporary smoke
      watch.
- [ ] Automated tests cover status diagnostics, repeatable safe test delivery,
      smoke/production checkpoint isolation, and scheduled smoke-watch duplicate
      suppression.
- [ ] `dotnet build MandarinBotNet.sln` succeeds.
- [ ] `dotnet test MandarinBotNet.sln` succeeds.

## Verification

Run:

```sh
dotnet build MandarinBotNet.sln
dotnet test MandarinBotNet.sln
```

Add focused tests proving:

1. status against a healthy no-sale fixture returns healthy/no-signal;
2. status against a matching fixture reports detected signal kinds without
   publishing;
3. status reports a source failure distinctly;
4. test delivery sends to the configured EventWatch target and does not allow
   an everyone mention;
5. test delivery can be run more than once;
6. smoke-watch delivery and Atalanta delivery use different checkpoints;
7. an unchanged smoke signal is delivered only once;
8. after smoke delivery, the Atalanta announcement and ticket-link
   notifications remain independently deliverable.

For the deployed manual verification, use the current Riga FC calendar candidate
if still present:

`Kairat`

Expected result: the live smoke watch detects the current ticket-related match
entry and sends to the dedicated configured EventWatch channel through the
normal scheduled job.

## Out of scope

- Changing the real Atalanta matching rules merely to make testing easier.
- Disabling or weakening normal notification checkpointing.
- Polling Biļešu Serviss directly.
- Building a general-purpose website monitoring framework.
- Adding recurring "everything is healthy" Discord reports.
- Sending test notifications automatically on startup.
- Keeping the temporary Kairat smoke watch enabled permanently.

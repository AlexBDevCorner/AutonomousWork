# MB-004 — Show all FPL price changes while preserving league team impact data

## Goal

Change MandarinBotNet's FPL price-change notification so every detected player
price change is shown, not only changes affecting players currently owned by
teams in the configured classic league.

Keep the existing league-specific enrichment as additional information:
identify which league teams own each changed player, keep the aggregate value
impact for the league, and keep the per-team value-change summary. This lets
managers see market-wide price drops and rises so they can spot transfer
opportunities while still seeing how the changes affect the league's current
squads.

## Context

- Project: `mandarinbotnet` (`projects/mandarinbotnet/project.yaml`).
- Target repository: `AlexBDevCorner/MandarinBotNet`.
- Default target branch: `main`.
- The existing price-change feature is implemented under
  `DiscordBot.FantasyPremierLeague/PriceChanges`.
- `FplPriceChangeService` already detects price changes for all FPL players.
- `FplLeaguePriceChangeService.CreateReportAsync()` already keeps all detected
  changes in `FplLeaguePriceChangeReport.PlayerChanges` and enriches each
  change with `OwnerEntryNames` for the configured classic league.
- The filtering happens in
  `FplPriceChangeMessageCompositionService.Compose()`: when league data is
  available it currently selects only entries where
  `OwnerEntryNames.Count > 0` and therefore hides price changes for unowned
  players.
- The same message composer is used by the scheduled
  `FplPriceChangeJob` and the interactive `/prices` command.
- Existing output already provides useful league information:
  - `В составах: ...` below an affected player;
  - total change in the value of league squads;
  - `📋 По командам:` with per-team value impact;
  - partial squad-load coverage warnings.
- `DiscordNotificationPublisher` already splits messages using
  `DiscordMessageChunker` and checkpoints multipart deliveries, so a longer
  all-player notification does not need a new Discord delivery mechanism.
- `PricesCommandHandler` also splits long command responses with
  `DiscordMessageChunker`.
- Current documentation in `docs/bot-configuration.md` states that the
  scheduled job hides changes that affect none of the league squads; this must
  be updated.

## Requirements

1. Change FPL price-change message composition so every item in
   `FplLeaguePriceChangeReport.PlayerChanges` is included in the user-facing
   output when price changes exist.

2. Do not filter a player out merely because
   `OwnerEntryNames.Count == 0`.

3. Preserve the existing per-player league ownership enrichment:
   - if one or more configured-league teams own the changed player, show the
     existing ownership information for that player;
   - if no configured-league team owns the player, still show the player's
     price change but do not fabricate an ownership line.

4. Preserve the existing price information for every listed player:
   - increase/decrease indicator;
   - player name;
   - previous price;
   - current price;
   - signed difference.

5. Preserve the existing aggregate league impact information when league data
   is available and at least one league squad is affected:
   - total change in squad value;
   - per-team value changes;
   - team impact values must continue to be based only on players actually
     owned by those teams, not on market-wide unowned players.

6. When league data is available but none of the changed players are owned by
   teams in the configured league:
   - still list every detected price change;
   - retain a concise indication that the league's current squads were not
     affected;
   - do not show misleading non-zero team totals.

7. Preserve the existing fallback behavior when league data cannot be loaded:
   all global price changes must still be shown and the existing warning that
   ownership could not be mapped to league squads must remain.

8. Preserve partial league-data behavior:
   - list all detected player price changes;
   - enrich ownership from the squads that were successfully loaded;
   - keep the existing coverage warning showing how many manager squads were
     loaded.

9. Apply the same composition behavior to both:
   - scheduled `FplPriceChangeJob` notifications;
   - the interactive `/prices` command.

10. Do not introduce an artificial cap such as "top N" changes. Every price
    change in the detected batch must be represented in the output. Existing
    Discord chunking must be relied on for long messages.

11. Preserve deterministic existing ordering of
    `FplLeaguePriceChangeReport.PlayerChanges`; this task must not add a new
    ranking, recommendation, or transfer-scoring algorithm.

12. Keep player/team external-name sanitization through
    `DiscordTextSafety.SanitizeExternalName`.

13. Update or replace the existing test
    `Compose_NoLeagueSquadsAffected_HidesGlobalNoise`, because hiding global
    changes is no longer desired.

14. Add automated message-composition coverage for at least:
    - a batch containing both an owned changed player and an unowned changed
      player: both appear;
    - only unowned changed players: all appear and the league-not-affected
      message is present;
    - owned players still show `В составах: ...`;
    - aggregate league and per-team impact remains correct and excludes
      unowned-player market changes;
    - league data unavailable: all changes appear with the fallback warning;
    - partial squad data: all changes appear and coverage warning remains;
    - external player/team names remain Discord-safe.

15. Add or update job/command tests as needed to prove the scheduled
    notification and `/prices` path both retain the complete composed output
    and continue to support messages exceeding Discord's single-message size.

16. Update `docs/bot-configuration.md` so the FPL price-change section
    describes the new behavior accurately:
    - every detected FPL player price change is included;
    - players owned in the configured league are annotated with their owners;
    - league total/per-team impact is still shown;
    - unowned players remain visible so managers can spot market opportunities.

17. Existing snapshot, source-identifier, notification checkpoint,
    scheduling, league-loading, and price-detection behavior must remain
    unchanged unless a small adjustment is strictly required to support this
    output change.

## Architectural direction

This should be a focused change to presentation/composition rather than a
redesign of the price-change subsystem.

The report model already contains the data needed for the requested behavior.
Prefer changing `FplPriceChangeMessageCompositionService` so it iterates all
`report.PlayerChanges` and adds ownership details only where present.

Keep `FplLeaguePriceChangeService` responsible for ownership and team-impact
calculation. Do not move Discord formatting into that service.

The intended information hierarchy is:

1. price-change heading;
2. league aggregate impact when applicable;
3. all detected player price changes;
4. ownership annotation directly under players owned in the configured league;
5. per-team impact summary when applicable;
6. partial-data/fallback warning when applicable.

Exact wording may stay close to the current Russian messages. The important
behavioral change is that league ownership enriches the global change list
instead of filtering it.

Do not manually pre-truncate the scheduled message. The shared
`DiscordNotificationPublisher` already chunks long messages and gives each
part its own delivery checkpoint. The `/prices` command already uses
`DiscordMessageChunker`.

## Acceptance criteria

- [ ] A scheduled FPL price-change batch lists every detected changed player.
- [ ] A changed player not owned by anyone in the configured league is visible
      in the Discord notification.
- [ ] A price decrease for an unowned player is visible, allowing league
      managers to notice a potentially cheaper transfer target.
- [ ] A changed player owned by one or more league teams still shows those team
      names.
- [ ] League-wide squad value impact remains correct.
- [ ] The `📋 По командам:` section remains available when one or more league
      teams are affected.
- [ ] Unowned market changes do not alter league team-impact calculations.
- [ ] If no league squad is affected, all market changes are still listed and
      the message states that the league squads were not affected.
- [ ] If league ownership data is unavailable, all changes are still listed
      with the existing fallback warning.
- [ ] Partial squad loading still reports coverage while showing all detected
      changes.
- [ ] `/prices` shows the same complete price-change list and league
      enrichment as scheduled notifications.
- [ ] Large batches continue to work through the existing Discord message
      chunking instead of being truncated.
- [ ] Existing deduplication/snapshot behavior is unchanged.
- [ ] Documentation no longer says global changes are hidden.
- [ ] `dotnet build MandarinBotNet.sln` succeeds.
- [ ] `dotnet test MandarinBotNet.sln` succeeds.

## Verification

Run in the target repository:

```sh
dotnet build MandarinBotNet.sln
dotnet test MandarinBotNet.sln
```

At minimum, automated tests must exercise a report equivalent to:

- Player A: price decreased, not owned by any league team.
- Player B: price increased/decreased, owned by one or more league teams.

Verify that the composed output contains both players, only Player B has the
ownership annotation, and league/team totals reflect only actual league squad
ownership.

Also verify a sufficiently large synthetic change batch produces output longer
than one Discord message and is handled by the existing chunking path without
dropping player changes.

## Out of scope

- Changing how FPL prices are fetched or how price differences are detected.
- Adding price predictions, transfer recommendations, ownership percentages,
  expected-points analysis, fixture analysis, or "best buy" scoring.
- Sorting players by attractiveness or recommending who managers should buy or
  sell.
- Changing the hourly FPL price-check schedule.
- Changing the configured Discord targets.
- Changing the notification checkpoint/deduplication model.
- Changing the stored price-snapshot format.
- Redesigning `DiscordNotificationPublisher` or
  `DiscordMessageChunker`.
- Changes to unrelated FPL, UCL, EventWatch, or AutonomousWork behavior.

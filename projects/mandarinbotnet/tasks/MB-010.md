# MB-010 — Simplify Riga FC EventWatch to monitor the real ticket catalogue

## Goal

Replace the current heuristic Riga FC EventWatch detection based on homepage,
calendar, and news content with a much simpler and more reliable rule:

**notify only when an individual ticket/product for the configured opponent
actually appears in Riga FC's ticket catalogue.**

Keep two real watches:

- Kairat — early production validation because this match happens before
  Atalanta;
- Atalanta — the actual target notification.

The Kairat watch should prove the exact same production path that will later be
used for Atalanta.

## Context

- Project: `mandarinbotnet`.
- Target repository: `AlexBDevCorner/MandarinBotNet`.
- Default target branch: `main`.
- Current EventWatch implementation was extended in MB-008 with:
  - `/eventwatch status`;
  - `/eventwatch test`;
  - a Kairat smoke watch;
  - isolated checkpoints.
- The current detector checks Riga FC homepage/calendar/news blocks for an
  opponent name combined with ticket-related wording or links.
- Real-world validation exposed a false-positive scenario:
  - Riga FC's calendar shows a **Tickets** action for Riga vs Kairat;
  - Riga vs Atalanta can also appear in the expanded calendar;
  - however, the currently available product is a package for the three UEFA
    Conference League home matches, not an individual ticket for Kairat or
    Atalanta.
- Therefore the calendar's generic **Tickets** action is not sufficient evidence
  that tickets for a specific match are on sale.
- Riga FC's public ticket landing page is:
  `https://rigafc.lv/biletes/`.
- The actual Riga FC shop ticket catalogue is:
  `https://shop.rigafc.lv/tickets`.
- At task creation time, the shop catalogue does not expose an individual
  Kairat or Atalanta ticket. This is the expected baseline state.

## Required behaviour

The EventWatch job should periodically inspect the real Riga FC ticket
catalogue and stay silent until a ticket/product specifically associated with
the configured opponent is visible.

Conceptually:

```text
fetch Riga FC ticket catalogue

for each enabled watch:
    if a ticket/product matching that watch's opponent is present
       and this watch has not already notified this target:
        send notification
```

For the two configured watches:

- Kairat watch matches an actual ticket/product containing `Kairat`;
- Atalanta watch matches an actual ticket/product containing `Atalanta`.

A generic Conference League package, generic `Tickets` link, calendar ticket
button, news article, fixture listing, or opponent mention outside the ticket
catalogue must not trigger either watch.

## Requirements

### 1. Use the ticket catalogue as the authoritative source

Change the Riga FC EventWatch source so normal opponent ticket detection is
based on the actual Riga FC ticket catalogue:

`https://shop.rigafc.lv/tickets`

Do not use homepage, calendar, or news pages as evidence that individual match
tickets are available.

The club landing page `https://rigafc.lv/biletes/` may remain documented as the
public entry point, but detection must ultimately inspect the actual catalogue
content where ticket products are listed.

If implementation discovers that `/biletes/` dynamically loads or redirects
to the same catalogue data, use the simplest stable HTTP source that exposes
the ticket products. Do not add browser automation unless it is genuinely
required.

### 2. Match the configured opponent against an actual ticket/product

A watch should produce a signal only when a catalogue ticket/product associated
with that opponent is present.

The implementation should match against a reasonably scoped product/card/item,
not arbitrary whole-page text.

Examples:

- product/title contains `Kairat` -> Kairat signal;
- product/title contains `Atalanta` -> Atalanta signal;
- product says only something equivalent to "UEFA Conference League home
  package" -> no Kairat or Atalanta signal unless the same actual product entry
  explicitly identifies that opponent and the implementation can demonstrate it
  represents an individual match ticket.

Do not infer individual availability merely because an opponent appears
somewhere else on the site.

### 3. Simplify the signal model where possible

The previous distinction between:

- announcement;
- ticket-link-available

was useful for homepage/news heuristics but may no longer be necessary when the
source itself is the ticket catalogue.

Prefer a single clear EventWatch "ticket available" signal per watch if the
catalogue provides enough evidence.

If retaining the existing signal types materially reduces implementation risk,
that is acceptable, but a single catalogue product must not cause confusing or
duplicate user notifications solely because two legacy signal types both fire.

The desired user experience is one useful notification that tickets for the
specific opponent are available.

### 4. Keep Kairat as a real early validation watch

Keep a Kairat watch using an isolated watch ID, for example the existing:

`riga-fc-smoke-kairat-2026`

It should no longer be treated as a synthetic false-positive smoke test. It is
now a real production validation watch:

- enabled temporarily or permanently until Kairat tickets appear;
- silent while no individual Kairat ticket exists;
- sends exactly one useful notification when an individual Kairat ticket first
  appears;
- proves the same catalogue monitoring path that Atalanta relies on.

Keep its checkpoints isolated from Atalanta.

### 5. Keep Atalanta as the production target

The existing production watch:

`riga-fc-atalanta-2026`

must remain independent and notify when the real ticket catalogue contains an
individual Atalanta ticket/product.

A Kairat notification must never suppress the future Atalanta notification.

### 6. Preserve manual diagnostics

Keep the useful MB-008 commands:

- `/eventwatch status`;
- `/eventwatch test`.

Update `/eventwatch status` so it reports the new catalogue-based source and
detection state.

It should clearly distinguish:

- catalogue reachable and parsed, opponent ticket not present;
- opponent ticket/product detected;
- catalogue fetch/parse failure.

`/eventwatch test` should continue to verify Discord delivery without
consuming normal Kairat/Atalanta checkpoints.

### 7. Preserve duplicate suppression

Once Kairat has notified a given configured target, unchanged catalogue content
must not send it repeatedly every scheduler run.

The same applies independently to Atalanta.

Use the existing notification checkpoint infrastructure rather than introducing
a second persistence mechanism.

### 8. Configuration

Keep the EventWatch schedule and dedicated targets configurable through the
existing `Bot__...` configuration model.

The tracked configuration should contain both watches disabled by default.

Example intent:

```text
riga-fc-smoke-kairat-2026 -> MatchTerms: Kairat
riga-fc-atalanta-2026     -> MatchTerms: Atalanta
```

Do not hard-code opponent matching logic specifically for Kairat or Atalanta in
the parser/detector. The mechanism should remain driven by configured watch
terms.

### 9. Remove obsolete heuristic complexity

Remove or simplify code that exists only to correlate fixture/news content with
generic ticket wording if it is no longer required by the catalogue approach.

In particular, normal detection should no longer depend on:

- homepage fixture blocks;
- calendar `Tickets` buttons;
- news articles;
- generic ticket-sale terms near an opponent;
- unrelated site-wide ticket links.

Keep the change focused. Do not redesign the whole scheduling or notification
framework.

## Acceptance criteria

- [ ] EventWatch normal detection uses the real Riga FC ticket catalogue rather
      than homepage/calendar/news heuristics.
- [ ] A calendar fixture with a generic `Tickets` button does not trigger
      Kairat or Atalanta.
- [ ] A generic multi-match Conference League package does not by itself count
      as an individual Kairat or Atalanta ticket.
- [ ] No notification is sent while the catalogue has no ticket/product
      specifically matching the configured opponent.
- [ ] A catalogue item for Kairat causes exactly one Kairat notification per
      configured target.
- [ ] A catalogue item for Atalanta causes exactly one Atalanta notification per
      configured target.
- [ ] Kairat and Atalanta use independent watch/checkpoint identities.
- [ ] A Kairat notification cannot suppress a later Atalanta notification.
- [ ] Re-running against unchanged catalogue content does not resend the same
      notification.
- [ ] `/eventwatch status` reflects catalogue reachability, parse result, and
      per-watch match state.
- [ ] `/eventwatch test` remains repeatable and does not consume production
      watch checkpoints.
- [ ] The tracked Kairat and Atalanta watch definitions remain disabled by
      default.
- [ ] Documentation explains that the bot watches the actual ticket catalogue,
      not the calendar's generic ticket button.
- [ ] Obsolete homepage/calendar/news matching complexity is removed or no
      longer used for these watches.
- [ ] `dotnet build MandarinBotNet.sln` succeeds.
- [ ] `dotnet test MandarinBotNet.sln` succeeds.

## Tests

Add/update tests covering at least:

1. empty ticket catalogue -> no signal;
2. generic Conference League package -> no opponent-specific signal;
3. calendar-style generic Tickets content cannot trigger because it is not an
   EventWatch source anymore;
4. catalogue product containing Kairat -> Kairat signal;
5. catalogue product containing Atalanta -> Atalanta signal;
6. Kairat product does not trigger Atalanta;
7. Atalanta product does not trigger Kairat;
8. unchanged Kairat catalogue product is delivered only once per target;
9. Kairat delivery does not consume Atalanta checkpoint;
10. status command reports healthy/no-match when catalogue fetch succeeds but
    opponent ticket is absent;
11. status command reports a detected match when a configured opponent product
    exists;
12. status command reports source failure distinctly.

## Documentation

Update `docs/bot-configuration.md` to explain:

- EventWatch now monitors the Riga FC ticket catalogue;
- `https://rigafc.lv/biletes/` is the public ticket landing page;
- the actual catalogue is `https://shop.rigafc.lv/tickets`;
- calendar `Tickets` buttons are intentionally ignored because they can point
  to package offers rather than individual match tickets;
- Kairat is the early real-world validation watch;
- Atalanta is the later target watch;
- how to enable each watch and configure its Discord target;
- how to use `/eventwatch status` and `/eventwatch test`.

## Verification

Run:

```sh
dotnet build MandarinBotNet.sln
dotnet test MandarinBotNet.sln
```

For deployed verification:

1. enable EventWatch scheduling;
2. configure and enable the Kairat watch;
3. run `/eventwatch test` to verify Discord delivery;
4. run `/eventwatch status`;
5. while no Kairat product exists, status should report healthy/no match and
   Discord should remain silent;
6. when an individual Kairat product appears in the real catalogue, the normal
   scheduled job should send one Kairat notification;
7. keep the Atalanta watch independently configured for later detection.

## Out of scope

- Browser automation unless the ticket catalogue cannot reasonably be read
  through HTTP.
- Polling unrelated third-party ticket websites.
- Treating generic competition packages as individual match tickets.
- Reintroducing homepage/calendar/news heuristics as fallback triggers.
- Sending periodic "nothing found" Discord reports.
- Changing unrelated FPL/UCL features.

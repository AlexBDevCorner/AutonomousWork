# MB-009 — Strengthen deterministic .NET quality gates for autonomous changes

## Goal

Strengthen MandarinBotNet's existing .NET quality guardrails so common AI-generated
code problems are caught mechanically during implementation and CI, before they
reach the separate PR reviewer.

Keep the change deliberately conservative: build on the repository's existing
`Directory.Build.props`, `Directory.Packages.props`, `.editorconfig`, locked
restore, formatting check, and warnings-as-errors instead of introducing a large
new quality platform or hundreds of opinionated rules.

## Context

- Project: `mandarinbotnet`.
- Target repository: `AlexBDevCorner/MandarinBotNet`.
- Default target branch: `main`.
- The repository already has a strong baseline:
  - `Directory.Build.props` enables .NET analyzers, code-style enforcement,
    locked restore in CI, and `TreatWarningsAsErrors`;
  - `Directory.Packages.props` provides Central Package Management;
  - `.editorconfig` provides formatting/style settings;
  - CI runs restore, build, tests, `dotnet format --verify-no-changes`, and a
    production-container build.
- The missing piece is a small curated analyzer layer that can catch more
  correctness, maintainability, async, and test-quality problems while OpenCode
  is still implementing a task.
- This task is intentionally not a bulk clean-code rewrite. The repository must
  remain practical for unattended autonomous work.

## Requirements

1. Add a conservative general-purpose C# analyzer package suitable for .NET 10.
   Prefer `Meziantou.Analyzer` unless repository constraints discovered during
   implementation make another focused analyzer clearly more appropriate.
2. Add/enable NUnit-specific analyzers for `DiscordBot.Tests`.
3. Manage analyzer package versions through the existing
   `Directory.Packages.props`; do not put new package versions directly into
   individual project files.
4. Analyzer packages must be development-only dependencies and must not flow as
   runtime/transitive dependencies to application consumers.
5. Keep the existing pinned numeric .NET analysis level. Do **not** replace it
   with `latest` or another moving analyzer baseline.
6. Extend `.editorconfig` only with a small set of high-signal rules that are
   useful for autonomous development. Favor correctness and maintainability
   over subjective formatting preferences.
7. The resulting analyzer configuration must be deterministic and CI-enforced:
   a newly introduced violation at warning/error severity must fail the normal
   build because the repository already treats warnings as errors.
8. Keep the repository green after enabling the analyzer layer.
   - Fix straightforward existing violations where the fix is clearly safer and
     behavior-preserving.
   - For noisy, subjective, or inappropriate analyzer rules, configure their
     severity explicitly rather than performing unrelated refactors solely to
     satisfy the analyzer.
9. Update package lock files as required by the repository's existing locked
   restore policy.
10. Update `AGENTS.md` only as needed to make the new mechanical quality gate
    explicit to autonomous workers. Do not duplicate large analyzer rule lists
    in prose when the build configuration is already authoritative.
11. Preserve all existing CI checks and production-container verification.

## Architectural direction

The purpose of this task is to move repeatable review concerns into deterministic
tooling:

`OpenCode implementation -> compiler/analyzers/format/tests -> PR reviewer`

Prefer rules that catch concrete defects or code-health problems such as:

- incorrect async/cancellation patterns;
- suspicious exception/error handling;
- nullability/correctness issues not already caught by the compiler;
- disposable/resource misuse;
- test mistakes that NUnit analyzers can identify.

Do not adopt broad style dogma merely because an analyzer supports it.

Use `PrivateAssets="all"` and appropriate `IncludeAssets` metadata for
analyzer-only package references where needed.

Keep the existing numeric `AnalysisLevel` so SDK updates do not silently change
the enabled Microsoft analyzer rule set.

## Acceptance criteria

- [ ] A focused general-purpose C# analyzer is active for production code.
- [ ] NUnit analyzer diagnostics are active for `DiscordBot.Tests`.
- [ ] New analyzer package versions are centrally managed in
      `Directory.Packages.props`.
- [ ] Analyzer packages do not become runtime/transitive application
      dependencies.
- [ ] The numeric .NET `AnalysisLevel` remains pinned.
- [ ] `.editorconfig` contains only a curated set of additional high-signal
      analyzer/code-quality settings.
- [ ] Existing code builds without analyzer warnings/errors after the change.
- [ ] Any baseline suppressions/severity reductions are narrow and explainable;
      there is no blanket `NoWarn` or repository-wide suppression of the new
      analyzer package.
- [ ] Existing formatting, test, locked-restore, and container-build gates remain
      intact.
- [ ] Package lock files are consistent with the new analyzer dependencies.
- [ ] The full CI-equivalent local verification succeeds.

## Verification

Run from the MandarinBotNet repository root:

```bash
dotnet restore MandarinBotNet.sln --locked-mode
dotnet build MandarinBotNet.sln --configuration Release --no-restore
dotnet test MandarinBotNet.sln --configuration Release --no-build --no-restore
dotnet format MandarinBotNet.sln --verify-no-changes --no-restore
docker build --tag mandarinbot:verify --file Dockerfile .
```

Also verify from the resolved dependency graph/project assets that analyzer
packages are used as analyzers/development assets rather than runtime
application dependencies.

## Out of scope

- Adding SonarQube, Qodana, CodeRabbit, or another hosted quality platform.
- Adding every available analyzer or enabling hundreds of low-signal style
  rules.
- Replacing the existing ChatGPT PR reviewer.
- Redesigning the autonomous worker or reviewer workflow.
- Changing application behavior, Discord features, scheduling, deployment, or
  infrastructure.
- Bulk refactoring unrelated code merely to satisfy subjective analyzer advice.
- Switching `AnalysisLevel` to `latest` or another moving baseline.
